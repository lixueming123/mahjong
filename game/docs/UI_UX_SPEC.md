## 1. 运行环境与全局约束

### 1.1 分辨率与窗口

| 项 | 冻结值 | 说明 |
| --- | --- | --- |
| 逻辑分辨率 | **1280 × 720**（16:9） | 本文所有坐标均指逻辑坐标，原点左上，单位 px |
| 窗口默认尺寸 | 1280 × 720（窗口标题「麻将 · ex_actor」） | `pygame.display.set_mode((1280,720))` |
| 小屏策略 | 若 `min((sw-80)/1280, (sh-80)/720) < 1.0`（即屏幕不足以 1:1 容纳 1280×720 并保留 80 px 边距）：按 `scale = min((sw-80)/1280, (sh-80)/720, 1.0)` 等比缩放并居中留黑边 | 不做分区重排，避免多套布局 |
| 坐标变换 | `screen = (logical * scale) + letterbox_offset`；鼠标输入必须用同一变换的反函数 `logical = (mouse - offset) / scale` | 点击命中与渲染共用一套变换 |
| 全屏 | 支持（`--fullscreen`），仍按上述等比缩放渲染 | 非验收项 |
| 最小可用分辨率 | 1024 × 576（scale = 0.8） | 低于此值字号不可读，启动时打印提示但继续 |

### 1.2 主循环与帧率

| 项 | 冻结值 |
| --- | --- |
| 目标帧率 | 60 FPS（`clock.tick(60)`），渲染与输入无关的定时逻辑用 `time.monotonic()` |
| 每帧 socket 帧处理上限 | 256 帧（防风暴；超出的帧留到下一帧，不丢弃） |
| 倒计时计算 | 每帧重算，基于 `time.monotonic()`，不依赖帧计数 |
| 网络 I/O | 独立读取线程 + `queue.Queue`（非阻塞主循环）；发送走同一 socket 的锁保护写 |
| 发送队列上限 | 64 帧；超限丢弃并记日志（避免触发服务端 `RATE_LIMITED`） |
| 本地出站帧上限 | 4 KB（本客户端的所有帧都远小于此；服务端单帧上限 64 KB，见 GAME_DESIGN 8.1） |
| 心跳 | 每 **5000 ms** 发一次 `ping`（GAME_DESIGN 8.1）；收到 `pong` 时刷新「延迟/连接」指示 |

### 1.3 美术约束（硬性）

1. **只使用 pygame 几何绘制**：`pygame.draw.rect` / `line` / `polygon` / `circle` / `aaline`。**不加载任何外部图片资源**（无 PNG/JPG/SVG/字体文件）。
2. **只使用系统字体**：`pygame.font.SysFont(name, size)`（或 `pygame.font.match_font` 查找）。候选族按顺序：
   `["PingFang SC", "Heiti SC", "Hiragino Sans GB", "Microsoft YaHei", "Noto Sans CJK SC", "WenQuanYi Micro Hei", "Arial Unicode MS", "DejaVu Sans"]`。
   全部候选都缺失时回退 `pygame.font.Font(None, size)`，中文将显示为方块，但**不得崩溃**，并在日志中记一条 WARN。
3. **无音效、无动画资源**。允许的唯一动效是「状态切换的 120 ms 淡入」（见 §13）。
4. 牌面绘制 = 圆角矩形 + 描边 + 文字，分两类：
   - **数牌**（`1m`..`9s`）：数字 `rank`（大号，中央偏上）+ 花色字（万 / 筒 / 条，小号，**右下角**）+ 花色配色 `SUIT_M`/`SUIT_P`/`SUIT_S`（§1.4）。
   - **字牌**（`1z`..`7z`）：**单个字符居中，无花色角标、无数字**，配色统一为 `SUIT_Z`（§1.4）。字形**冻结为繁體**：

| 编码 | `1z` | `2z` | `3z` | `4z` | `5z` | `6z` | `7z` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 字形 | 東 | 南 | 西 | 北 | 白 | 發 | 中 |

   > **名称与字形的关系（避免歧义）**：`1z`..`7z` 的**规范名**用简体（东/南/西/北/白/发/中）——即 `PROTOCOL.md` §2.1 与 `RULESET.md` §1.2 映射表使用的写法；**牌面上的字形**冻结为**繁體**（東/南/西/北/白/發/中）。两者指同一张牌，实现方在日志/代码注释里可用规范名，在牌面绘制时必须用繁體字形。
   > **繁體字形的冻结依据（实测）**：本机 `pygame.font.match_font` 实际选中 **Hiragino Sans GB**（候选表中 PingFang SC / Heiti SC 未命中，回退链生效）；对 `東南西北白發中` 的覆盖度实测**零缺字**，简体 `东南西北白发中` 亦零缺字，回退链末端 DejaVu Sans 同样零缺字。选择繁體的理由是牌面上「發」「東」等字形辨识度高于简体，且**无方框风险**（结论由 t16 作者的只读字体预检提供）。
5. 所有颜色为本文 §1.4 冻结值，禁止使用随机色或未定义色。

```

**硬性迁移规则**

1. 握手链路是**串行**的：`login` → 等 `login_ok` → **停在大厅** → `create_room` 或 `join_room` → 等 `room_joined`（仍停在大厅）→ 点「开始对局」发 `ready` → 等 `game_start`。
   `login_ok` **不得**自动建桌，`room_joined` **不得**自动 `ready`（v1.9）。少发一帧会停在大厅或「准备中…」，此时必须有「返回登录」。
   唯一的例外是结算页「再来一局」：登录成功后跳过大厅，建桌并且自动 `ready`（§9.5 第 7 条）。
2. `SCREEN_TABLE` → `SCREEN_RESULT` 只由 `game_end` 触发；不允许由本地推断（如「手牌打空」）触发。
3. `SCREEN_RESULT` 是**终态**：本里程碑不允许从结算回到**本局**牌桌（`GAME_DESIGN.md` 2.3）。两个出口都是「断开重连」（v1.8 起都自动复用凭据，不必重输账号密码）：
   - 「返回大厅」→ 断开 → 重连 → `login` → `login_ok` → **`SCREEN_LOBBY`**（停留，玩家可看战绩、再点「开始对局」）；
   - 「再来一局」→ 断开 → 重连 → `login` → `login_ok` → **直接 `create_room`**（跳过大厅）→ 进入**新房间的新一局**（v1.6）。
   两者都**不是**同一房间的续局：协议无「离开房间」帧，结算后的连接在服务端仍属该房间，且房间在 `game_end` 后 30 秒被回收（`PROTOCOL.md` §1.4.5）。
4. `SCREEN_ACTIONBAR` 的显示条件是「本连接最近收到一帧 `action_request` 且该窗口尚未被任何新帧推进」，判据见 §5.1。
5. 同一时刻最多一个操作栏；新 `action_request`（新 `seq`）**替换**旧操作栏内容并重置倒计时。

### 3.3 昵称与账号本地预校验（与服务端 3.5 / `ACCOUNT_DESIGN.md` §3.1 一致）

| 规则 | 本地行为 |
| --- | --- |
| 长度 1..16 个字符（按 Unicode 码点计） | 输入框长度计数 `n/16`；超 16 拒绝继续输入（不截断已有文本，直接忽略按键） |

| 全空白（trim 后为空） | 「进入牌桌」置灰禁用，状态行提示「昵称不能为空」 |

### 3.4 提交链路（v1.5：游客「进入牌桌」/ 账号「登录」/「注册」）

```
点击主按钮（游客：「进入牌桌」；账号：「登录」）/ 账号模式点「注册」
  ├─ 本地校验通过？
  │    否 → 状态行红字，不发帧
  └─ 是
       ├─ 主按钮 → 「连接中…」（禁用）
       ├─ 建立 TCP 连接（连接超时 3000 ms）
       │    ├─ 失败 → 状态行「连接失败：<原因>（重试 n/3）」（§8.2）
       │    └─ 成功 → 按模式发送握手第一帧：
       │             游客   login{name}
       │             登录   login{username,password}
       │             注册   register{username,password}
       ├─ 等 login_ok{player_id,name} ── 游客 3 秒 / 账号 8 秒未到 → 状态行「服务器无响应」（§8.2）
       │    ├─ 收到 error{INVALID_NAME} → §8.3，主按钮恢复可用
       │    ├─ 收到 error{AUTH_FAILED|USERNAME_TAKEN|ALREADY_ONLINE|INTERNAL(账号服务)} → §8.5，断开并回到可编辑状态
       │    └─ 收到 login_ok → 进入 SCREEN_LOBBY（不发 create_room）
       │         （注册成功同样回 login_ok —— 注册即登录，`ACCOUNT_DESIGN.md` §3.2）
       └─ 之后的建桌、加入、开局全部在大厅完成（§12）
```

- 模式页签只在 `IDLE` 时可切换（连接/握手中不可换）；切换不清空已输入文本。
- 账号模式收到 `game_end` 后自动发一次 `stats_request`，把累计战绩显示在结算页 footer（§9.5、`ACCOUNT_DESIGN.md` §5.5）。

- 登录界面**没有**房间号/座位选择控件。建桌和加入都在大厅（§12）。
- 「准备中…」状态下必须保留「返回登录」出口（点击 = 断开并回到可编辑状态），避免卡在死等（§8.6）。

### 4.4 牌元素几何与绘制（冻结）

| 牌位 | 尺寸 (w×h) | 圆角 | 数牌字体 | **字牌字体（v1.3 冻结）** |
| --- | --- | --- | --- | --- |
| 本家手牌 | 56 × 76 | 6 | rank 26px 粗体 + 花色字 15px（右下角） | 單字 **34px 粗體** 居中，**无角标** |
| 牌河（中央） | 30 × 38 | 3 | rank 16px + 花色字 11px（右下角） | 單字 **20px 粗體** 居中，**无角标** |
| 牌河（左右列） | 26 × 32 | 3 | rank 14px + 花色字 10px（右下角） | 單字 **17px 粗體** 居中，**无角标** |
| 副露 | 28 × 36 | 3 | rank 15px + 花色字 10px（右下角） | 單字 **19px 粗體** 居中，**无角标** |
| 他家手牌背 | 16 × 16 | 3 | 无文字（纯 `BACK` 圆角矩形 + `BACK_EDGE`） | 无文字（同左，牌背不区分数牌/字牌） |
| 结算和牌张 | 100 × 120 | 8 | rank 44px + 花色字 22px（右下角） | 單字 **56px 粗體** 居中，**无角标** |
| 结算手牌 | 42 × 56 | 4 | rank 22px + 花色字 13px（右下角） | 單字 **28px 粗體** 居中，**无角标** |

> **字牌字号与角标（D3，冻结）**：上表 7 档字号全部写死，实现方**不得自行取值**；字牌一律**单行单字 + 无花色角标 + 不旋转**（渲染器从不旋转文本；本文中「竖排/纵列」仅指**网格排布方向**，不要求字形转向）。字牌与数牌共用同一套圆角与描边参数。

**牌面绘制规则（`draw_tile(surface, rect, face, opts)`）**

1. 底：`pygame.draw.rect(..., border_radius=)`，填充 `FACE`，`FACE_EDGE` 1px 描边。
2. 文本（按牌种类二分，v1.3）：
   - **数牌** `face = "<rank><m|p|s>"`（`rank ∈ {1..9}`）：中央偏上居中绘制 `rank` 数字，右下角小号绘制花色字（`m→万`、`p→筒`、`s→条`）；颜色 = `SUIT_M`/`SUIT_P`/`SUIT_S`。
   - **字牌** `face = "<1..7>z"`：**居中等宽绘制单个繁體字形**（`1z→東`、`2z→南`、`3z→西`、`4z→北`、`5z→白`、`6z→發`、`7z→中`），**不绘制数字、不绘制角标**；颜色 = `SUIT_Z`。字号取上表「字牌字体」列（按牌位档位）。
   - 未知/非法牌面字符串走第 5 条；`{a,b}` 之类多张牌不合并渲染（每张独立）。
3. 牌背：`BACK` 填充 + `BACK_EDGE` 描边 + 内部 1px 内嵌十字线（两条对角线可选，仅装饰）。
4. `opts` 标记位（按优先级叠加，最多同时 2 种）：
   - `selected`：`SELECT` 3px 描边 + 整体上移 **8 px**；
   - `drawn`：`DRAWN` 2px 描边 + 上移 **4 px** + 右上角 14×14 `DRAWN` 实心方块（无文字）；
   - `win_tile`：`SELECT` 3px 描边 + 微放大 1.08×（结算页专用）。
5. 未知/非法牌面字符串（防御性）：渲染为 `FACE` 底 + 中央 `?`（`NEG` 色），并在日志记 WARN；**不崩溃**。

### 4.5 本家手牌区（可点击、选中高亮）

| 项 | 规则 |
| --- | --- |
| 内容 | `hand[]`（本家未副露手牌）逐张渲染，**保持服务端下发的顺序**（GAME_DESIGN 3.1 排序：花色 `m<p<s`，同花色 rank 升序；同牌面副本相邻）。客户端**不重新排序**，避免与服务端顺序不一致导致点击错位 |
| 张数 | `concealed = 13 − 3×melds`（等待态）/ `14 − 3×melds`（行动态），故手牌区长度 ∈ {13,14} **− 3×副露组数**：无副露时 13/14（庄家第一打为 14），有 1 组副露时 10/11。**明杠会把 3 张手牌移入副露**（`melds` +1 ⇒ `concealed` −3），物理持有 = 13/14 + 杠数（GAME_DESIGN 3.2） |
| 居中 | `total_w = n*58 - 2`；`x0 = 640 - total_w//2`；`y0 = 566`（选中/摸牌标记会向上溢出到 558，需在 558 以上留空） |
| 命中测试 | 逐张 `rect` 判断；`logical_mouse` 在 `rect` 内（含 8px 上移后的实际矩形）即命中；同一 x 只可能命中一张 |
| 选中 | 单击 → 该张标记 `selected`（金色描边 + 上移 8px），并记录 `selected_index`（**下标**，不是牌面字符串，因同牌面副本不可区分） |
| 改选 | 单击另一张 → 选中转移 |
| 取消 | 右键 / `Esc` → 清除选中 |
| 确认打出 | 再单击**同一张**，或按 `Enter`，或点「打牌」按钮 → 构造 `discard{tile, seq}`（§5.5） |
| 可点条件 | 仅当：①最近一帧 `action_request` 的 `window == "discard"`；②PENDING 状态为假；③倒计时 `remaining_ms > 0`；④未处于结算/断线状态。否则手牌区为只读（无高亮、不响应点击） |
| 摸牌标记 | 收到本家 `draw{tile}` 后，在 `hand[]` 中标记**一张**与 `tile` 同牌面的牌为 `drawn`（并入列排序后就地标记，取同牌面中**最左**的一张；副本不可区分，见 GAME_DESIGN 5.6.2）。**不设置独立摸牌槽位**，理由：排序要求（3.1）与副本不可区分性（5.6.2） |
| 张数交叉校验 | 若 `len(hand) + 3*len(melds) ∉ {13,14}`（GAME_DESIGN 3.2 口径），在 HUD 右侧显示 `WARN` 色「张数异常」并记日志；**不修改**本地数据 |

#### 4.7.1 单座位牌河张数上限（推导，用于容量设计）

一局最多 **84** 次打牌：牌山 **83** 张，**每次摸牌（含杠补牌）恰好对应 1 次打牌**，另加庄家第一打 1 次（GAME_DESIGN 3.3 第 5 条：每次摸牌使 `remaining` 减 1；杠补牌取自**同一副 83 张牌山**，不额外增加牌数，故与杠数无关）。
四座位轮流，单座位上限 `⌈84/4⌉ = **21**`。中央牌河 24 容量与左右 27 容量均**大于实际需求**（**21 ≤ 24**），因此紧凑模式在**当前 136 口径下常规对局不会触发**；该规则**保留**，其作用为**防御性容量保护**：一旦某座位牌河张数 > 24（例如后续改为长局、多局累计牌河、或再引入花牌等使单座位牌河超过 24 张的口径）即自动启用，避免渲染溢出与索引越界。**原「安全上限 25」口径作废**（v1.3）。

- **关闭**：`ESC`、点击面板外、再点一次「战绩」按钮。断线时断线蒙层优先，战绩弹窗不绘制。
- 打开面板**不产生任何出站帧**（除那一次 `stats_request`），不影响 `seq`、不参与窗口判定。

## 5. 操作界面（`SCREEN_ACTIONBAR`，与牌桌同屏）

### 5.1 操作栏的显示与推进（判据冻结）

| 事件 | 操作栏行为 |
| --- | --- |
| 收到 `action_request{seq,deadline_ms,window,options}` | **显示/替换**操作栏；记录 `current_seq = seq`、`window`、`options`、`deadline_ms`；倒计时重置；清除 PENDING |
| 本家发出 `discard` / `action` | 进入 **PENDING**（所有按钮 `BTN_DISABLED`，文案「已提交：<动作>」，手牌不可点选）；倒计时条保留显示并继续走（服务端窗口可能在别处推进） |
| 收到与 `current_seq` **不同**的 `seq`（仅比较**携带 `seq` 的帧**：`action_request` / `state_sync` / `action_event` / `discard_event` / `draw`） | 清除 PENDING；若新帧是 `action_request` 则按新窗口重建，否则**隐藏**操作栏 |
| 收到**不携带 `seq`** 的帧（仅 `game_end`，见 GAME_DESIGN §11.2/§11.4） | 清除 PENDING；`game_end` 直接迁移 `SCREEN_RESULT`（操作栏随结算隐藏） |
| **兜底规则**（防御性，适用于实现方按不带 `seq` 的帧变体处理时） | 收到本家 `discard_event`（= 本家打牌已生效）或**任一** `action_event`（= 本窗口已结算）→ **立即清除 PENDING**，不等 `seq` 比较；随后按 §5.1 首行的规则重建或隐藏操作栏 |
| 倒计时归零 | 见 §6.4（不代打、不发帧、禁用一切点击） |
| 收到 `game_end` | 隐藏操作栏 |
| 断线 | 隐藏操作栏（断线蒙层接管） |

- **只有收到 `action_request` 才进入可操作态**：客户端**绝不**用「`state_sync.current_seat == 本家`」自己开操作栏
  ——因为鸣牌窗口只发给有非 `pass` 选项的座位（GAME_DESIGN 4.2 步 7、5.1），未收到即表示本家无选项。
- 操作栏始终绘制在 `R_BAR` 内，不遮挡手牌区（手牌区下沿 644，操作栏上沿 650）。

#### 5.3.1 「过」在打牌窗口为什么不出现（重要，防 error 帧）

- `GAME_DESIGN.md` 5.1/5.3 明确：`window == "discard"` 的 `options` **只承载「是否和牌」**（`[{"action":"win"}]` 或 `[]`），
  打牌本身由 `discard{tile,seq}` 表达，`pass` **不在**打牌窗口的 `options` 中。
- 因此客户端在打牌窗口**不提供**「过」按钮：若点了，将发出 `action{pass}` 而该动作不在 `options` 中，
  服务端按 5.6.1 第 3 行回 `error{ILLEGAL_ACTION}`（违反 GD-C1「全程零 error 帧」）。
- 「放弃自摸」的正确表达 = **直接打牌**（不回复 `win`，服务端即视为放弃，5.6.2 的超时代打口径与此等价：放弃自摸机会 + 打出牌）。
- 打牌窗口 `options` 含 `win` 时，界面在「胡」按钮旁显示中性提示「也可直接点手牌打牌（本局不胡）」，帮助玩家理解
  （该提示不含「过」按钮，也不使用「放弃」等 §0.3 禁词）。
- ⚠️ **协议待澄清项 S1（提交 t1/t10）**：`PROTOCOL.md` 应写明「打牌窗口的合法回复是 `discard{tile,seq}` 或 `action{win,seq}`；
  在打牌窗口回 `action{pass,seq}` 视为 `ILLEGAL_ACTION`」。避免服务端实现者把 `pass` 也接受为打牌窗口的合法回复而破坏 `options` 校验一致性。

### 5.4 手牌点选 → 确认打出的完整交互流程（冻结）

```
① 打牌窗口开启（window=="discard" 且 remaining_ms>0 且非 PENDING）
     → 手牌区进入可点选态：鼠标悬停在某张牌上时该牌 1px 亮边（BTN_HOVER 色，不算选中）
② 第一次左键单击某张牌
     → selected_index = 该张下标；渲染 SELECT 描边 + 上移 8px
     → 「打牌」按钮由禁用变启用（BTN）
     → 状态提示：「已选中 4 筒，再点一次或按 Enter 打出」（牌名用 §5.3 文案公式，不再显示线上牌码）
③ 再次左键单击同一张（或 Enter / 点「打牌」按钮）
     → 构造 discard{tile: <该下标对应的牌面字符串>, seq: current_seq}
     → 发送；进入 PENDING：该牌灰显 + 下沉 6px（不移除）、按钮组禁用、提示「已提交：打牌」
④ 单击另一张 → 选中转移（回到 ②）
⑤ 右键 / Esc → 清除选中，「打牌」按钮回到禁用
⑥ 超时归零 / 窗口被推进 → 强制清除选中与 PENDING
```

| 边界情形 | 处理 |
| --- | --- |
| 同一牌面有多张副本 | 选中按下标记录；发出 `discard{tile}` 只携带牌面字符串（副本不可区分，GAME_DESIGN 5.6.2）；本地移除「最左同牌面」那一张 |
| 双击过快（< 120 ms 两次单击） | 视为两次单击 = 选中 + 确认（等价双击打出），是**期望行为**，无需去抖 |
| 在 PENDING 期间继续点手牌 | 忽略，并抖动 1 帧的 `NEG` 描边提示 |
| 倒计时最后 1 秒内确认 | 允许提交；`seq` 若已过期，服务端静默丢弃（5.6.1），本地在下一次 `state_sync`/`discard_event` 后清 PENDING 并显示服务端的真实结果 |
| 选中期间窗口被新 `seq` 推进 | 清除选中（新窗口的 `options` 可能不同） |
| `hand[]` 变为空（异常） | 手牌区显示「手牌为空」红字，禁用一切打牌入口，并请求一次 `sync` |

### 5.5 `discard` / `action` 帧的构造规则（防 error 帧客户端自律）

| 规则 | 说明 |
| --- | --- |
| `seq` 必须回带 | 取最近一次 `action_request.seq`（`current_seq`），**禁止**使用更早的 `seq`（GAME_DESIGN 10.6 第 2 条） |
| 无窗口不发帧 | `current_seq is None` 时，发送函数直接返回 False（UI 层已经禁用入口） |
| 动作必须在 `options` 内 | 发送前断言：`discard` 需要 `window=="discard"`；`action{act}` 需要 `act`（与 `tiles` 组合）出现在 `options` 中 |
| `tiles` 语义 | `win: []`；`kong/pong: [T]`；`chow: [a,b]`（手中两张）；`pass: []`（GAME_DESIGN 5.2） |
| 不在一次事件里连发 | 每帧最多发送 1 帧 `discard`/`action`（避免触发限速） |
| 出站节流 | 发送队列上限 64；同一 `seq` 只允许一次动作提交（PENDING 即锁） |
| 心跳独立 | `ping` 每 5000 ms 一次，与动作无关（GAME_DESIGN 8.1） |

## 6. 倒计时表现（冻结）

### 6.1 形式

- **进度条 + 数字双表现**，两者都在操作栏倒计时区（`(8,650,224,66)`）。
- 数字：`ceil(remaining_ms / 1000)`，显示为 `"<n> s"`（如 `14 s`）；`remaining_ms < 1000` 时显示一位小数（如 `0.4 s`）。
- 进度条：前景宽 = `round(208 * remaining_ms / window_ms)`，钳制在 `[0, 208]`。
- 颜色分级（数字与进度条同色）：

| 剩余时间 | 颜色 | 附加表现 |
| --- | --- | --- |
| `> 10000 ms` | `POS` | 无 |
| `3000..10000 ms` | `WARN` | 无 |
| `< 3000 ms` | `NEG` | 每秒闪烁 2 次（400 ms 相位，交替 60% 透明度） |
| `== 0` | `NEG` | 数字显示 `0 s`，进度条空；文案切到「已超时，等待服务端行动」（§6.4） |

### 6.2 数据来源（字段冻结）

| 数据 | 来源 | 用法 |
| --- | --- | --- |
| 窗口序号 | `action_request.seq` | 与本地 `current_seq` 比较；不等即视为窗口已推进（§5.1） |
| 服务端截止时刻 | `action_request.deadline_ms`（服务端系统时钟 epoch 毫秒，UTC） | `remaining_server = deadline_ms − now_epoch_ms`（客户端 `time.time()*1000`） |
| 本地兜底截止 | 收到该帧时的单调时钟 + 窗口时长估计 | `remaining_guard = recv_monotonic + window_ms_est − time.monotonic()` |
| 窗口时长估计 | 首帧：`window_ms_est = clamp(deadline_ms − recv_epoch_ms, 1000, 60000)` | 区间与 GAME_DESIGN 5.4 的 `[1000,60000]` 一致；避免硬编码 15000 而在 `--action-timeout-ms` 变化时兜底错误 |
| 显示用剩余 | `remaining_ms = max(0, min(remaining_server, remaining_guard))` | **取两者较小值**（保守），防御时钟偏差（GAME_DESIGN 5.2 明确要求客户端做本地兜底） |

- 所有差值计算使用单调时钟（`time.monotonic()`）做兜底项，绝不用 `sleep` 累计。
- 时钟偏差过大（`|remaining_server − remaining_guard| > 5000 ms`）时：HUD 显示 `WARN` 色「时钟偏差」，但**不改变**上述「取较小值」的判定。

### 6.3 倒计时与窗口类型的关系

| 窗口 | 倒计时是否显示 | 说明 |
| --- | --- | --- |
| `discard`（自家） | 是 | 玩家决定打牌（或自摸）的窗口 |
| `claim`（自家） | 是 | 玩家决定 碰/吃/杠/胡/过 的窗口 |
| 他家窗口 | **否**（本家收不到 `action_request`，因此操作栏隐藏，不显示他家倒计时） | 与他家行动相关的进度只通过 `discard_event`/`action_event`/`state_sync` 呈现 |
| AI 座位 | 不存在倒计时 | AI 时延 0 ms（GAME_DESIGN 7.1），窗口在同一消息处理内结算，客户端可能只看到事件连发 |

### 6.4 归零时的界面行为（冻结）

1. **客户端不做任何代打、不发任何帧**。超时代打由服务端执行（GAME_DESIGN 5.6.2），客户端只等待结果。
2. 倒计时区：数字 `0 s`（`NEG`）、进度条空、文案「已超时，等待服务端行动」。
3. 手牌区：全部取消选中高亮，**不可点选**（悬停无反馈）。
4. 按钮区：全部按钮 `BTN_DISABLED`（不隐藏，保持布局稳定），鼠标悬停显示 tooltip「已超时」。
5. 中央情报区追加一行 `WARN` 色小字：「本轮将由服务端代为行动」（1.5 秒后淡出）。
6. 随后按收到的帧更新：
   - 本家打牌窗口超时 → 服务端代打 → 收到 `discard_event{seat==本家, tile}` → 从手牌区移除该张、牌河追加，清 PENDING。
   - 鸣牌窗口超时 → 服务端记 `pass` → 收到下一位的 `state_sync`（或 `action_event`）→ 操作栏隐藏。
7. **异常兜底**：归零后 **5000 ms** 内未收到与该窗口相关的任何帧（`discard_event` / `action_event` / `state_sync` / `game_end`），
   显示底部横幅「服务器无响应（5 秒无状态更新）」+ 提供「返回登录」按钮；**不自动重连、不本地推进牌局**。
8. 归零后若玩家仍点了手牌（理论不可点，防御性）：本地一律忽略，绝不补发 `discard`/`action`（避免 `seq` 过期后被静默丢弃造成困惑）。

### 7.2 三种「不可绕」的保证（协议层 / 数据层 / 渲染层）

| 层 | 保证 |
| --- | --- |
| **协议层（服务端责任）** | `game_start.hand` / `state_sync.hand` 只包含收件人自己的手牌，服务端按座位过滤后逐座位单独下发（GAME_DESIGN 8.2）；`draw{tile}` 只发给摸牌者本人（11.2）；不存在查询他家手牌的请求类型（`sync` 只返回调用者视角） |
| **数据层（客户端数据结构）** | 客户端为每个座位维护的视图对象字段**固定为**：`seat, name, is_bot, hand_count, discards[], melds[], disconnected`（外加本家专属 `hand[]`、`melds[]`）。**不存在**任何可存放他家牌面字符串的字段；本家 `hand[]` 之外没有第二个牌面数组 |
| **渲染层** | 他家手牌渲染函数签名固定为 `draw_opponent_hand(view: SeatView)`，函数体内**只允许**读 `view.hand_count`；渲染他家牌面属于实现缺陷（代码评审项） |

### 7.3 禁止的绕过途径清单（逐条禁止）

1. 不使用 `state_sync.seats[i].hand`（协议已规定他家不含 `hand`；即便服务端有 bug 下发了，客户端**必须**：不渲染、不写入本地状态、记一条 WARN、并（可选）在 HUD 显示「协议异常」提示。**绝不显示牌面**）。
2. 不从 `hand_count` 变化、`draw` 事件时序、牌河与副露做**牌面推断**（禁止维护「他家手牌可能集合」这类数据结构）。
3. 不发送任何非 `GAME_DESIGN.md` 11.1 列出的消息类型；不尝试 `sync` 之外的私有视图请求。
4. 日志与调试输出只写「本家视角」：帧日志中若出现 `seats[].hand` 非空，写 `"[REDACTED]"`；日志文件**禁止**出现他家牌面。
5. 调试面板（默认**关闭**，快捷键 `F1` 可开）只显示：本家 `hand`、`seq`、`remaining`、`current_seat`、最近 8 帧的 `type`；**不显示**任何他家牌面的原始 JSON。
6. 不提供「导出对局」「本地回放」功能（避免把服务端 bug 泄漏的私有信息固化到文件）。
7. 结算页允许展示 `results[win.seat].hand`（14+杠数 张）：这是服务端在结算时**主动公开**的信息（GAME_DESIGN 6.4），不属于私有信息泄漏。
8. 断线托管期间（`disconnected == true`）不降低任何隔离要求；被托管座位的牌面依然不可见。

## 8. 状态与错误态（四种必答情形 + 错误码全表）

### 8.1 通用呈现机制

| 机制 | 位置 | 表现 | 消除条件 |
| --- | --- | --- | --- |
| 顶部错误条 `OVERLAY_ERROR` | `(240,36,800,44)` 居中 | `PANEL` 底 + `NEG` 2px 描边；主文案 = 服务端 `error.message`（若为空用本地映射文案）；下方小字 = `code`（15px，`TEXT_DIM`） | 4 秒后自动消失，或收到下一帧 `state_sync`/`action_request` 时立即消失 |
| 底部状态横幅 `OVERLAY_BANNER` | `(240,610,800,32)`（操作栏隐藏时 `(240,668,800,32)`） | `WARN`/`NEG` 底 + 白字 + 可选按钮（重试 / 返回登录） | 状态恢复或用户点击 |
| 断线蒙层 `OVERLAY_DISCONNECT` | 全屏 `MASK` | 中央面板 `(440,280,400,160)`：「连接已断开」+ 原因 + 「返回登录」 | 只能由用户点「返回登录」 |
| 战绩弹窗 `OVERLAY_STATS`（v1.7） | 全屏 `MASK` + 面板 `(340,96,600,440)` | 见 §4.12 | `ESC` / 点击面板外 / 再点「战绩」按钮（断线时优先显示断线蒙层） |

### 8.2 情形一：服务器未启动 / 连接失败

| 触发 | 可见提示 | 后续行为 |
| --- | --- | --- |
| `connect()` 被拒（ConnectionRefused / 无监听） | 登录界面状态行红字：`连接失败：无法连接 127.0.0.1:9527（重试 1/3）`；「进入牌桌」恢复可用 | **自动重试 3 次**：间隔 1 s / 2 s / 4 s；3 次全失败后状态行改为 `无法连接服务器，请确认服务端已启动` + 显示「重试」按钮（手动） |
| 连接超时（3000 ms 未完成三次握手） | 同上，文案 `连接超时（3 秒）` | 同上 |
| 连接成功但 3000 ms 内未收到 `login_ok` | 状态行 `服务器无响应（未返回 login_ok）` | 保留连接、显示「重试」按钮（重发 `login`，最多 3 次）；3 次后建议「返回登录」（断开重连） |
| 已连接后 socket 被服务端关闭（EOF） | 见 §8.4 | 见 §8.4 |
| 连上后 `ping` 连续 3 次未收到 `pong`（>16 s） | HUD 连接点变 `NEG` + 底部横幅 `连接不稳定（心跳无响应）` | 不主动断开，继续等待；20 s 无任何入站帧 → 进入 §8.4 断线蒙层 |

> 服务端默认端口 9527（GAME_DESIGN 附录 A）；客户端启动参数 `--host` / `--port` 覆盖，登录界面「目标服务器」行如实显示。

### 8.3 情形二：非法昵称

| 阶段 | 可见提示 | 后续行为 |
| --- | --- | --- |
| 本地预校验失败（空 / >16 字符，含控制字符被忽略） | 输入框 `NEG` 2px 描边；状态行红字：`昵称不能为空` / `昵称最多 16 个字符（当前 18）` | 不发帧；「进入牌桌」禁用；用户修改输入后清除红框 |
| 服务端回 `error{code:"INVALID_NAME"}` | 输入框 `NEG` 描边 + 状态行红字：`昵称非法：需 1..16 个字符，且不含换行或控制字符（第 n/3 次）` | **保留输入内容**；「进入牌桌」恢复可用；`invalid_name_count++`；`n == 3` 时额外提示 `再提交一次将被断开连接` |
| 第 4 次非法（服务端断开连接） | 转入 §8.4 断线蒙层，原因文案 `昵称连续非法，服务端已断开连接` | 只能「返回登录」（回到可编辑的登录界面） |
| 服务端回 `error{code:"AUTH_FAILED"}`（v1.5） | 状态行红字 `账号或密码错误`；密码框 `NEG` 描边（账号名保留） | 断开并回到可编辑的登录界面（客户端不自动重试）；非空、非活动、非生产环境**不得**回显口令 |
| 服务端回 `error{code:"USERNAME_TAKEN"}`（v1.5） | 状态行红字 `账号名已被占用`（账号名保留，可改名或改点「登录」） | 同上；不改动输入内容 |
| 服务端回 `error{code:"ALREADY_ONLINE"}`（v1.5） | 状态行红字 `该账号已在别处登录` | 同上；**必须**与该账号的其它错误区分提示（用户需去关闭旧会话） |
| 服务端回 `error{code:"INTERNAL"}` 且 `message == "account service unavailable"`（v1.5） | 状态行红字 `账号服务暂不可用` | 同上；游客模式与对局不受影响 |

- 客户端发送前对昵称 `strip()` 首尾空白，但**不做**其它改写（不截断、不替换字符），保证用户看到的与服务端判定的一致。

### 8.4 情形三：游戏中断线（对局中掉线）

| 触发 | 可见提示 | 后续行为 |
| --- | --- | --- |
| socket 关闭 / 读线程异常 | 全屏 `MASK`（alpha 150）+ 中央面板：`连接已断开` / `对局进行中，服务端将托管你的座位（不等待 15 秒窗口）` / 按钮「返回登录」 | **冻结画面**：保留最后一帧渲染结果（牌桌、手牌、牌河、副露、剩余牌数全部保留但只读），禁用所有交互；**不自动重连**（GAME_DESIGN 8.3 明确不做断线重连与状态恢复） |
| 20 秒未收到任何入站帧（心跳超时，客户端侧判断） | 先显示底部横幅 `网络无响应（20 秒）`，再升级为断线蒙层 | 同上 |
| 断线前已收到 `game_end` | **不显示断线蒙层**，直接进入 `SCREEN_RESULT`（结算数据完整，可正常查看） | 结算页「返回大厅」→ 断开重连 → 大厅（§9.5） |
| **在大厅里断线**（v1.8） | **不显示断线蒙层**（此时还没有对局，谈不上托管）：直接回到 `SCREEN_LOGIN`，状态行红字写原因（如 `连接已断开：…`）后可从登录界面重来 | 「返回登录」或重新提交登录 |
| 他家座位 `disconnected == true`（自己仍在连线） | 该座位昵称后缀 `（断线托管）` + 昵称条 `WARN` 描边 | 牌局继续（托管由服务端执行）；结算页该座位保留该后缀（GAME_DESIGN 8.3） |
| 托管后想继续玩 | 断线蒙层的「返回登录」是**唯一**出口 | 重新 `login` + `create_room` 开新的一局（旧房间已无恢复入口） |

- 断线蒙层出现的瞬间，客户端：停止 `ping` 定时器、关闭 socket、清空发送队列、**保留**已解析的显示状态（用于画面冻结），清空 `current_seq` 与 PENDING。

### 8.5 情形四：非法操作被服务端拒绝（`error` 全表）

> 客户端**设计目标**是守规矩时零 `error` 帧（`GAME_DESIGN.md` GD-C1）；本表是防御性兜底。

| `code` | UI 文案（`message` 为空时的本地兜底） | 呈现位置 | 后续行为 |
| --- | --- | --- | --- |
| `INVALID_NAME` | 「昵称非法：需 1..16 个字符，且不含换行或控制字符」 | 登录界面状态行 + 输入框红框 | 见 §8.3 |
| `NOT_LOGGED_IN` | 「会话未建立（客户端缺陷）」 | 顶部错误条 | 这是客户端 bug 的信号：记日志、清理本地状态、断开并回到登录界面自动重新 `login` |
| `ROOM_NOT_FOUND` | 「房间不存在或已关闭」 | 顶部错误条 | 提供「重新建桌」按钮 → 重发 `create_room`（登录态仍有效）；房间号清空 |
| `NOT_YOUR_TURN` | 「还没轮到你」 | 顶部错误条（`WARN` 底） | 清除 PENDING 与选中；若本地仍有 `discard` 窗口则手牌恢复可点，否则隐藏操作栏；**不改变**牌桌状态；随后自动请求一次 `sync` 对齐 |
| `NO_PENDING_ACTION` | 「当前没有需要你处理的动作」 | 顶部错误条（`WARN` 底） | 清除 PENDING；隐藏按钮组（等待新 `action_request`）；自动请求一次 `sync` |
| `ILLEGAL_ACTION` | 「该动作当前不可用」 | 顶部错误条 | 清除 PENDING；按最近一帧 `action_request` 的 `options` **重建按钮组**（保证只显示合法动作）；若已无有效窗口则隐藏操作栏 |
| `UNKNOWN_TILE` | 「牌不在你的手牌中（操作可能已过期）」 | 顶部错误条 | 清除选中 + PENDING；请求一次 `sync`；手牌区以下一帧 `state_sync.hand` 为准 |
| `BAD_REQUEST` | 「请求格式错误（客户端缺陷）」 | 顶部错误条 | 记日志（含出站帧类型）；请求一次 `sync`；服务端会累计坏帧（10 次断开，GAME_DESIGN 8.1），本地同时提示「继续出现该错误将被断开」 |
| `FRAME_TOO_LARGE` | 「发送帧过大」 | 顶部错误条 | 本客户端的出站帧都 < 4 KB，出现即实现缺陷：记录出站帧长度并断开重连（防止被判罚） |
| `RATE_LIMITED` | 「操作过于频繁，请稍候」 | 底部横幅 | 本地进入 **1000 ms 发送节流**；丢弃排队中的非心跳帧；提示用户正常游戏不会触发 |
| `INTERNAL` | 「服务端内部错误」 | 顶部错误条（`NEG`） | 提示「牌局可能无法继续」+ 提供「返回登录」；不自动重试 |

**统一规则**

1. 任何 `error` 都**不改变**本地牌桌状态（不增删手牌、不改牌河），只清除「待确认」类临时态（PENDING / 选中）并按需 `sync` 对齐。
2. `error_count` 累加并在 HUD 右侧显示「非法操作 n/10」；服务端在第 10 次断开连接（GAME_DESIGN 8.2）→ 客户端转 §8.4；`n ≥ 7` 时提示文案变红。
3. 不弹出堆栈、不弹出模态对话框（除登录/断线两处），避免打断牌桌操作；错误条永不超过 4 秒。
4. 所有 `error` 都写一条客户端日志：`{ts, code, message, outbound_frame_type, current_seq}`（不含他家私有信息）。

### 9.3 和牌者手牌的分组渲染规则（冻结，可机械实现）

输入：`hand = results[win.seat].hand`（长度 `14 + 该家杠数`，按 GAME_DESIGN 3.1 排序，含和牌张）；
`melds[] = 最后一帧 state_sync.seats[win.seat].melds`，其元素形状已由 GAME_DESIGN **§11.2.1** 冻结为 `{type, tiles[]}`（`type ∈ {pong, chow, kong}`；`kong` 组 4 张）。
`hand` 与 `melds[]` **并存**：`hand` 是扁平数组（门前手牌 + 副露牌面），**不替代**分组信息。

```
① 复制 hand 为 multiset M
② for each meld in melds[]:            # 按 melds[] 原顺序
       在 M 中扣除一组它自己的 tile（与 melds[].tiles 多重集匹配，扣最左匹配项，保证确定性）
       → 渲染为「副露组」框（组内按 tiles 顺序），kong 组渲染 4 张，组框右上角小字标注「碰/吃/杠」
③ 剩余牌面（= 门前手牌。逻辑上 = 14 − 3×melds 张，含和牌张）按 3.1 排序渲染为一行
④ 在剩余牌行中，把「最左的那张与 win.tile 同牌面」的牌标记 win_tile（SELECT 描边 + 1.08× 放大）
⑤ win.tile 同时在 (500,246,120,120) 放大位单独显示
⑥ 若 hand 与 melds 无法匹配（数据异常）：退化为「不分组，整行按 hand 顺序渲染」，记 WARN，不崩溃
```

> 荒庄分支：`win == null` → 隐藏和牌张放大位、收付文案、和牌者手牌区（该区替换为居中文案「本局不计分」）；
> 四张卡片 `delta_score` 全为 0（灰）。GAME_DESIGN 6.5 的「荒庄文案」在此显示。

### 9.5 「返回大厅」/「再来一局」行为（冻结）

1. 关闭 socket（若仍连接）；停止 `ping` 与读线程。（v1.8 起「返回大厅」**随后立刻重连**，见第 7′ 条；「返回登录」才停在这一步。）
2. 清空全部本地状态：`hand[]`、`melds[]`、四家视图、`room_id`、`seat`、`dealer`、`current_seq`、PENDING、`error_count`、`deadline`。
3. 迁移到 `SCREEN_LOGIN`，昵称/账号名输入框**保留**上次输入（便于再来一局），但清空角色/连接状态；
   **密码框清空**（不保留口令），并按上次的模式（游客/账号）恢复登录界面状态。
   （这条只适用于「返回登录」这一出口；「返回大厅」v1.8 起不停在登录界面。）
4. 登录界面状态行显示「已返回大厅（本局已结束）」2 秒。
5. 若 5 秒内 socket 仍未关闭成功（服务端已回收），本地强制关闭并继续（服务端在 `game_end` 后 30 秒回收房间，GAME_DESIGN 2.2 ⑧）。
6. **战绩块（v1.5 起为一行；v1.7 扩为块）**：账号模式下，客户端在收到 `game_end` 后自动发一次 `stats_request`；
   收到 `stats` 后在按钮上方绘制「汇总一行 + 最近 ≤10 局（2 列 × 5 行）」（坐标见 §9.2、渲染规则见 §4.12）。
   游客会话该区域留空，footer 只有底注文案（GAME_DESIGN §11.2 `stats`、`ACCOUNT_DESIGN.md` §3.4/§5.5）。
7′. **「返回大厅」（v1.8 改写）**：= 第 1–2 条（断开 + 清空对局状态）之后立即重连：
   `login` → `login_ok` → **`SCREEN_LOBBY`**（停在这里，不再回登录界面、不用重输账号密码）。
   因为换的是新连接，服务端那条「一个玩家一个房间」的记录也随之翻篇——大厅里点「开始对局」立刻能开新局
   （老房间由服务端在 `game_end` 后 30 秒自行回收，`PROTOCOL.md` §1.4.5）。
7. **「再来一局」（v1.6；v1.8 保持一键）**：= 第 1–2 条之后立即重连并**跳过大厅**直接建桌：
   `login` → `login_ok` → `create_room` → `room_joined` → `ready` → `game_start` → `SCREEN_TABLE`。
   - 游客模式复用当前昵称；账号模式复用刚用过的账号名与口令（即上次提交的握手帧），无需重输。
   - 连接失败与超时按 §8.2/§8.6 的既有出口处理（状态行 + 「返回登录」）。
   - 账号模式可能撞上「上一连接刚关、服务端还没释放账号」的竞态：`error{ALREADY_ONLINE}` 时客户端**自动短重试**
     （约 300 ms 间隔、至多 5 次），全部失败才按 §8.5 提示。
   - 服务端**零改动**：不新增帧，不新增房间语义；新房间就是既有 `create_room` 的结果（`room_id` 递增）。

### 10.3 客户端对 `seq` 的使用规范（与 5.6.1 对齐）

| 场景 | 客户端行为 |
| --- | --- |
| 收到 `action_request{seq}` | `current_seq = seq`；本地窗口开启 |
| 发送 `discard`/`action` | 必须回带 `current_seq`；若为 `None` 则拒绝发送 |
| 收到与 `current_seq` 不同的 `seq`（**仅比较携带 `seq` 的帧**：`action_request` / `state_sync` / `action_event` / `discard_event` / `draw`；`game_end` 无 `seq`，直接迁移结算页） | 视为旧窗口已结束：清 PENDING / 选中 / 倒计时，按新帧重建界面 |
| 兜底：收到不携带 `seq` 的窗口相关帧 | 收到本家 `discard_event` 或任一 `action_event` → 直接清除 PENDING（见 §5.1 兜底规则），不依赖 `seq` 比较 |
| 自己提交后又被静默丢弃（迟到） | 客户端**不会**收到 `error`（5.6.1）；因此 PENDING 必须由「下一帧 seq 变化或本家 `discard_event`」来解除，绝不设「超时自动重发」 |
| 重发策略 | **禁止自动重发**（会触发静默丢弃与限速）；玩家需在新窗口内重新操作 |

### 10.4 契约冲突处理

1. 若 `PROTOCOL.md` 的字段名与 `GAME_DESIGN.md` 第 11 章不一致 → 以 `GAME_DESIGN.md` 为准（§0.1），本文的字段引用随之修正。
2. 若 `PROTOCOL.md` 提供了 §10.2-D 中「不需要」的字段 → 客户端**不消费**，不因此增加界面元素。
3. 若 `PROTOCOL.md` 缺少 §10.2-B 的任一必需字段 → 对应界面元素无法落地，属**阻塞缺陷**，须由 t1 补齐后再实现客户端。

### 12.2 交互（冻结）

| 操作 | 行为 |
| --- | --- |
| 停留在大厅 | 每 1 秒发一次 `list_rooms`（仅 `SCREEN_LOBBY` 且已登录）。用 `room_list` 刷新列表，不改当前房间 |
| 点「新建房间」 | 发 `create_room`。按钮置灰直到 `room_joined` 或 `error`。成功后**仍停在大厅**，状态行「已在 `room_id`，座位 0，点「开始对局」开局」。不发 `ready` |
| 点某一房间行 | 若已在该房间：不发帧。若已在别的房间：状态行「已经在房间里」，不发帧。否则发 `join_room{room_id}`。成功后同样停在大厅，座位号以 `room_joined.seat` 为准 |
| 点「开始对局」（或 Enter） | 仅当已收到 `room_joined` 且对局未开始。发 `ready`，状态行「准备中…（等待 game_start）」，直到 `game_start` 进入牌桌。未进房时按钮禁用，Enter 改为「新建房间」 |
| 点「返回登录」（或 ESC） | 关闭 socket、清空会话与战绩快照、迁移 `SCREEN_LOGIN`（昵称/账号名保留，口令清空）。未开局时房主断开会拆掉房间，其他玩家断开则把座位还给 AI |
| 点「退出」 | 关闭 socket 与窗口 |
| 建桌或加入失败 | 按 §8.5。`ROOM_NOT_FOUND` 的「重新建桌」= 再点一次「新建房间」 |
| 在大厅断线 | 回 `SCREEN_LOGIN`，状态行写明原因；**不**显示 `OVERLAY_DISCONNECT`（§8.4） |

- 未开局的房间永远是 4 个座位：空位是 AI。别人加入是顶掉一个 AI 座位，不是把房间撑过 4 人。有人点「开始对局」之后列表里不再出现这间房，后来的 `join_room` 失败。
- 大厅**不提供**改昵称/换账号：要换身份走「返回登录」（§9.5 的口径不变：登录界面保留昵称、清空口令）。
- 大厅里的战绩与牌桌弹窗（§4.12）、结算页战绩块（§9.2）共用同一份 `stats` 快照与同一套行版式。

### 12.3 与既有冻结项的关系

1. 建桌仍是 `create_room`，加入仍是 `join_room`，开局仍是 `ready`。v1.9 把这三步都放在大厅里由玩家分开点，不再连成一次点击。
2. §2.2 硬性迁移规则第 1 条是「`login_ok` → 大厅 → 新建或加入 → `room_joined` → 开始对局 → `ready` → `game_start`」。
3. 本界面**不**改变任何 `seq`、窗口、倒计时或私有信息规则（点「开始对局」之前没有对局）。
