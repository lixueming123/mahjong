## 一、风格定义

### 1.1 风格定位：「深色绒毡上的黄铜铭牌」

播报带不是弹窗、不是贴纸，是**刻在结算面板上的一块黄铜铭牌**：三块下沉凹槽，内部一律无渐变无阴影；只有一个金色指示物在移动。

| 维度 | 定义 |
| --- | --- |
| 材质 | 三块**下沉凹槽**（比面板更暗、无高光），内部**无渐变、无阴影**；只有「番值徽标」「封顶徽标」是微凸亮面小块 |
| 光照 | 全屏唯一高光 = **当前行左侧 4 px 金色竖条** + 该行 `SELECT` 12% 行底。同时只允许**一处**金 |
| 色彩 | 墨绿黑底；信息色三系：金 `SELECT`（结论/当前）、绿 `POS`（得分）、红 `NEG`（失分）；其余全灰阶 |
| 密度 | 左密右疏：番种区 7 行等距小字（数据表），中区 5 行（算式），右区 3 行（结论）。行距全为整数像素 |
| 同源 | 圆角链 8（面板）/6（卡片）/4（按钮、字幕条、凹槽）/3（徽标）；描边链 2（面板）/1（凹槽、分隔、徽标） |

**明确不做**：逐条弹入/飞入；14 个彩色番种图标；发光描边外扩（特效侧）；番数数值滚动（R3 已裁定）。

**新增（4 个，全为「底/条」类，不引入新语义色）**

| token | 值 | 用途 | 为什么不复用 |
| --- | --- | --- | --- |
| `T.BC_ZONE` | `(14,22,20,150)` | 三块凹槽的统一填充 | `PANEL` 只比面板暗 10 灰阶，肉眼不可分；需要「下沉」层级 |
| `T.BC_ACTIVE_BG` | `(255,200,64,30)` | 当前行行底（`SELECT` @12%） | 无半透明金；硬填 `SELECT` 会把文字对比压到 1.4:1 |
| `T.BC_CAPTION_BG` | `(0,0,0,120)` | 字幕条底 | `MASK` α150 过重且是全屏语义，塞进面板会「挖洞」 |

### 1.3 字号阶梯（三段 + 辅助）

| 层级 | 字号 | px | 字重 | 用在哪 | 对比度 |
| --- | --- | --- | --- | --- | --- |
| ① 数据行（最密最轻） | `FS_SMALL` | **15** | 常规 | 番种名、番数值、算式标签、支付方位 | 7.9:1 |
| ② 关键结论（跳出来） | `FS_H3` / `FS_H2` | 22 / **28** | 粗体 | 合计番数（28）、倍率 `×R`（28）、字幕正行（22） | 10.7–14.0:1 |
| ③ 支付结果（钱） | `FS_BODY` | **18** | 粗体 | `−16` / `+16` / `−384` 支付数值列 | 4.96:1（`NEG`，见 R5 红线） |
| 辅助 | `FS_MICRO` | **12** | 常规 | 区标题、徽标数字、「上限 6 番」注、跳过提示 | 7.9:1 |

> 三档倍数关系必须 **15 / 22–28 / 18**：15 与 28 恰好 1.87×，形成「扫一眼落下第二眼」的错位；18 是「数字但非结论」的中间档。
> 禁止把番种行做到 18（会与支付数值抢视觉），禁止把合计番数做到 40（会与标题 `FS_H1` 抢层级）。

### 1.4 形语言

| 元素 | 规则 |
| --- | --- |
| 凹槽（三区） | `rect(radius=4)`，填 `T.BC_ZONE`，1 px `PANEL_EDGE`；**封顶时中区描边 2 px `T.SELECT`** |
| 番值徽标 | `20×15 rect(radius=3)`，**填充无描边**（省 1 draw），`FS_MICRO` 数字居中；档位色见 §3.3 |
| 高亮竖条 | 纯 `rect`，`border_radius=0`，宽 0/2/4，高 = 行高 |
| 字幕条 | `952×32 rect(radius=4)` 黑底 + 左侧 4 px `T.SELECT` 竖条 |
| 封顶徽标 | `244×22 rect(radius=3)`，`T.BC_CAP_FILL` 底 + 2 px `T.SELECT` 边 |
| 芯片（庄家/自摸） | `120×22 rect(radius=3)`，1 px 边、**无填充**；生效 = 边 `POS`/`DEALER` + 亮字 |

#### 3.3.1 溢出处置（唯一答案，R1 已采纳）

| 条件 | 表现 |
| --- | --- |
| `n ≤ 7` | 逐条渲染 |

#### 3.5.1 定宽数字排法（**R3 补件：滚动时不抖的对齐方案**）

**问题**：支付数值要滚动（220 ms `ease_out_cubic` + 末 40 ms 锁值），而 `R_BC_PAY` 内宽只有 200 px。数字从 `0` 滚到 `−32`／`+384` 时，若按「整串渲染 + 右对齐」，字串宽度每帧变化 ⇒ 右对齐锚点不动、但**左沿会左右跳**，多位数字滚动时整行「抽搐」。

**方案：数字位槽（digit cell）排法——每个字符占一个固定宽的槽，逐槽居中绘制。**

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `BC_DIGIT_W`（数字位槽宽） | **11 px** | `FS_BODY 18` 下 `0–9` 在候选字体栈（Hiragino Sans GB / PingFang / DejaVu）的最大 advance ≈ 10.1 px，取 11 留 0.9 余量 |
| `BC_SIGN_W`（符号槽宽） | **13 px** | `−`（U+2212）/`+` 比数字宽，取 13 |
| 数值区右锚 | `x_right = 1104` | 支付区内容右沿 1108 内缩 4 |
| 最大位数 | **4 位** | 实测上界：`per_payer` ≤ 128（3 位）、`total` ≤ 384（3 位）；留 1 位给未来封顶调整 |
| 数值块总宽 | `BC_SIGN_W + 4 × BC_DIGIT_W = 13 + 44 = 57 px` | 固定，**不随内容变化** |
| 数值块左沿 | `1104 − 57 = 1047` | 与方位标签区（`908..1040`）留 7 px |
| `−384` 实际占宽 | `13 + 3×11 = 46 px` | 居中在 57 px 块内 ⇒ 左侧留白按位数补空槽 |

**绘制规则（三条，逐字实现）**
1. 先算 `digits = str(abs(value))`，`pad = 4 − len(digits)`；
2. 符号槽 `(x_right − 57, …, 13, h)`：`value < 0` 画「−」、`> 0` 画「+」、`== 0` 不画（**`0` 不带符号**，与既有 `{delta:+d}` 会产生 `+0` 的差异，这里以「0 不画符号」为准，避免 `+0`/`−0`）；
3. 数字从右往左逐槽绘制：槽 k（从右数，k 从 0 起）`x = x_right − 11*(k+1)`，每个字符**在 11 px 槽内 `ALIGN_CENTER`**。

**为什么用「定宽槽 + 逐字居中」而不是等宽字体**：pygame 没有 OpenType `tnum`（tabular figures）控制，`SysFont` 也无法指定字重/特性；而候选字体栈里 Hiragino Sans GB 的数字是比例字宽（`1` 明显窄于 `8`）。逐槽居中把「字宽差异」吸收进槽内留白，**视觉上等价于等宽数字**，且不依赖任何字体特性——这是唯一在零外部资源约束下可保证不抖的做法。

**滚动时的额外约束**：滚动全程**不改变字号、不改变字重、不改变槽宽**，只改槽内字符 ⇒ 数值块外框恒定 57 px，右对齐永不抖。锁值后（末 40 ms）不得再有字形变化。

**两处改动（与动效 v1.1 对齐）**
1. **删掉「（倒计时已暂停）」六字**：它可能是不实陈述（若服务端局间时钟照走），且「冻结的秒数 → 解冻跳变」本身就是 bug。改为「播报中…」——在「时间真暂停」与「时间照走」两种语义下都成立。
2. **不要呼吸描边**（回复动效 §5 第 1 问）：① 本案 1 px 描边在全站是**输入框/按钮**的语言（`login.py` 输入框、`draw_button` 均用 1 px 边），给它加边会让倒计时行看起来可点；② 「播报正在进行」已由字幕条 + 金色竖条 + 高亮行三重表达，描边无信息增量；③ 省 1 draw，留给更紧的地方。

### 4.8 绘制预算核算（重算，回应动效 §6）

按本文件规格，播报带**新增**绘制项（不含既有四卡/手牌/战绩）：

| 区块 | draw | 说明 |
| --- | --- | --- |
| 字幕条 | 4 | 底 + 左条 + 文本 +（跳过提示，P2 可省） |
| 三区凹槽 | 6 | 3 rect + 3 描边 |
| 番种区 S1 | 36 | 竖条 7 + 当前行底 1 + 徽标 7 + 徽标数字 7 + 名 7 + 番值 7 |
| 链区 | 16 | 区标题 1 + 段 2（2）+ 段 3（芯片 4 + 文本 2）+ 段 4（封顶态 3）+ 5a（2）+ 5b（2） |
| 支付区 | 6 | 区标题 1 + P1（2）+ P2（2）+ P3（1） |
| **合计新增** | **68** | 动效算的 64 未含「徽标数字」与「P3 公式行」 |

**结论：68 次，不是 56，也不是 64。** 三个可选的削减档（按「信息损失从小到大」排）：

| 档 | 削减 | 省 | 剩余 | 损失 |
| --- | --- | --- | --- | --- |
| 完整版 | — | 0 | **68** | 无 |
| 建议版 | 凹槽只画描边不填充（`T.BC_ZONE` 取消，改靠 1 px 边分区） | −3 | **65** | 分区感变弱，但 8 px 间隙仍在 |
| 建议版+ | 再砍段 3 芯片边框（改纯文本双色） | −4 | **61** | 芯片不再像「开关」，靠颜色区分生效 |
| 底线版 | 再砍番值徽标（改纯色阶文字） | −14 | **47** | 失去番值扫读的视觉节奏，仍符合红线 |

**我的推荐：建议版+（61）**——保留徽标（它是「番值可扫读」的关键），牺牲凹槽填充与芯片边框。若架构侧 p95 吃紧，直接跳到底线版（47）。
**真正的性能大头不是这 68 次**，而是：① `render/result.py:218` 每帧 `Surface(1280×720)`（221 MB/s，**必须缓存蒙层**）；② 文本 `font.render`（约 20 条/帧，**必须做 `(text,size,bold,color)` 缓存，稳态帧 0 次**）。这两条不解决，68→47 也救不了 p95。
