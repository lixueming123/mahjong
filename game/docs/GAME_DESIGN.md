### 0.3 一致性硬约束（来自 ex_actor）

ex_actor 的 `Send` 不可取消、mailbox 不可撤回、actor 执行不可抢占；**并且** actor 的 handler 一旦挂起，框架就会把下一条消息交给同一个 actor（`include/ex_actor/internal/actor.h` 的 drain loop）。因此原子性必须自己保证，本项目的做法是**每个 actor 一个协程锁**（`game/server/async_gate.h`）：

1. 超时**不使用**任何取消机制，统一采用**「seq 作废」**方案（见 5.6）。
2. 任何窗口超时消息到达 RoomActor 时，先比对 `seq`；不匹配即丢弃，不产生任何状态变更。
3. 每个 actor 只有**一个公开入口** `Dispatch(<X>Envelope)`，入口处取该 actor 的 `AsyncGate`。**因此一次消息处理就是一次原子状态转移**：在该次处理内**允许** `co_await`（含向其它 actor 发送），但一次决策禁止拆到多条消息里分几次完成。
4. 向多个座位推送状态必须在**同一次消息处理内并行发出并逐条等待**（`stdexec::when_all` / `exec::async_scope`）：禁止逐座位串行等待（延迟累加），也禁止 fire-and-forget（顺序会丢）。投递对象是各座位的 `ConnectionActor`（`ActorRef<SeatEndpoint>`），不再有共享出站队列。
5. 存在先后依赖的两步（如「先发帧、再记配额」，后者可能触发断开）必须**按序**落地，保证前一步已经生效；本次实现用同一条消息承载这两步。

## 1. 游戏定位与目标体验

### 1.1 定位

- **形态**：1 名真人玩家 + 3 个服务端 AI 的四人牌桌，一局定胜负（无场次、无连庄）。
- **体验目标**：类「雀魂」式的日麻牌桌仪表感——四方位布局、手牌可点选、牌河可视化、轮到本人时弹出带倒计时的操作栏、结算页展示四家得失分与和牌牌型。
- **技术定位**：这是 ex_actor 框架上的一个**可运行样例游戏**，优先保证「一局能从头跑到结算」的确定性、可复现性，而不是玩法深度。
- **规则深度（已冻结，不得扩大）**：
  - 9 级 × 3 门（万 / 筒 / 条）= 27 种数牌 + 7 种**字牌**（`1z`..`7z` = 东/南/西/北/白/发/中）= **34 种牌面**，每种 4 张，**共 136 张**；
  - **有**字牌、**无**花牌、无宝牌、无立直、无振听；
  - **无役种表、无符数**：任何和牌型都成立，基础分为底分 1；
  - 和牌型 = 标准型（4 面子 + 1 将）或 七对子；清一色为叠加倍率（不是独立牌型）；
  - 副露 = 碰 / 吃 / 明杠（不含暗杠、加杠）。

### 1.2 目标体验的量化指标

| 指标 | 目标值 | 说明 |
| --- | --- | --- |
| 一局时长 | ≤ 120 秒（固定 seed 的端到端脚本内） | 由 t6 脚本的兜底超时判定 |
| 真人决策次数（典型区间） | 约 20..90 次 | 牌山 83 张，每次决策窗口 ≤ 15 秒；**估计值，不是验收项** |
| 单帧延迟 | 本机回环，≤ 10 ms | 非硬性验收项 |
| 一局最少消息往返 | login → login_ok → create_room → room_joined → ready → game_start → … → game_end | 见第 2 章 |
| 复现性 | 同一 `--seed` 必须得到完全相同的牌山与 AI 决策序列 | 洗牌与 AI 均确定性，见 7.5 |

## 2. 核心循环

### 2.1 循环总览

```
┌──────────────────────────────────────────────────────────────────────┐
│ ① 登录       客户端连接 127.0.0.1:9527 → login{name} → login_ok      │
│ ②′ 大厅      身份、战绩、未开局房间列表；新建或加入后仍停在这里       │
│ ② 建桌/加入  create_room 占 seat 0；join_room 顶掉一个 AI 座位        │
│ ③ 座位就位   空位保持 AI；开局前可被其他真人替换                      │
│ ④ 开局       房内真人点「开始对局」发 ready → game_start              │
│ ⑤ 局内       摸打循环 + 副露 + 和牌判定（第 4/5 章）                   │
│ ⑥ 局终       和牌（荣和/自摸）或 荒庄（牌山摸尽）                      │
│ ⑦ 结算       game_end{reason, results[4], win} → 结算界面             │
│ ⑧ 回大厅     「返回大厅」→ 客户端断开 → 回到 ①（本里程碑为单局，      │
│              不提供同房间直接开第二局）                                │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 逐阶段定义

| # | 阶段 | 触发方 | 服务端行为 | 下发消息 | 可见信息 | 超时 / 异常行为 |
| --- | --- | --- | --- | --- | --- | --- |
| ① | 登录 | 客户端 `login{name}`（游客）或 `login{username,password}` / `register{...}`（账号） | 游客：校名校（1.4）并分配进程内 `player_id`；账号：查库校验并分配持久 `player_id`（`ACCOUNT_DESIGN.md` §1.2） | `login_ok{player_id,name}` | 玩家自己的 id 与昵称 | 非法昵称回 `error{INVALID_NAME}`，连接保持，最多 3 次后断开；账号错误回 `AUTH_FAILED`/`USERNAME_TAKEN`/`ALREADY_ONLINE`（连接保持），账号服务不可用回 `INTERNAL` |
| ②′ | 大厅 | 客户端 | 回答 `list_rooms`：只列出还没 `ready` 的房间 | `room_list` | 房间号、房主昵称、已入座真人数 / 4 | 断线 → 回登录界面（此时无对局，不涉及托管） |
| ② | 建桌或加入 | 客户端 `create_room` 或 `join_room` | 建桌：新 `room_id`，真人占 `seat 0`。加入：开局前把最小编号的 AI 座位换成该真人 | `room_joined{room_id,seat,seats[]}` | 房间号、自己的座位、四座位名字与 `is_bot` | 已在别的房间 → `BAD_REQUEST`；房间不存在、已开局或没有空 AI 座位 → `ROOM_NOT_FOUND` |
| ③ | 就位 | 服务端 | 建桌时 `seat 1..3` 是 `AI-1/AI-2/AI-3`。开局前这些座位可被真人替换；房主断开则拆房，其他真人断开则座位恢复为 AI | 下一次 `room_joined` 或 `room_list` | 四座位始终齐备 | AI 不占网络连接 |
| ④ | 开局 | 已入座的真人发 `ready`（大厅「开始对局」） | 4 座位已满（真人 + 剩余 AI）→ 洗牌、发牌 | 向每个座位单独发 `game_start{hand,seat,dealer}` | 本家手牌、本家座位、庄家座位 | 不在房间 → `ROOM_NOT_FOUND` |
| ⑤ | 局内 | 服务端回合驱动 | 见第 4/5 章 | `draw`/`discard_event`/`action_request`/`action_event`/`state_sync` | 见第 4 章逐步表 | 见 5.6 超时表 |
| ⑥ | 局终 | 服务端判定 | 和牌立即结算；需摸牌且 `remaining==0` 判荒庄 | `game_end` | 和牌信息 / 荒庄原因 | — |
| ⑦ | 结算 | 服务端 | 计算四座位 `delta_score`（第 6 章），生成结算数据 | `game_end{reason,results[4],win}` 广播 4 家 | 四座位得失分、和牌牌型、是否自摸、和牌张、放炮者 | — |

### 2.3 循环的可达性约束

- ② 之后房间停在 ③，直到有真人发 `ready` 才进入 ④。不需要等满 4 个真人：空位保持 AI。
- ④ 之后必然到达 ⑤，⑤ 之后必然到达 ⑥ 或 ⑦（不存在无法结束的局面：牌山有限，83 次摸牌后必定荒庄）。
- ⑦ 是终态；本里程碑不允许从 ⑦ 回到**本局**的 ⑤。
- ⑦ 之后客户端可以「返回大厅」（回 ②′）或「再来一局」（直接回 ②）：两者都是**断开重连后开一个全新的房间**，因此走的是 ②′→②→④→⑤ 的新一轮，而不是把本局的 ⑤ 续下去（`UI_UX_SPEC.md` §2.2 第 3 条）。

## 3. 牌张与座位模型

### 3.1 牌编码（与 PROTOCOL.md 一致）

- 数牌：`<rank><suit>`，`rank ∈ {1..9}`，`suit ∈ {m,p,s}`；字牌：`<rank>z`，`rank ∈ {1..7}`；例：`"1m"`、`"9s"`、`"1z"`、`"5z"`。
- **字牌映射（冻结）**：`1z`=东、`2z`=南、`3z`=西、`4z`=北、`5z`=白、`6z`=发、`7z`=中。
- 共 **34** 种牌面（27 种数牌 + 7 种字牌），每种 4 张，合计 `34 × 4 = 136`。
- 无花牌编码；收到非法编码回 `error{UNKNOWN_TILE}`。
- **字牌只能构成刻子/杠，不可吃**；和牌判定对字牌与数牌一视同仁（`RULESET.md` §3）。
- 排序规则（服务端与客户端**必须一致**）：**先数牌后字牌**（`m < p < s < z`），数牌内按 rank 升序、字牌内 `1z`..`7z` 升序；同牌面副本相邻。
  例：`1m 1m 2m 5m 9m 3p 3p 4p 1s 2s 2s 7s 9s 1z 5z 6z`。

### 3.2 手牌张数不变量（实现必须遵守）

设 `concealed` = 未副露手牌张数，`melds` = 副露组数，`kans` = 明杠数：

| 状态 | 不变量 |
| --- | --- |
| 等待态（未轮到自己摸牌 / 已打牌完毕） | `concealed + 3×melds = 13` |
| 行动态（摸牌后 / 副露后待打牌） | `concealed + 3×melds = 14` |

说明：**每个杠在账面上按 3 张计入 `melds`**，杠的第 4 张是「额外张」，因此实际持有张数
`physical = concealed + 3×melds + kans = (13 或 14) + kans`。

- 和牌判定的**逻辑张数恒为 14**（杠按 3 张计入面子），和牌时的物理张数 = `14 + kans`。
  例：一次明杠后，等待态为 `concealed=10, melds=1(杠), kans=1`，账面 `10+3=13`，实际持有 14 张。
- 杠后补牌仍然从**同一牌山**摸取（本里程碑无王牌/岭上牌概念）。
- 七对子要求 `melds = 0` 且 `kans = 0`（门前清）。

### 3.3 开局发牌（确定性，便于同 seed 复现）

1. 以 `--seed` 初始化 `std::mt19937`，用 Fisher–Yates 洗 **136** 张牌得到牌山序列（`RULESET.md` 冻结算法）。
2. 顺序发牌：seat 0 取 13 张 → seat 1 取 13 张 → seat 2 取 13 张 → seat 3 取 13 张；
3. 庄家（`dealer = seat 0`）再取 1 张作为第 14 张。
4. 牌山剩余 `remaining = 136 − 53 = 83`。
5. 每次摸牌（含杠补牌）使 `remaining` 减 1；需摸牌而 `remaining == 0` → 立即荒庄。

### 3.4 庄家与名次

- 庄家固定为 `seat 0`（本局建桌的真人）。
- 庄家起手 14 张，**第一打不摸牌**；其余三家起手 13 张。
- **无连庄、无庄家加成、无场次分**；一局结束后四家 `delta_score` 就是唯一结果。

### 3.5 昵称与房间号

- 昵称长度 1..16 个 UTF-8 字符，不得含 `\n`、`\r`、控制字符；允许重名（用 `player_id` 区分）。
- **账号名（v1.5）**：3..16 个字符，仅 `[A-Za-z0-9_]`，**全局唯一**（数据库唯一键裁决）；口令 6..64 个可见 ASCII 字符。账号的昵称独立于账号名，缺省取账号名，仍受上面 1..16 规则约束。
- `room_id` 格式 `r-0001`（4 位十进制，进程内从 1 递增）。
- 每个连接同时只属于 1 个房间。一个进程可以同时有多间房间；每间房仍然只打一局。开局前其他真人可以加入，开局后不能。

## 4. 牌桌流程时序

### 4.1 状态机

```
        ┌───────────────── DEALING（发牌，瞬时） ─────────────────┐
        │                                                        │
        ▼                                                        │
  TURN_START ──(庄家第一打 / 副露后待打牌，不摸牌)──────────┐     │
        │                                                  │     │
        │ (普通回合)                                        ▼     │
        ▼                                            DISCARD_WINDOW
  TURN_DRAW ── remaining==0 ──► GAME_END(draw_exhausted)   │      │
        │                                                  │      │
        ▼                                                  ▼      │
  SELF_WINDOW（= 打牌窗口，含自摸选项）── discard/超时 ──► DISCARDED
                                                             │
                                                             ▼
                                              CLAIM_WINDOW（他家动作窗口）
                                                 │              │
                    无人鸣牌 / 全部 pass ────────┘              │
                                                 │              │
                          有座位鸣牌 ──► MELD_APPLIED ───────────┘（鸣牌者成为 current_seat）
                                                 │
                          有座位和牌 ──► GAME_END(win_ron / win_tsumo)
                          自摸 ─────────► GAME_END(win_tsumo)
```

### 4.2 逐步时序表（每步：触发方 / 服务端动作 / 可见信息 / 超时行为）

> 记号：`S` = 当前行动座位；`T` = 被打出的牌；座位表达式均为 mod 4。

| 步 | 名称 | 触发方 | 服务端动作（权威） | 下发消息 / 可见信息 | 超时行为 |
| --- | --- | --- | --- | --- | --- |
| 1 | 发牌 | 服务端（`ready` 后） | 洗牌、发牌、置 `current_seat = dealer = 0`、`seq = 1`、`window = DISCARD_WINDOW(seat 0)` | 对每个座位单独发 `game_start{hand,seat,dealer}`；本家手牌可见，他家手牌不可见 | 无（瞬时） |
| 2 | 庄家第一打窗口 | 服务端开窗 → 座位 0 决策 | 校验座位 0 手牌 14 张；若 14 张已成和牌型，options 含 `win`（允许「天和」） | 座位 0 收 `action_request{seq,deadline_ms,window:"discard",options}`；他家无消息 | 15000 ms 未 `discard` → 打出排序后最后一张（最大牌），见 5.6 |
| 3 | 摸牌 | 服务端（回合开始） | `remaining--`；从牌山取 1 张加入 `S` 手牌；广播 `state_sync`；`seq++` 并开 `SELF_WINDOW` | `draw{tile,seat,seq}` **仅发给 `S` 本人**；其余三家只收 `state_sync`（含 `remaining` 与各家 `hand_count`） | 无（瞬时） |
| 4 | 自摸判定 | 服务端 | `S` 手牌（含刚摸的牌）若成和牌型 → options 含 `win`；否则 options 不含 `win` | 同上（`action_request` 随步 5 一起下发） | — |
| 5 | 打牌窗口 | 服务端 → `S` | 置 `window = SELF_WINDOW(seq)`，`deadline_ms = now + 15000` | `S` 收 `action_request{seq,deadline_ms,window:"discard",options}`；`options` 是**除打牌之外**的可选动作（`["win"]` 或 `[]`） | 15000 ms → 自动 pass 自摸机会并打出**刚摸到的那张牌**（同牌面副本不可区分，等价） |
| 6 | 打牌 | `S` 发 `discard{tile,seq}` | 校验：`seq` 匹配、`S == current_seat`、`tile` 在本家手牌、窗口类型为 `discard`；移除 1 张该牌加入 `S` 的牌河；关闭窗口；`seq++` | `discard_event{seat,tile}` **广播 4 家**（牌河为公开信息）；不再额外发 `state_sync` | — |
| 7 | 鸣牌/和牌计算 | 服务端 | 对每个 `s ≠ S` 计算可选项（表 5.1）；若有任一 `s` 存在非 `pass` 选项 → 开 `CLAIM_WINDOW(seq)` | 仅向**有非 pass 选项**的座位发 `action_request{seq,deadline_ms,window:"claim",options}`；无选项的座位**不发消息** | 无选项 → 窗口立即关闭，直接进入步 3（下家摸牌），不等待 15000 ms |
| 8 | 动作窗口 | 服务端 → 窗内各座位 | 收集 `action{seq,action,tiles}` 或超时；`seq` 不匹配一律丢弃（5.6） | 窗内座位各自收 `action_request`；他家无消息 | 每个窗内座位独立 15000 ms；超时记 `pass` |
| 9 | 窗口结算 | 服务端（收齐所有窗内座位答复或全部超时后） | 按优先级 5.5 选出一个动作执行 | 结果通过 `action_event{seat,action,tiles,from_seat,seq}` 广播 4 家（语义见 §11.2.1-B） | 全部超时 = 全部 `pass` → 步 3（`S+1` 摸牌） |
| 10 | 副露生效 | 服务端（步 9 结果为碰/吃/杠） | 被鸣牌从 `S` 牌河移除（`S` = 打出该牌的人）；鸣牌者手牌扣料；新增副露；`current_seat = 鸣牌者`；碰/吃 → 开 `DISCARD_WINDOW`；杠 → 补摸 1 张（`remaining--`）后开 `DISCARD_WINDOW` | `action_event{seat,action,tiles,from_seat,seq}` 广播（`seat` = 鸣牌者；**客户端据 `from_seat` 从该座位的牌河移除其最后一张**）；`state_sync` 并行广播 4 家（含各家副露与牌河） | 杠补牌时 `remaining == 0` → 荒庄；鸣牌者 15000 ms 未打牌 → 自动打出手牌排序后最后一张（无摸牌记录） |
| 11 | 和牌 | 服务端 | 荣和：在 `CLAIM_WINDOW` 结算时按 5.5 选出和牌者；自摸：在 `SELF_WINDOW` 收到 `action{win}` | `action_event{seat,"win",[和牌张],from_seat}` 广播（荣和 `from_seat` = 放炮者；自摸 `from_seat` = `null`）；随后 `game_end` 广播 | 窗内和牌座位 15000 ms 未回 → 记 `pass`（放弃和牌） |
| 12 | 荒庄 | 服务端 | 需摸牌而 `remaining == 0` 时立即结束 | `game_end{reason:"draw_exhausted",results:[4 个 delta_score=0],win:null}` 广播 4 家 | — |
| 13 | 结算 | 服务端 | 计算 `delta_score`（第 6 章） | `game_end` 广播 4 家 | — |

### 4.3 一轮完整交互示例（含一次碰）


## 5. 操作窗口（最关键的章节）

### 5.1 何时弹出动作请求

**窗口类型只有两种**，且**同一时刻全房间最多存在一个未决窗口**（由 `room.seq` 唯一标识）：

| 窗口类型 | `window` 字段 | 开窗时机 | 收件人 | `options` 内容 |
| --- | --- | --- | --- | --- |
| 打牌窗口 | `"discard"` | 摸牌之后；庄家第一打；副露（碰/吃/杠）之后待打牌 | **仅当前行动座位 `S`** | 除「打牌」之外的可选动作：可自摸时含 `win`，否则为空数组 `[]` |
| 鸣牌窗口 | `"claim"` | 某座位打出牌 `T`，且至少有一个他家座位存在非 `pass` 可选项 | **仅存在非 `pass` 选项的座位**（可能是 1..3 个） | 至少含 `pass`，另含其可选动作 |

> 「打牌」本身**不进入 `options`**：打牌由 `discard{tile,seq}` 消息表达；`options` 只承载「是否和牌」「是否鸣牌」这类附加决策。
> `window:"discard"` 时客户端必须始终渲染倒计时与手牌点选；`options` 里的按钮叠加显示。

### 5.2 `action_request` 的精确形状（PROTOCOL.md 必须按此冻结）

```json
{
  "type": "action_request",
  "seq": 42,
  "deadline_ms": 1791174514000,
  "window": "claim",
  "options": [
    {"action": "win",   "tiles": []},
    {"action": "kong",  "tiles": ["5p"]},
    {"action": "pong",  "tiles": ["5p"]},
    {"action": "chow",  "tiles": ["3p", "4p"]},
    {"action": "pass",  "tiles": []}
  ]
}
```

- `deadline_ms`：服务端系统时钟的 epoch 毫秒（UTC），客户端计算 `remaining = deadline_ms − now`；
  客户端另需以「本地收到本帧的时刻 + 15000 ms」作为兜底，防止时钟偏差。
- `seq`：本次窗口的序号；客户端必须在 `discard` / `action` 中原样回带。
- `tiles` 语义：
  - `win`：`[]`（和牌张由服务端从上下文确定：荣和 = 被打出的 `T`；自摸 = 刚摸到的牌）；
  - `kong` / `pong`：`[T]`（被鸣的那张牌）；
  - `chow`：`[a, b]`（**手中的两张**，被鸣牌 `T` 由窗口上下文确定；服务端校验 `{a,b,T}` 构成顺子）；
  - `pass`：`[]`。
- 同一张牌同时可碰可胡时：`options` **同时**列出 `win` 与 `pong` 两条（顺序固定 `win → kong → pong → chow → pass`，客户端按此顺序渲染按钮）。
  玩家只能回一个动作；服务端在窗口结算时按 5.5 裁决。

### 5.3 可选项计算（权威算法，t2/t4 必须一致实现）

对打出牌 `T` 的座位 `S`，对每个 `s ≠ S`：

| 选项 | 出现条件 | 备注 |
| --- | --- | --- |
| `win` | `can_win(hand_s + melds_s + [T])` 为真 | 有副露也可和；本里程碑无役种限制，任何完成形都可和 |
| `kong` | `count(T, hand_s) == 3` **且** `remaining ≥ 1` | 3 张时同时提供 `pong`；`remaining == 0` 时**不提供** `kong`（无牌可补） |
| `pong` | `count(T, hand_s) ≥ 2` | 3 张时与 `kong` 并存 |
| `chow` | `s == (S+1)%4` **且 `T` 为数牌** **且** 手牌中存在 `{a,b}` 使 `{T,a,b}` 构成顺子 | 顺子仅同花色 rank 连续；可能存在 1..3 种组合，每种组合是一条独立的 `chow` 选项；**`T` 为字牌时恒无 `chow` 选项**（字牌不可吃） |
| `pass` | 永远存在 | 仅当存在非 `pass` 选项时才会开窗；窗内所有座位都收到 `pass` |

吃（chow）组合枚举（`T` 的 rank 为 `r`，花色 `x`）：候选 `{a,b} ∈ {{r-2,r-1}, {r-1,r+1}, {r+1,r+2}}`（rank 必须落在 1..9），且 `a`、`b` 两张都必须在手牌中。
例：`T = 3p` 时可能组合为 `{1p,2p}`、`{2p,4p}`、`{4p,5p}`。

**当前行动座位 `S` 自己的打牌窗口**：

| 情况 | `options` |
| --- | --- |
| 摸牌后手牌（含刚摸的牌）成和牌型 | `[{"action":"win","tiles":[]}]` |
| 庄家第一打时 14 张已成和牌型（天和） | `[{"action":"win","tiles":[]}]` |
| 其他 | `[]`（仅能打牌） |

> 暗杠不在本里程碑范围内，因此自己的打牌窗口**不会**出现 `kong` 选项。

### 5.4 窗口时长与配置

| 项 | 取值 |
| --- | --- |
| 默认动作窗口时长 | **15000 ms** |
| 配置方式 | 服务端启动参数 `--action-timeout-ms`（默认 15000） |
| 合法区间 | `[1000, 60000]`；越界或非数字 → 启动时打印错误并退出（退出码非 0，fail fast） |
| AI 动作延迟 | **900 ms**（默认） |
| 配置方式 | 服务端启动参数 `--ai-delay-ms`（默认 900；`0` = 不延迟，立即回包） |
| 合法区间 | `[0, 5000]`；越界或非数字 → 启动时打印错误并退出（退出码非 0，fail fast） |
| AI 座位是否会「立即回包」 | **否（v1.4 起）**：AI 座位的**主动决策**（自己的打牌、以及鸣牌/和牌选择）在窗口开启后延迟 `ai_delay_ms` 再执行，让真人看得清对手动作与牌河变化。延迟期间**人类玩家的任何合法回复优先立即生效**，不受延迟影响 |
| 计时器/断线托管是否也延迟 | **否**：`OnWindowTimeout` 的默认动作与断线托管座位的动作**仍立即执行**——它们本身就代表「已经等过了」（超时已等满 15 s、断线无人在等），再延迟只会拖慢收尾。这是与上一条并列的两条独立路径，实现时不得合并 |
| 窗口是否在「仅 AI 座位有选项」时等待 | **否，但会延迟**：若窗内所有收件人都是 AI（真人无选项），窗口在 AI 延迟后结算，不消耗 15 秒 |
| 窗口是否在「自家有选项」时等待 | **是**：真人没回包就等到 `deadline_ms` |
| 时钟来源 | 服务端单调时钟计算超时（`timer` / `poll` 超时），`deadline_ms` 用 epoch 毫秒下发给客户端 |

### 5.5 优先级裁决（窗口结算）

当窗口内多个座位（或同一座位的多个选项）都给出了动作时，按以下顺序选出唯一一个执行：

1. **胡 > 杠 > 碰 > 吃 > 过**。
2. 同一层级内：按**距离打出者 `S` 的逆时针顺序**（即 `S+1`、`S+2`、`S+3`）最近者优先（头跳）。
   - 例：`S+3` 和 `S+1` 都能荣和 → `S+1` 和牌。
   - 例：两个座位都能碰同样的牌（各持 2 张副本）→ `S+1` 若可碰则 `S+1` 碰，否则 `S+2`。
3. 同一座位只执行它回复的那**一个**动作（客户端不能同时提交两个动作）。
4. 被裁决掉的鸣牌意图**不产生任何副作用**，对应座位不损失手牌、不进入副露、不获得牌权。

### 5.6 超时与「seq 作废」方案（与冻结决断自洽）

#### 5.6.1 机制

1. `room.seq` 初始为 1，**每个窗口过渡恰好自增一次**（进入一个新窗口时自增；窗口因动作/超时结束而**关闭本身不自增**，其自增由紧随其后的新窗口过渡承担）；`seq` 单调递增，永不回退。
   > **裁决（captain，t4 提出）**：原文「每次窗口产生或窗口结束都自增」与本文 §4.3 示例（碰后 `state_sync` 与 `DISCARD_WINDOW` 同为 `seq=3`）、§4.2 步 10/11、以及 `PROTOCOL.md` §9.4（`draw{seq:9}` 与 `action_request{seq:9}` 同值）三处示例均不自洽，唯一例外是 `PROTOCOL.md` §9.2 的 `action_request{seq:4}`。故统一为「每个窗口过渡自增一次」，并把 §9.2 的该值改为 3。原因：`seq` 只需让客户端识别「窗口是否已推进」，同窗口内的帧共用同一 `seq` 是自洽且更易校验的；客户端按单调比较处理，两种编号在客户端侧行为等价。
2. 开窗时服务端记录 `window_seq = room.seq`，并派发一个延时的「超时消息」，消息中携带 `window_seq`。
3. 超时消息到达 RoomActor 时：
   - `window_seq != room.seq`（或该窗口已关闭/已被动作结束）→ **直接丢弃**，不改变任何状态（这就是「seq 作废」）；
   - `window_seq == room.seq` 且窗口仍开启 → 执行下表 5.6.2 的「代为执行」。
4. 收到的 `discard{seq}` / `action{seq}` 按下面的判定表处理（`room.seq` 即当前仍在开启的那个窗口）：

| 输入情形 | 处理 |
| --- | --- |
| `seq != room.seq`（窗口已结束 / 已被动作推进） | **静默丢弃**，不回 `error`，状态零变更（这就是 seq 作废本体） |
| `seq == room.seq` 但该座位**不是**本窗口收件人（claim 窗口期间第三方发 `action`；或 `seq` 对但轮不到他发 `discard`） | 回 `error{code:"NO_PENDING_ACTION"}`（`action`）/ `error{code:"NOT_YOUR_TURN"}`（`discard`），状态零变更 |
| `seq == room.seq` 且座位在窗口内，但动作不在其 `options` 中（如未提供 `win` 却回 `win`、`tiles` 不满足条件） | 回 `error{code:"ILLEGAL_ACTION"}`，状态零变更 |
| `seq == room.seq` 且座位在窗口内，动作合法 | 接受，进入 5.5 的窗口结算 |

理由：**迟到**（`seq` 过期）的合法回复是「seq 作废」方案的正常产物，必须静默丢弃，不能被当成错误；
而「`seq` 正确但越权 / 动作不合法」是真正的错误，必须回 `error`（也保证 e2e 在客户端守规矩时不会收到任何 `error` 帧）。
5. 不使用任何取消机制：不撤销 mailbox 消息、不中断 actor 执行。

#### 5.6.2 超时后系统代为执行什么（按窗口类型）

| 窗口 | 座位 | 超时行为（确定性，无随机） |
| --- | --- | --- |
| `discard` | 当前行动座位（有摸牌记录） | 放弃自摸机会（等价 `pass`），**打出刚摸到的那张牌**；若该牌面有多个副本，移除同牌面 1 张即可（副本不可区分） |
| `discard` | 庄家第一打（无摸牌记录） | 打出**手牌排序后的最后一张**（即最大牌：先比 rank，再比花色 `m < p < s`） |
| `discard` | 副露后待打牌（碰/吃，无摸牌记录） | 同上：打出排序后的最后一张 |
| `discard` | 明杠补牌后待打牌（**有**补牌记录） | 打出**补摸到的那张牌** |
| `claim` | 窗内某座位 | 记 `pass`（不鸣牌、不和牌） |
| `claim` | 窗内全部座位超时 | 全部 `pass` → 当前行动座位移交 `S+1`，进入其摸牌流程 |
| 任意窗口 | 断线托管座位 | 立即执行与「超时」完全相同的默认动作，**不等待 15 秒**（见 8.3） |

> 「打出刚摸到的牌」是超时代打的固定策略，同时也是 t6 端到端脚本中真人客户端的默认策略，
> 因此可复现性最强的路径是：**e2e 真人脚本每次收到打牌窗口即立刻 `discard` 刚摸到的牌**。

#### 5.6.3 超时方案的自洽性检查（评审关注点）

| 检查项 | 结论 |
| --- | --- |
| 超时消息能否「打断」正在执行的 actor | 不能（不可抢占），因此**只能**用 seq 作废 |
| 玩家在超时后 100 ms 才回包 | 其 `seq` 已过期 → 静默丢弃；此时服务端已经代打了，牌局状态自洽 |
| 玩家在窗口内回包但被同窗优先级裁决掉 | 不产生副作用；`action_event` 广播的是真实执行结果 |
| 同一座位重复回包 | 第一次生效后 `seq++`，第二次 seq 不匹配 → 丢弃 |
| 窗口结束后立即到来的「旧超时消息」 | `window_seq != room.seq` → 丢弃，不会重复代打 |
| 服务器重启 | 本里程碑不做持久化恢复，重启即丢弃房间（不在范围内） |

## 6. 算分与结算表现

### 6.1 算分公式（冻结）

- **底分** `base = 1`（固定，不提供配置项）。
- 倍率（可叠加，**乘算**）：
  - 七对子 `seven_pairs = ×4`
  - 清一色 `pure_one_suit = ×4`
  - 自摸 `tsumo = ×2`
- 定义 `M = base × 4^[七对子] × 4^[清一色]`，因此 `M ∈ {1, 4, 16}`。
- **荣和（点炮）**：放炮者付 `M`，和牌者得 `M`，其余两家 `0`。
- **自摸**：其余三家**每家**付 `M × 2`，和牌者得 `3 × M × 2 = 6M`。
- **荒庄**：四家全部 `0`。
- 任何情形下 `Σ delta_score = 0`（整数运算，无舍入）。

### 6.2 和牌牌型判定规则（与 RULESET.md 一致）

| 牌型 | 判定 |
| --- | --- |
| 标准型 | 逻辑 14 张可拆成 4 组面子（刻子/顺子，含已副露的面子与杠）+ 1 对将 |
| 七对子 | `melds == 0`、`kans == 0`，14 张恰好是 **7 个不同牌面**各 2 张（4 张同牌面**不能**算作两对） |
| 清一色 | 和牌全部 14 张（含副露与和牌张）花色相同（`m` / `p` / `s` 之一） |
| 平和（普通和牌） | 非七对子、非清一色，也照常和牌，`M = 1`（**本里程碑无役种限制**） |

> 说明：本里程碑**没有**「必须满足某个役才能和牌」的限制；任何完成形都可和。
> 这是与简化规则的刻意取舍，t2 的算分实现必须按此执行。

### 6.3 算分示例表（可作为 t2 的用例来源）

| 七对子荣和 | 4 | −4 | +4 | 0 | |

| 七对子自摸 | 4 | — | +24 | 各 −8 | |
| 清一色自摸 | 4 | — | +24 | 各 −8 | |

## 7. AI 机器人行为（3 个座位，可直接实现）

### 7.1 总则

| 项 | 取值 |
| --- | --- |
| AI 座位 | `seat = 1, 2, 3`；`is_bot = true`；昵称 `AI-1` / `AI-2` / `AI-3` |
| AI 难度等级 | **L1（入门级）**，本里程碑唯一且固定的等级；**不提供难度配置项**（不新增启动参数） |
| 决策时延 | **0 ms**（同步完成，不 sleeping，不 `co_await` 其他 actor） |
| 随机性 | **无**：全部决策为确定性函数；平局用固定规则打破（见 7.4） |
| 决策入口 | 只有两个：`decide_self_turn()`（打牌窗口）与 `decide_claim()`（鸣牌窗口） |
| 决策约束 | 必须在 RoomActor 单次消息处理内完成；决策后立即以「座位回包」形式推进状态，绝不等待 15 秒 |

### 7.2 `decide_claim(options)` —— 鸣牌窗口

按以下顺序取**第一个满足**的分支（等价伪码）：

```
if "win" in options:                      # 能胡则胡，无条件
    return action("win")
if "kong" in options:                     # 能杠则杠
    return action("kong", tiles=[T])
if "pong" in options:                     # 能碰则碰
    return action("pong", tiles=[T])
if "chow" in options:                     # 吃：受限条件，避免过快废掉手牌
    if suit_count(suit(T)) >= 6:          # 吃之前手牌中该花色的张数（含将要用的 a、b，不含 T）
        pick the chow option minimizing (rel(a) + rel(b))
        # rel(x) = 手牌中同花色、与 x 的 rank 差 ≤ 2 的牌张数（不含 x 自身）
        # 并列时取 (a,b) 编码字典序最小者
        return action("chow", tiles=[a, b])
    else:
        return action("pass")
return action("pass")
```

- `suit_count(suit(T))` 定义为：**吃之前手牌中该花色的张数**（含将要用的 `a`、`b`，不含被鸣的 `T`）。
- 阈值 **6** 是本里程碑冻结值，不许改为其他数值。
- 若 `options` 中同时有 `pong` 与 `kong`（手中 3 张），选 `kong`（顺序：`win > kong > pong`）。
- 只要 `win` 出现就一定和牌，**不放弃和牌**（包括被裁决掉的风险——服务端会按 5.5 处理）。

### 7.3 `decide_self_turn(hand, drawn_tile, can_tsumo)` —— 打牌窗口

```
if can_tsumo:                                        # 能自摸则自摸
    return action("win")
return discard(choose_discard(hand, drawn_tile))
```

`choose_discard(hand, drawn_tile)`（确定性，含具体数值权重）：

```
对 hand 中每个不同牌面 t：
    n       = 手中 t 的副本数 (1..4)
    adj1    = 同花色且 rank 与 t 相差 1 的牌张数
    adj2    = 同花色且 rank 与 t 相差 2 的牌张数
    suit_cnt= 手中 t 所属花色的总张数
    suit_bonus = 1 if suit_cnt >= 9 else 0           # 清一色倾向（阈值 9 为冻结值）
    usefulness(t) = 3*(n-1) + 2*adj1 + 1*adj2 + suit_bonus
cost(t) = -usefulness(t)
选择 cost 最小的牌面 t*；并列时：
  1) 若 drawn_tile 在并列集合中 → 打 drawn_tile（拟人化：优先弃摸牌）
  2) 否则取编码字典序最小者（rank 升序优先，同 rank 时 m < p < s）
从手牌移除该牌面 1 张
```

### 7.4 确定性平局规则

- 每个决策函数都必须返回**唯一**结果：任何集合取值都按「先按 (rank, 花色序) 排序，再取第一个」打破平局。
- AI 不使用随机数；同一 `--seed`（决定牌山） + 相同对手行为 ⇒ 完全相同的对局过程。
- 这一点是 t6 端到端脚本可复现的前提。

### 7.5 AI 决策示例（用于 t2/t4 单测对齐）

| 场景 | 手牌（排序后）+ 摸牌 | 决策 | 依据 |
| --- | --- | --- | --- |
| 孤立摸牌 | `1m 1m 2m 3m 4m 5m 6p 6p 7p 8p 9s 9s 9s` + 摸 `1s` | 打 `1s` | `usefulness(1s)=0`（无 2s/3s 邻接）为唯一最小值（其余牌面 ≥3，如 `usefulness(9s)=3*(3-1)+2*0+1*0=6`），且它正是刚摸到的牌 |
| 边张孤张 | `1m 2m 4m 5m 6m 1p 3p 5p 7p 9p 2s 5s 8s` + 摸 `9m` | 打 `9m` | `usefulness(9m)=0`；`2s/5s/8s` 同为 0（均为孤张）→ 并列，按 7.3 规则 1「刚摸到的牌优先」打 `9m` |
| 能碰即碰 | 手中有 `7s 7s`，他家打出 `7s` | 碰 | 7.2 顺序（无更高级选项） |
| 吃受限 | 手牌含 `1p 2p 4p 5p`（筒子共 4 张，其余为万/条），上家打出 `3p` | 过 | 存在吃法 `{1p,2p}` 与 `{4p,5p}`，但 `suit_count(p) = 4 < 6`，按 7.2 走 `pass` |

## 8. 反作弊与异常

### 8.1 打协议风暴（frame flooding / 超大帧 / 高频心跳）

| 情形 | 阈值（冻结值） | 期望系统行为 |
| --- | --- | --- |
| 单帧超过 64 KB | > 65536 字节 | **立即断开该连接**（先尝试回一次 `error{code:"FRAME_TOO_LARGE"}`，失败则直接 `close`） |
| 入站帧速率超限 | 滑动 1 秒窗口内 > **100** 帧（`ping` 也计入） | 丢弃超出的帧；对同一次限速事件**最多回 1 帧** `error{code:"RATE_LIMITED"}`（避免错误放大）；之后继续按限速丢弃 |
| 持续风暴 | 1 秒内 > **500** 帧，或连续 **3 秒**每秒都触发限速 | **立即断开该连接** |
| 坏帧（非法 JSON / UTF-8 非法 / 未知 `type` / 缺 `type`） | 累计 **10** 次 | 回 `error{code:"BAD_REQUEST"}` 并保持连接；第 10 次后断开连接 |
| 超长无 `\n` 的流 | 缓冲区累积 > 64 KB 仍无换行 | 立即断开该连接 |
| 心跳 | 客户端每 **5 秒** 发 `ping`（服务端回 `pong`）；服务端 **20 秒** 未收到该连接任何帧 | 大厅中：断开连接并释放座位；对局中：进入**托管**（8.3），不立即断开 |

其他要求：
- 一个连接的异常**绝不**影响其他连接、其他座位或房间状态；断开的连接必须回收 socket 与其玩家映射。
- 服务端对入站帧的解析必须在**定长缓冲**内完成，不得做无界内存增长。
- 服务端广播必须并行发出（0.3 第 4 条），避免被单连接慢读拖垮整局。

### 8.2 非本座位 / 越权操作

服务端只承认 RoomActor 的权威状态，**不信任**客户端上报的任何状态（手牌、座位、`room_id`、窗口归属）。
仅当校验全部通过才改变房间状态；否则状态**零变更**、只向该连接回 `error`、绝不广播、绝不崩溃。

| 非法输入 | 错误码 | 期望行为 |
| --- | --- | --- |
| 未 `login` 就发其他消息 | `NOT_LOGGED_IN` | 回 error，连接保持 |
| `room_id` 不存在 / 已关闭 | `ROOM_NOT_FOUND` | 回 error，连接保持 |
| `discard` 时 `current_seat != 座位` 且该座位无未决打牌窗口 | `NOT_YOUR_TURN` | 回 error，状态不变 |
| `discard` 的牌不在本家手牌中 | `UNKNOWN_TILE` | 回 error，状态不变 |
| `discard` 的牌码不合法（非 `<1-9><mps>`） | `UNKNOWN_TILE` | 回 error，状态不变 |
| `action` 时该座位不在当前窗口内 / 无未决窗口 | `NO_PENDING_ACTION` | 回 error，状态不变 |
| `action` 与可选项不符（无对子却碰；非下家吃；`{a,b,T}` 不成顺子；`remaining==0` 杠；手中 3 张却报碰但条件不满足） | `ILLEGAL_ACTION` | 回 error，状态不变 |
| `action` 声称和牌但实际不成立（伪造 `win`） | `ILLEGAL_ACTION` | 回 error；**服务端必须用规则库重算**，永不采信客户端结论 |
| `discard` / `action` 的 `seq` 与当前窗口不符 | ——（不报错） | **静默丢弃**（5.6.1 第 4 条），状态不变 |
| 同一连接累计非法操作 | ≥ **10** 次 | 断开该连接（对局中则转为托管，见 8.3） |

额外硬性要求：
- 客户端**不可能**看到他家手牌：`game_start.hand` / `state_sync.hand` 只包含收件人自己的手牌，服务端按座位过滤后逐座位单独下发。
- 服务端不接受客户端对「他家手牌/牌山内容」的任何查询；`sync` 只返回调用者视角的 `state_sync`。
- 和牌、副露、算分全部由服务端规则库重算，客户端只做展示。

### 8.3 断线

| 场景 | 期望行为 |
| --- | --- |
| 大厅中（未开局）真人断线 | 释放座位与连接；本里程碑只有 1 个真人，因此**销毁房间**并回收 3 个 AI 座位；其他连接不受影响 |
| 对局中真人断线（socket 关闭或心跳 20 秒超时） | 该座位标记 `disconnected = true` 并进入**托管**：后续任何需要其决策的时刻，**立即**执行 5.6.2 的「超时默认动作」（不等 15 秒）；若是鸣牌窗口则直接 `pass`，若是打牌窗口则按其策略打牌（本里程碑托管采用与 AI 座位相同的 7.2/7.3 策略，保证托管方也在争取和牌）。房间与牌局继续推进，绝不卡死 |
| 托管座位参与结算 | 照常计算 `delta_score`，出现在 `game_end.results` 中；结算界面在昵称后标注「（断线托管）」 |
| 托管后重连 | **不在本里程碑范围**：本里程碑不做断线重连与状态恢复。托管玩家若重新连接，只能重新 `login` 并 `create_room` 开启新的一局 |
| 结算后仍未断开/重连 | 服务端在 `game_end` 后 30 秒回收该房间与所有相关资源 |
| AI 座位「断线」 | 不存在（AI 无网络连接）；AI 决策异常时由服务端兜底执行 5.6.2 的默认动作并记录一条服务端日志 |

### 10.5 一局「从头跑到结算」的判定条件（汇总口径）

**当且仅当** GD-A1..GD-A5、GD-B1..GD-B7、GD-C1..GD-C4 全部为真，判定「单房间一局已完整跑通：登录 → 开局 → 局内逻辑 → 结算」。
判定口径完全落在协议事件与字段上，不需要人工目测，不需要客户端截图。

### 10.6 端到端脚本的实现要点（避免卡局的三个硬性细节）

1. **开局握手顺序必须是** `login` → 等 `login_ok` → `create_room` → 等 `room_joined` → `ready` → 等 `game_start`。
   少发 `create_room` 或 `ready` 就永远等不到 `game_start`（服务端按 2.2 处理，不会报错提示）。
2. **每次 `discard` / `action` 必须回带最近一次收到的 `action_request.seq`**（打牌窗口与鸣牌窗口都是如此）。
   `seq` 不匹配的帧会被服务端**静默丢弃**（5.6.1），脚本将表现为卡局，而不是收到 `error`。
3. 脚本自身的打牌策略：收到 `window == "discard"` 且 `options` 含 `win` 时回 `action{win}`；
   否则回 `discard{刚摸到的牌}`；庄家第一打（本家无摸牌记录）则打出手牌排序后的最后一张（与 5.6.2 的代打口径一致）。

#### 11.2.1 载荷形状与 `action_event` 语义（冻结，PROTOCOL.md 必须逐字采用）

**A. `melds[]` 元素形状**（本家 `state_sync.melds` 与他家 `state_sync.seats[].melds[]` **同形状**）：

```json
{"type": "pong", "tiles": ["5p", "5p", "5p"]}
{"type": "chow", "tiles": ["3p", "4p", "5p"]}
{"type": "kong", "tiles": ["9s", "9s", "9s", "9s"]}
```

| 项 | 冻结值 |
| --- | --- |
| `type` | `pong` / `chow` / `kong` 三者之一（本里程碑无暗杠、无加杠） |
| `tiles` | 该组副露的**全部物理牌面**，按 3.1 排序。`pong` / `chow` 恒 3 张；`kong` 恒 **4 张**（3 张来自手牌 + 1 张额外张，见 3.2） |
| 组顺序 | `melds[]` 按成组时间先后排列（= 副露发生顺序） |
| 与 `results[].hand` 的关系 | `game_end.results[i].hand` 是**扁平**数组（门前手牌 + 副露牌面、按 3.1 排序、长度 = 14 + 杠数），**不替代** `melds[]`。两者并存：客户端用 `melds[]` 还原副露分组，在扁平数组上扣除这些牌后得到门前手牌（UI_UX_SPEC §9.3） |

**B. `action_event` 语义**（`seat` = **执行该动作的座位**；`from_seat` = 被鸣 / 被荣和那张牌的**打出者座位**）：

| `action` | `seat` | `tiles[]` | `from_seat` |
| --- | --- | --- | --- |
| `pong` | 鸣牌者 | `[T]`（被鸣的那张牌） | `T` 的打出者（**必带**） |
| `chow` | 鸣牌者 | `[a, b]`（**手中的两张**，与客户端提交同语义；被鸣牌 `T` 由 `from_seat` 的牌河确定） | 被鸣牌 `T` 的打出者（**必带**） |
| `kong` | 鸣牌者 | `[T]`（被鸣的那张牌） | `T` 的打出者（**必带**） |
| `win`（荣和） | 和牌者 | `[和牌张 T]` | `T` 的打出者（**必带**） |
| `win`（自摸） | 和牌者 | `[摸到的牌]` | 不携带（等价 `null`） |

**C. 其他冻结规则**：

1. **`pass` 不产生 `action_event`**：窗口结算结果为「全部 `pass`」时，服务端不广播任何 `action_event`，直接进入下一家摸牌（4.2 步 9）。
2. **被鸣牌恒为 `from_seat` 座位最近一次打出的那张**（鸣牌窗口正是由它触发）。因此客户端据 `from_seat` 从该座位牌河移除**最后一张**即可：既不必匹配 `tiles[0]`，也不必猜测 `chow` 的被鸣牌归属。
3. `seq` = 触发该动作的窗口序号（与对应的 `action_request.seq` 相同），供客户端判断窗口是否已推进（5.6.1）。
4. `action_event` 是**即时事件**；服务端权威状态仍以随后到达的 `state_sync` 为准（11.4），两者到达顺序不作保证。

### 11.3 错误码表（PROTOCOL.md 必须逐字采用）

`INVALID_NAME`、`NOT_LOGGED_IN`、`ROOM_NOT_FOUND`、`NOT_YOUR_TURN`、`NO_PENDING_ACTION`、`ILLEGAL_ACTION`、`UNKNOWN_TILE`、`BAD_REQUEST`、`FRAME_TOO_LARGE`、`RATE_LIMITED`、`INTERNAL`，以及 v1.5 新增的 `AUTH_FAILED`（账号不存在或口令错误，计入非法操作计数）、`USERNAME_TAKEN`（账号名已占用）、`ALREADY_ONLINE`（该账号已在别处登录）——共 **14** 条。

> `STALE_SEQ` **不作为**错误码下发：`seq` 不匹配按 5.6.1 静默丢弃。

### 11.4 状态同步（`state_sync`）下发时机

| 时机 | 是否下发 |
| --- | --- |
| 摸牌后 | ✅ 并行广播 4 家 |
| 副露（碰/吃/杠）后 | ✅ 并行广播 4 家 |
| 和牌后（紧随 `game_end`） | ✅ 并行广播 4 家 |
| 打出牌后 | ❌ 已有 `discard_event` 广播，不重复下发 |
| 客户端主动 `sync` | ✅ 仅回请求者 |
| 窗口开启/结束（`seq` 变化） | ❌ 不额外下发；`seq` 由 `action_request` / `action_event` / `state_sync` 携带，`draw` / `discard_event` 亦携带 `seq`；**仅 `game_end` 不携带 `seq`**（不参与 `seq` 比较） |
