## 一、声音基调

### 1.1 一句话

> **这是一个念给你听的结果，不是一个念给你听的广告。**

播报的全部职能是**替眼睛确认「这些数字是怎么加出来的」**。它必须比牌桌上的任何音效都清楚，也必须比任何音效都快消失——玩家听完就要进入下一局。

### 1.2 三条不可违反的基调

1. **信息优先于好听**：番种名与数字必须**可懂**。任何为了「有磁性/有气势」而牺牲辅音清晰度的音色、语速、混响，一律否决。播报**不加混响、不加背景音乐、不加音效垫底**。
2. **不参与判定，只做摘要**：语音是**有损摘要**，字幕是**无损全量**。语音可以省略（省字、省句、降档），字幕一句都不能少。**任何「语音里没说的信息」必须在字幕里找得到**。
3. **听感一致 = 同一个人一口气念完**：57 条必须听起来是**同一位播音员、同一支麦克风、同一间屋子**。这意味着必须**逐句 RMS 归一化**（实测原始句间峰值差 **4.1 dB**、RMS 差更大，不归一化会像换了人）。这条是硬要求，不是优化项。

### 1.3 音色方向与选型依据

| 维度 | 决定 | 依据（实测 / 结构） |
| --- | --- | --- |
| 音色 | **`Tingting`（婷婷）** | zh_CN 里语流最自然、辅音最清晰的一条；另外 8 条新音色（Eddy/Flo/…）偏「播报腔」，长句易疲 |
| 备选 | `Shelley` / `Sandy` / `Flo` | 若用户试听后认为 Tingting 偏「客服感」，按此序换；**换音色 = 全量重生成 57 条**（同一套脚本、同一套 manifest，成本 < 1 分钟） |
| 性别 | 女声（中频 200–300 Hz 基频） | **刻意避开低频**：既有 `sfx_call_kong`（123 Hz）、`call_ankan`（82 Hz）、`draw_hand`（79 Hz）主能量在 80–300 Hz；女声与它们重叠最少 |
| 语速 | `-r 175`（= 系统默认，**显式写死**以保证可复现） | 不用默认值（未显式写出），也不用 200（会赶）。**若最终觉得太长，唯一的语速旋钮是 `-r 190`，全局省约 8%** |
| 情绪 | 中性 · 报数 · 无起伏 | 不允许「戏剧化重音」（例如把「清一色」念出惊喜感）。这是结算，不是抽奖 |

### 1.4 与既有 16 条音效的关系

- 播报**不替代**任何已有音效：`sfx_win_tsumo` / `sfx_win_ron` / `sfx_hand_end` / `sfx_draw_hand` 全部保留原触发点与原时长。
- 播报**不新增**任何非人声音效。结算页不引入「翻牌声/盖章声/金币声」——`FEEL_SPEC` §5.2 的 16 条是牌桌手感，结算页的音效职责已由和牌铃 + 收束族承担。
- 唯一的交互是 **duck（压低）**，不是静音（见 §4.2）。

## 二、声音清单：57 条原子句库

### 2.1 句库设计的三条硬规则（先看规则再看表）

**规则 A：单句 ≤ 8 字。**
实测每字约 **223–250 ms**（`say -r 175`，见 §0.2），8 字 ≈ 2.0 s。超过 8 字就必然出现「一口气念不完」的机械感，且无法与高亮对齐。

**规则 B：番数与番种**烘焙成一句**，不拆成「番种名」+「N番」两个文件。**
理由：番数是番种的**函数**（`menzen` 恒 1 番、`pure_one_suit` 恒 5 番），不是自由变量。拆开有 3 个坏处：① 多一个 90 ms 间隔，实测「门前清」+「一番」拆分 = 1327 ms 与整句烘焙**同长**，但拼接处有可听的断点；② 拼接处的共振峰不连续，听起来像两个人在念；③ 组合数虚高（14×6=84），实际只有 16 种合法组合。**整句烘焙后只需 16 个文件，且更自然。**

**规则 C：数字一律用汉字书写，不用阿拉伯数字。**
实测「六十四倍」**853 ms**、「64倍」**934 ms**（阿拉伯数字反而慢 81 ms，且读音无法在不试听的前提下确认）。**文本里出现阿拉伯数字即视为规格错误。**

**「可拼接」列的含义**：`是` = 允许与前句之间只用 **70 ms**（`G1`，同一口气）紧贴；`否` = 必须独立成句，前/后至少 **140 ms**（`G2`）或段间隔（`G3`/`G4`）。

## 三、拼接与播放规则

### 3.1 句间静音（四个常数，全部写死）

| 常数 | 值(ms) | 用在哪 | 为什么是这个数 |
| --- | --- | --- | --- |
| `G1` 同气 | **70** | 「可拼接 = 是」的句对（`合计六番` → `已封顶`） | 70 ms 约等于一个字的尾音衰减，听起来是「一口气念完」，语义不断 |
| `G2` 段内 | **140** | 同一段内两个条目之间（两条番种、摘要句接最高番句） | 140 ms 是可辨识的换气，但不足以构成句号。**低于 100 ms 会连成一句（不可接受），高于 200 ms 会像两条独立播报** |
| `G3` 跨段 | **240** | 段与段之间 | 240 ms 形成清晰的段落感，配合高亮分区切换 |
| `G4` 结论前 | **320** | **进入 S4 前** 与 **进入 S6 前** | 这两处是「算完了」和「要付钱了」的转折点，需要一段可感知的停顿把注意力拉回来 |
| `T_VO_START` | **320** | 结算页 `onEnter` → S1 首句起播 | 见 §4.2：让 `win_tsumo` 的起音（源素材 90% 峰值在 404 ms）先被听到，再让位给人声 |

> 这些是**试听可调项**（允许范围 `G1 50–90 / G2 120–160 / G3 200–280 / G4 280–380`），但**相对关系不得反转**（`G1 < G2 < G3 < G4`）。

### 3.2 队列与打断

| 规则 | 内容 |
| --- | --- |
| `V-R1` 单句串行 | **同一时刻只允许一句 VO**。不做并发、不做叠加、不做交叉淡入 |
| `V-R2` 无插队 | 队列一旦装配即固定。玩家输入、UI 事件、`state_sync` 一律不改队列 |
| `V-R3` 不做追赶 | 若主循环卡顿导致某句起播晚了，**后续句不顺延压缩间隔**（会造成语速错乱）；直接顺延，由 §3.5 的看门狗在硬上限处收尾 |
| `V-R4` 缺句跳过 | 某句 wav 文件缺失/解码失败 ⇒ **跳过该句与它后面的间隔**，立刻念下一句。不重试、不等待、不报错弹窗（只记一条 WARN） |
| `V-R5` 唯一可终止者 | 只有 **P0 事件（`match_end`）** 可以终止播报：`Channel(3).fadeout(80)` + 清空队列。玩家的「跳过播报」若被采纳（X3-③），等价于 `fadeout(40)` + 清空队列 + 高亮 snap 到全亮 |
| `V-R6` 静音不跳字 | `M` 静音时**队列照常推进**（时间轴不变、字幕不变、高亮不变），只是不出声。不允许「静音就加速」——那会让同一个功能在两种状态下节奏不同，玩家换开关时会感觉错乱 |
| `V-R7` 幂等 | 同一局 `game_end` 只装配一次。以 `room_id + round_index` 为键，重复帧丢弃 |

### 3.3 装配算法：「先算后播」+ 三档

**不要边播边算。** 所有句子时长在加载期已知（`vo_manifest.json` 的实测值），所以可以在**起播前**求出精确总长并决定档位。

```
输入：game_end 载荷（win.yaku[] / han_breakdown / multiplier / tsumo / reason）
1  若 reason == "draw_exhausted" ⇒ 序列 = [s1_draw, G3, s6_draw_no_score, G2, s6_draw_renchan]
                                          档位固定 = Tier1（≈2.9 s）
2  否则：
   2.1 S1 = [s1_tsumo 或 s1_ron]
   2.2 S2 = yaku[] 顺序 → 逐条句子（箭刻按 han 取 _1/_2/_3）
   2.3 S3 = [tsumo? s3_tsumo_no_add] + [dealer? s3_dealer]
   2.4 S4 = [合计N番 或 无番] + [发生了截断? G1 + s4_capped]
   2.5 S5 = [s5_mult_{R}]
   2.6 S6 = [s6_ron_{R} 或 s6_tsumo_{2R}]
3  按 §3.4 的间隔规则拼成清单，求 total_ms
4  若 total_ms ≤ VO_MAX_TOTAL_MS(11000) ⇒ Tier1（完整）
5  否则 把 S2 换成 [最高番那条整句, G2, s2_sum_{n}]
        （最高番 = max han；并列取 yaku[] 序最小者）→ 重算
6  若仍 > 11000 ⇒ Tier3：S2 与 S3 全部静默（不念），只保留 S1/S4/S5/S6
7  若仍 > 11000（理论上不会：Tier3 ≤ 6.6 s）⇒ Tier4：只念 S4 + S5 + S6
8  起播
```

**三档的实测总长（按保守估计上界，实测会低 5–15%）**：

| 档位 | 组成 | 典型总长 | 何时触发 |
| --- | --- | --- | --- |
| **Tier1 完整** | S1 + S2 逐条 + S3 + S4 + S5 + S6 | **4.0 – 10.4 s** | 1–3 条番种（覆盖绝大多数手牌） |
| **Tier2 摘要** | S1 + S2(最高番 + 共N项) + S3 + S4 + S5 + S6 | **9.0 – 10.5 s** | 4 条以上番种，或 3 条 + 封顶 + 128 分 |
| **Tier3 极简** | S1 + S4 + S5 + S6 | **4.5 – 6.6 s** | Tier2 仍超限（仅理论边界） |

> 关键：**降档只影响语音，不影响字幕。** 字幕永远显示 `yaku[]` 全量。所以 Tier2 的摘要句后面，那 4–6 条番种仍然会在屏幕上**逐条高亮**（用固定节拍扫过，见 §3.7 的「静默段」）。

### 3.5 总时长上限（**用户选了暂停倒计时，所以上限是硬要求**）

| 常数 | 值 | 含义 |
| --- | --- | --- |
| `VO_MAX_TOTAL_MS` | **11 000** | **硬上限**。装配超限即降档；播报开始后到 11 000 ms 仍未结束 ⇒ **看门狗强制结束**：`fadeout(40)`、丢弃剩余句、高亮 snap 到全亮终态 |
| `VO_TARGET_MEDIAN_MS` | **6 000** | 设计目标（中位数）。实测分布：0 番 ≈4.0 s、1–2 番种 ≈6–9.5 s |
| `VO_TAIL_MS` | **400** | 播报结束后再等 400 ms 才恢复倒计时（防止「刚说完就跳下一局」的仓促感） |
| `VO_FALLBACK_MS` | **6 000** | 无语音可用时的固定时间轴总长（§3.8），段内 700 ms/条、段间 280 ms |
| 倒计时暂停时长 | `播报实际总长 + VO_TAIL_MS` | **这就是玩家多等的时间**，必须对外可解释 |

> **为什么是 11 000 而不是 8 000**：8 000 会强制把「2 番种 + 庄家」（9.5 s）也降成摘要，而这类手牌占实战的相当比例，等于大部分对局都听不到明细——那就白做了。11 000 让完整档覆盖 1–3 条番种，同时给最坏情况（封顶自摸）留出降档空间。
> **这个数唯一该动的时候**：用户试玩后说「太长了」。调整顺序是 **① 先加逃生口（X3-③）→ ② 再降 `VO_MAX_TOTAL_MS` 到 9 000 → ③ 最后才动 `-r 190`**。不要先动语速（会把所有句子一起变难听）。

### 3.6 倒计时暂停口径（交 UI 实现）

| 情形 | 倒计时行为 |
| --- | --- |
| 播报序列正在推进 | **冻结**：`remaining_ms` 保持当前值，不递减、不触发 `countdown_tick` |
| 播报序列正常结束 | 等待 `VO_TAIL_MS`(400) 后，**从冻结值继续**递减（不重置为 5 秒） |
| 看门狗强制结束 | 同上（从冻结值继续） |
| `M` 静音（字幕/高亮仍在走） | **仍然冻结**（暂停条件是「播报在推进」，与有没有声音无关） |
| 语音全部不可用（fallback 时间轴） | **仍然冻结**（视觉播报仍在进行） |
| `--no-feel` | **不暂停**（整功能关闭，必须完全等价 v2.0 旧行为） |
| `match_end` 到来（场终页） | 场终页无「下一局倒计时」，无需处理；VO 立即终止 |

### 3.7 与视觉高亮的对齐锚点（**谁是主时钟**）

**答案：主时钟是「播报序列推进器」；它的时间源分两种——有声段由语音句首驱动，静默段由固定节拍驱动。语音不是唯一时钟，但它是所有**有声句**的时钟。**

```
锚点 A（有声句）：Channel(3).play() 返回成功的**同一帧** ⇒
   · 该句对应的高亮格切到「激活」态（≤ 1 帧 / 16.7 ms 内必须切完，不得延后）
   · 该句字幕文本**已经在句首前 80 ms 显示**（先读后听；字幕早于声音 80 ms 是刻意的）
   · 段标题（S1..S6）高亮在该段首句的同一帧切换
   · 下一句起播时刻 = 本句 play() 时刻 + 本句实测时长 + 本句后接间隔（由 manifest 决定，不用 get_busy() 轮询）

锚点 B（静默段 / 静默条目）：固定节拍
   · 每条停留 = max(180, 段时长 / 条目数)
   · Tier2 的 S2：语音念摘要（≈2.25 s）期间，把 N 条番种按 2250/N ms 逐条点亮
   · Tier3 的 S2/S3：整段用 VO_FALLBACK 的 700 ms/条
   · 语音全缺：段内 700 ms/条、段间 280 ms

锚点 C（终态）：序列结束（或看门狗/跳过）⇒ 所有格子保持「已亮」到离开页面，**不熄灭、不回退**
```

**三条实现硬约束**：

1. **不得用 `get_busy()` 轮询推进**。`get_busy()` 在 22050→44100 转码后与文件时长有 10–40 ms 偏差，累积后高亮会飘。用「起播时刻 + manifest 时长」的**绝对时刻表**。
2. **看门狗**：每段最长等待 = 该段语音预估时长 + **400 ms**。超时强制推进到下一段（记 WARN）。**这是防「某句解码卡住导致整页假死」的唯一保险**，必须有。
3. **字幕先于声音 80 ms**：这是「先读后听」的阅读节奏，不是笔误。若实现成「同步」或「声音先到」，玩家会先听到不认识的词再去找字。

### 3.8 降级矩阵（**语音加载失败/缺失时如何不阻塞流程**）

| 情形 | 语音 | 字幕 | 高亮 | 时间轴 | 倒计时 |
| --- | --- | --- | --- | --- | --- |
| 正常 | ✅ | ✅ | ✅ | 语音驱动（锚点 A/B） | 冻结 |
| 个别句缺失（1–2 句） | 该句静默，**跳过其间隔** | ✅ 完整 | ✅ | 其余句仍按语音；缺句处用 180 ms 固定 | 冻结 |
| manifest 缺失 | ✅（按文件名推断） | ✅ | ✅ | 用保守公式 `60+250×字数` 代替实测时长 | 冻结 |
| 全部 VO 缺失 / 目录为空 | ❌ | ✅ 完整 | ✅ 完整 | **fallback 固定时间轴**（段内 700/条、段间 280、总 ≤6 000） | 冻结 |
| `mixer` 初始化失败（无声卡/CI） | ❌ | ✅ | ✅ | fallback | 冻结 |
| `M` 静音 | ❌（用户选择） | ✅ | ✅ | **语音时刻表**（manifest 实测时长，节奏与有声时一致） | 冻结 |
| `--no-feel` | ❌ | ❌（整功能关） | ❌ | 无 | **不冻结** |
| `match_end` 到达 | 立即 `fadeout(80)` + 清队列 | 切场终页 | snap 终态 | 终止 | — |

**核心承诺（这条决定法律风险能否不阻塞上线）**：
> **`assets/vo/` 目录为空时，本功能必须完整可用（字幕 + 六段逐条高亮 + 倒计时暂停），只是没有声音。** 零代码改动、零异常、零 WARN 刷屏（只记一条 INFO）。
> 这不是「兜底」，这是**第一版就要实现的正常路径之一**——因为 TTS 授权尚未确认（§5.7），上线时完全可能只能发字幕。

## 四、混音架构

### 4.1 VO 总线（新增第 4 组）

| 项 | 值 | 与既有的关系 |
| --- | --- | --- |
| 通道 | **`Channel(3)`** | 既有 WIN=0 / ACTION=1 / UI=2 不动 |
| 保留位 | `pygame.mixer.set_reserved(3)` → **`set_reserved(4)`** | 否则 `Sound.play()` 的自动分配可能偷走 ch3 |
| 通道总数 | `set_num_channels(16)` **不变** | 4 组 + 12 条余量，够 |
| 并发上限 | 3 → **4**（WIN1 + ACTION1 + UI1 + **VO1**） | 需改 `F-AU-20`（X2） |
| 组乘子 | **1.00** | 与 WIN 同级。VO 的清晰度靠 ducking 得到，不靠开大音量 |
| 采样率/位深/声道 | 与 `mixer` 一致（44100 / −16 / 单声道）；文件 22050，**SDL 在 `Sound()` 加载期转 44100** | 重采样发生在加载期，**不进运行时热路径** |
| 优先级 | **P0.5** | 可打断 P1/P2/P3；**不可**被 P1–P3 打断；只能被 P0（`match_end`）终止 |

### 4.2 既有 sfx 逐条处置（播报期间）

| sfx id | 通道 | 播报期间处置 | 具体数值 | 理由 |
| --- | --- | --- | --- | --- |
| `win_tsumo` / `win_ron` | WIN(0) | **DUCK −12 dB**（不是静音、不是 fadeout） | VO 起播前 **120 ms** 开始降、**300 ms** 内完成；VO 结束后 **400 ms** 线性回升到 0 dB（若已自然播完则不回升） | 和牌铃是整局情绪高点（有效电平 −14.8/−15.3 dBFS，全场最亮）。掐掉 = 毁掉「炸一下」；不压 = 人声被铃声糊住。duck −12 dB 让铃的「存在感」还在，但让出语音可懂度所需的 `300 Hz–4 kHz` |
| `match_end` | WIN(0) | **不 duck**（场终页无 VO）；若与 VO 重叠 ⇒ **VO 让位** | VO `fadeout(80)` + 清队列 | P0 高于 VO |
| `hand_end` | ACTION(1) | 按原时机播（切页 + 100 ms），**VO 起播时 `fadeout(80)`** | 80 ms（比 P0 的 30 ms 更柔） | 这是「让位」不是「抢占」。100 ms 起播 → 有 220 ms 完整窗口，足够听出「一局收束」 |
| `draw_hand` | ACTION(1) | 按原时机播（切页 + 60 ms），**VO 起播时 `fadeout(80)`** | 同上 | 荒庄时 VO 只有 2 句（≈2.9 s），`draw_hand` 有 260 ms 窗口 |
| `countdown_tick` | UI(2) | **直接禁用**（播报期间 `play()` 直接 return False） | 不播 | 倒计时已冻结，本来也不会触发；这是**双保险**（防实现漏了冻结） |
| `ui_click` | UI(2) | **不 duck**，保持原样 | 原 −30.1 dBFS | 局终页 v2.0 **没有按钮**，实际不触发。若将来加了按钮，点击必须有反馈，不能被 duck 掉 |
| `tenpai_on` / `turn_start` / `tile_draw` / `tile_discard` / `call_*` | ACTION(1) | **不适用**（结算页已离开牌桌，这些事件不再产生） | — | 无需处理 |

**Ducking 曲线（写死的实现口径）**：

```
t = -120ms 开始（相对 VO 首句起播）  ch0 音量 1.00 → 线性
t = +180ms（即 300ms 内完成）        ch0 音量 0.251（= −12 dB）
t = VO 最后一句结束                   保持 0.251
t = +400ms                            ch0 音量 0.251 → 1.00（线性）
注：音量 = GROUP_MULT × MASTER × duck_linear，逐帧 set_volume；不要用 fadeout（它会把通道停掉）
```

### 4.3 电平预算（不削波，逐项算给你）

**目标**：VO 有效电平（50 ms 窗口 RMS）≈ **−18 dBFS**，比 WIN（−15 dBFS）低 3 dB——**但因为在播报期间 WIN 被压到 −27 dBFS，人声实际领先 9 dB**，可懂度绰绰有余。

| 源 | 文件峰值 | 通道音量 | 输出峰值 | 说明 |
| --- | --- | --- | --- | --- |
| VO | **−3.5 dBFS** | `1.00 × 0.70 = 0.700` | **−6.6 dBFS** | 57 条统一限幅到 −3.5 |
| WIN（duck 后） | −3.2 dBFS | `1.00 × 0.70 × 0.251 = 0.176` | **−18.3 dBFS** | |
| **最坏相干叠加** | — | — | **≈ −4.6 dBFS** | `0.700×0.668 + 0.176×0.692 = 0.589` |

**结论：余量 4.6 dB，不削波。** 且 VO 与 WIN 是**不同通道**，`pygame.mixer` 在 32-bit 内部累加后回落 16-bit，`MASTER 0.70` 已经预留 3.1 dB 头域，双重保险。

**逐句归一化（必须做，否则像换了人）**：

| 项 | 值 | 依据 |
| --- | --- | --- |
| 整句 RMS 目标 | **−20.0 dBFS ± 0.5**（排除 < −50 dBFS 的静音帧） | 实测原始峰值 0.44–0.71（**−7.1 … −3.0 dBFS，句间差 4.1 dB**），不做 RMS 对齐，长句会明显比短句「虚」 |
| 峰值上限 | **−3.5 dBFS** | 若 RMS 归一化后峰值超限，先限幅；若限幅使 RMS 偏离目标 > 1 dB，**峰值优先**（记 WARN） |
| 首静音 | **≤ 10 ms**（阈值 −50 dBFS，保留 5 ms 前滚） | 实测 `say` 首静音 1–21 ms（多数 4–5 ms） |
| 尾静音 | **≤ 25 ms**（含末 8 ms 线性淡出） | 实测原始尾静音 22–36 ms，必须裁——否则每句多 10–15 ms 空响，7 句累计 100 ms 的「闷」。**原写「≤20 ms」与 §8.4 的「后滚 25 ms」算术冲突，已按 team-lead 2026-10-23 裁决改为 25 ms**，见 §8.3 末「规格自纠 S-1」 |
| DC 偏移 | 去均值 | 与既有 16 条同一套纪律（`AUDIO_SPEC` §6.3） |

### 4.4 人声频段避让（**诚实说明：本项目没有 EQ 能力**）

`pygame.mixer` 没有滤波/FX API，**运行时不可能做人声频段的动态 EQ 避让**。因此避让必须靠**三件非 DSP 的事**：

| 手段 | 做法 | 效果 |
| --- | --- | --- |
| ① 时间错开（最有效） | `T_VO_START = 320 ms`：让和牌铃的起音（源素材 90% 峰值在 **404 ms**，实测）先被完整听到，再起人声；S1 的 2 字句（492/564 ms）又恰好落在铃音的衰减段 | 语音首字与铃音峰值不重叠 |
| ② duck | WIN −12 dB | 直接给人声腾出 12 dB 的动态空间，比 EQ 更彻底 |
| ③ 选音色 | 女声 Tingting，基频 200–300 Hz；**刻意不选低男声** | 避开既有低频重击的主能量区：`call_ankan` 82 Hz、`draw_hand` 79 Hz、`call_kong` 123 Hz（实测谱质心）。若用 100–150 Hz 的男声，会和这三条「闷木」抢同一块频谱 |
| 已知短板 | 语音辅音清晰度带 2–6 kHz 与 `sfx_win_*` 的 1050–1170 Hz 质心、`tenpai_on` 1984 Hz 有部分重叠 | 由 ② 覆盖；**不追求完全分离**，追求「人声领先 9 dB」 |

> 如果将来引入音频中间件（FMOD/Wwise）才谈得上动态 EQ。**v1 不加中间件**（`AUDIO_SPEC` §6.4 已定），因此本节的「无 EQ」是设计前提，不是妥协。

## 五、音频规格与命名

### 5.1 命名（**唯一答案：`vo_*.wav`，不并入 `sfx_*`**）

**结论：新开 `vo_` 前缀 + 新目录 `game/client/assets/vo/`。理由四条，任一条都足以否决「并入 sfx_」：**

1. **`sfx_<id>.ogg` 是既有命名空间，且被冻结**。`FEEL_SPEC.md` §5.3 **D1** 写明「16 个 id 各交付 1 个样本，命名 `sfx_<id>.ogg`，本行是命名与路径的唯一权威」。往里加 `sfx_vo_*` 会让「16 条」这个计数失效，并制造第二个权威。
2. **准入线不兼容**。`F-AU-00c` 要求「峰值 ≤ −3 dBFS / 首尾**无静音** / 不循环」。语音需要**尾静音 ≤25 ms 且必须做 RMS 归一化**，且长度是 sfx 的 3–5 倍——把它塞进同一套准入线，会让 16 条音效的验收口径变得含混。
3. **授权必须分开登记**。既有 16 条是 **CC0 1.0（无署名义务）**；语音是 **TTS 合成，授权未确认**。混进 `CREDITS.md` §1 的 CC0 表会让人误以为语音也是 CC0（这是实质性的法律误导）。
4. **加载时机不同**。16 条在**启动期预载**（`F-AU-00d`，实测 9.3–12.4 ms）；语音 57 条**不能启动预载**（会拖首帧），必须首次进结算页才加载（§5.6）。

**文件命名格式**：

```
vo_<seg>_<key>.wav
  seg ∈ { s1, s2, s3, s4, s5, s6 }        # 六段分区，与 §0.4 一致
  key = 小写英文/数字/下划线，与本文表格的 id 后缀逐字一致
  例：vo_s2_yaku_pure_one_suit.wav / vo_s6_tsumo_128.wav
```

| 对象 | 格式 | 示例 | 备注 |
| --- | --- | --- | --- |
| 逻辑 id（代码里引用） | `VO_<SEG>_<KEY>` 大写 | `VO_S2_YAKU_PURE_ONE_SUIT` | **代码只引用逻辑 id，不直接拼文件名**，映射集中一处 |
| 交付文件 | `vo_<seg>_<key>.wav` | `vo_s2_yaku_pure_one_suit.wav` | 小写 + 下划线 |
| 清单 | `vo_manifest.json` | — | 与 wav 同目录 |
| 文本表（生成输入） | `vo_lines.tsv` | `vo_s1_tsumo<TAB>自摸` | 随仓库归档，作为「文本 → 文件」的可审查记录 |
| 目录里**不放** | 原始 `.aiff`、临时文件、`say` 的中间产物 | — | 只放 57 条成品 + manifest + tsv + CREDITS |

### 5.2 格式规格

| 参数 | 值 | 依据 |
| --- | --- | --- |
| 容器 / 编码 | **WAVE / PCM 16-bit signed（RIFF）** | 无 ffmpeg，不能转 ogg；WAV 是 `afconvert` 与 `wave` 都能直出的唯一无损选择 |
| 采样率 | **22050 Hz** | `say` 原生输出（实测 `AIFC 1ch 22050Hz 16-bit BE`）。**落 22050 的理由**：① 语音的 Nyquist 11 kHz 足够（中文辅音能量集中在 2–8 kHz）；② 盘上体积减半（vs 44100）；③ 零重采样步骤（不引入转换损失）；④ `pygame.mixer.Sound()` 加载期自动转 44100，**不进热路径** |
| 声道 | **1（单声道）** | mixer 是单声道；双声道只会浪费一倍体积 |
| 峰值 | **≤ −3.5 dBFS** | 见 §4.3 |
| 整句 RMS | **−20.0 dBFS ± 0.5** | 见 §4.3 |
| 首静音 / 尾静音 | **≤ 10 ms / ≤ 25 ms**（含末 8 ms 淡出；原「≤20 ms」已按 §8.3「规格自纠 S-1」修正） | 拼接的间隔由播放器控制，**不能靠文件自带静音凑** |
| 循环 | **不循环**（`loops=0`） | 语音永不循环 |
| 单条时长 | **≤ 2 800 ms**（最长 `vo_s6_tsumo_128` ≈ 2600） | 超过 2.8 s 说明句子超 8 字，属规格错误 |
| 体积预算 | 57 条 × 平均 ≈ 1.05 s × 44.1 KB/s ≈ **2.5 MB** | 可接受（既有 16 条 sfx 仅 95.7 KiB）。**若需压包**：降到 16000 Hz 可再省 27%（语音仍可懂），但需重测 |
| 内存（解码后） | 57 × 88.2 KB/s ≈ **5.2 MB** | 因此**不启动预载**，见 §5.6 |

**平台备注（本项目当前只发 PC / pygame）**：若将来上移动端，WAV 的体积（2.5 MB）与内存（5.2 MB）是首要问题，届时应转 OGG Vorbis / Opus。本机无 ffmpeg，**这条明确留待 CI 或后续工具链**，v1 不做，也不在本文写不可执行的命令。

### 5.3 生成命令模板（**可复现，已实测**）

**单条生成（两步）**：

```bash
# ① 合成：say 直接出 AIFC 22050 单声道（不需要 --data-format，本机该选项不可用）
/usr/bin/say -v Tingting -r 175 -o /tmp/vo_tmp.aiff "门前清一番"

# ② 转 WAVE/Int16/22050
/usr/bin/afconvert -f WAVE -d LEI16@22050 /tmp/vo_tmp.aiff \
                   game/client/assets/vo/vo_s2_yaku_menzen.wav
```

> ⚠️ **不要写 `--data-format=LEI16@22050`**：本机 9 个 zh_CN 音色全部报 `This synthesizer does not support data format specifications.`（退出码 1）。默认输出**已经是** 22050 单声道 16-bit，只是容器为 AIFC，交给 `afconvert` 转即可。
> ⚠️ **`-r 175` 必须显式写**（虽然等于默认值）。不写的话，任何人改了系统偏好里的语速，重跑结果就不同——可复现性要求写死。

**参数表**：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 音色 `-v` | `Tingting` | 备选 `Shelley` / `Sandy` / `Flo`（换音色须全量重生成） |
| 语速 `-r` | **175** | 系统默认值，显式写死。压缩总时长的旋钮是 190（省约 8%） |
| 输出 `-o` | `/tmp/vo_tmp.aiff` | 中间件一律落 `/tmp`，**不入仓库** |
| 转码 `-f` | `WAVE` | RIFF 容器 |
| 转码 `-d` | `LEI16@22050` | little-endian 16-bit / 22050 Hz（`afconvert` 的写法与 `say` 不同，别搞混） |

### 5.4 批量生成脚本的规格（**只给规格，不写脚本文件**）

| 项 | 规格 |
| --- | --- |
| 输入 | `game/client/assets/vo/vo_lines.tsv`：两列 `id<TAB>文本`，57 行，UTF-8 无 BOM，无表头。**文本一律汉字数字** |
| 依赖 | `/usr/bin/say`、`/usr/bin/afconvert`、python3 **stdlib only**（`subprocess` / `wave` / `array` / `json` / `pathlib`）。**禁止** numpy / soundfile / ffmpeg（本机都没有） |
| 步骤 1 合成 | 逐条 `say -v Tingting -r 175 -o /tmp/vo_tmp.aiff "<文本>"`；失败即中止并报出 `id` + 被合成的文本 |
| 步骤 2 转码 | 逐条 `afconvert -f WAVE -d LEI16@22050 /tmp/vo_tmp.aiff <out>/<id>.wav` |
| 步骤 3 读入 | `wave.open()` → `array.array("h")` → 转 float（`/32768`），去均值（DC） |
| 步骤 4 裁剪 | 阈值 **−50 dBFS（相对本句峰值）**：首端保留 **5 ms** 前滚，尾端保留 **25 ms** 后滚 + **8 ms 线性淡出** |
| 步骤 5 归一化 | 先算整句 RMS（**排除** < −50 dBFS 的帧），增益至 **−20.0 dBFS**；再把峰值钳到 **−3.5 dBFS**；若钳位使 RMS 偏离 > 1 dB ⇒ **峰值优先** + 记 WARN |
| 步骤 6 写出 | 同规格 WAV 覆盖写（`array` 回 int16，`wave` 写 22050/1ch/16bit） |
| 步骤 7 复测 | 重新 `wave.open()` 读回，测 `ms` / `peak_dbfs` / `rms_dbfs` / `chars`，写入 `vo_manifest.json` |
| 步骤 8 偏差校验 | 打印「实测 vs 保守估计 `60+250×字数`」偏差表。**任一条偏差 > 20% ⇒ 判定文本异常**（多音字/断句/被 TTS 读成英文），必须回改文本重跑，**不许放行** |
| 幂等 | 输出路径纯由 `id` 决定，重跑覆盖；**不删除目标目录内其他文件**；失败条目不留下半成品 |
| 耗时预算 | 57 条 < 40 s（实测单条 0.15–0.4 s） |
| 日志 | 每条一行：`id / chars / ms / peak / rms`；末尾汇总 `57 条 / 总字节 / 总时长` |
| 归档 | 脚本与 tsv **随仓库提交**（无第三方依赖，任何人都能复跑）；wav 亦提交（2.5 MB 可接受） |

### 5.5 `vo_manifest.json` 规格

运行时用它做**「先算后播」的预算计算**与**高亮的绝对时刻表**（§3.7）。缺它则退化为公式估算（§3.8）。

```json
{
  "version": 1,
  "voice": "Tingting",
  "rate": 175,
  "sample_rate": 22050,
  "channels": 1,
  "generated_at": "2026-10-23",
  "generator": "vo_build.py v1",
  "items": {
    "vo_s2_yaku_menzen": {
      "file": "vo_s2_yaku_menzen.wav",
      "chars": 5,
      "ms": 1310,
      "peak_dbfs": -3.50,
      "rms_dbfs": -20.02
    }
  }
}
```

| 字段 | 必填 | 用途 |
| --- | --- | --- |
| `ms` | ✅ | 装配预算 + 高亮时刻表（**这是全篇最关键的一个数字**） |
| `chars` | ✅ | 供运行时交叉校验（`ms / chars` 落在 200–300 之外 ⇒ 记 WARN，疑似 TTS 读错） |
| `peak_dbfs` / `rms_dbfs` | ✅ | 试听前的客观体检 |
| `voice` / `rate` | ✅ | 换音色时用于检测「manifest 与 wav 不同批」 |

### 5.6 加载规格（决定首帧不被拖）

| 批次 | 内容 | 时机 | 条数 | 预算 |
| --- | --- | --- | --- | --- |
| **A 骨架句** | S1(3) + S3(2) + S4(8) + S5(7) + S6(14) | 结算页 `onEnter` **同步** | 34 | ≤ 25 ms（藏在 `F-G-05` 的 120 ms 淡入里） |
| **B 明细句** | S2 番种 16 + 摘要 5 | S1 首句起播后，**每帧 ≤ 6 句**增量加载 | 21 | 4 帧内完成（≈67 ms），远小于 S1 的 492–580 ms 窗口 |

- 加载失败/文件缺失 ⇒ 该 id 记为 `None`，**不重试、不抛异常**（`V-R4`）。
- **不做启动期预载**：57 条 × 88.2 KB/s ≈ 5.2 MB 解码内存，启动期加载会拖首帧，也不符合「结算功能按需」的原则。
- 会话内**只加载一次**，常驻到进程结束（局终页一局一次，最多 8 次/场，重复加载纯浪费）。
- 若实测批次 A 超 40 ms ⇒ 改为「`onEnter` 只加载 S1/S4/S5/S6（19 条），S2/S3 在 S1 窗口内补」——**降级路径已预留在本文**，不需要重新设计。

### 7.3 可行性矩阵：`6200 ms` 到底能念什么

动效的时间轴反推出每段预算：`n=4` 时 `MULT(4)=584`，`TOTAL = 2620 + 584 + 4D = 6200` ⇒ **`D = 749 ms`**。逐段对照实测：

| 段 | 动效给的段长 | 该段最必需的句子 | 实测时长(r=175) | 能否装下 |
| --- | --- | --- | --- | --- |
| S1 番种逐条 | `D = 749`（n=4）/ `467`（n=6） | 三色同顺（名-only） | 1060 | ❌ n=6 时被截到 44% |
| S2 合计 | 520 | 合计四番 | 957 | ❌ 缺 437 ms |
| S3 加成 | 460 | 庄家加一番 | 1204 | ❌ 缺 744 ms |
| S4 封顶 | 300 | 已封顶 | 698 | ❌ 缺 398 ms |
| S5 倍率 | `MULT(4)=584` | 十六倍 | ~810 | ❌ 缺 226 ms |
| S6 支付 | 880 | 放炮者付十六分 | ~1810 | ❌ 缺 930 ms |

**三条硬结论**：

1. **`6200 ms` 下，六个段里没有一段能装下它自己的最短句子。** 所有语音都会被 `fadeout(30)` 截断——玩家听到的是「自摸…四…庄家…一…已封…十…放炮者…」，**这是碎片，不是播报**。这比「没有语音」更糟：它听起来像 bug。
2. **`n` 越大，`D` 越小，而每条内容长度不变** —— `n=6` 时 `D=467 ms`，连 2 字的「自摸」（492 ms）都装不下。**结构上无解**，不是调参问题。
3. 因此 `6200 ms` 与「人声念出番数推导过程」**不可兼得**。而用户的原话需求是「番数计算的**详细过程**」——语音是这个需求的一半（字幕是另一半）。把语音砍成锚点，等于只交付了字幕。

**两个可选方案（需 team-lead / 用户裁决）**：

| | 方案 A：服从 6200 ms | 方案 B：**推荐** |
| --- | --- | --- |
| 时间轴 | 动效原样（6200 / TIGHT 4200） | **`BUDGET_NORMAL` 6200 → 9000 ms**；`BUDGET_TIGHT` 4200 保持（纯字幕形态不变） |
| 语音内容 | 只做**听觉锚点**：S2「四番」、S3「自摸」、S5「一倍」、S6「各家支付」——每段 2 字 | **完整六段推导**（本文 §2 的 57 条句库），超预算走 Tier2/Tier3 摘要 |
| 玩家听到 | 「自摸…四番…一倍…各家支付」= 几乎无信息 | 「自摸 · 门前清一番 · 七对子两番 · 自摸不加番 · 合计三番 · 八倍 · 三家各付八分」 |

**方案 B 的 `9000` 是怎么来的（可复算）**：
- `n=4, MULT=584` ⇒ `4D = 9000 - 2620 - 584 = 5796` ⇒ **`D = 1449 ms`**，可容纳最长番种整句「门前清一番」1327 ms ✅

- 与本文 §3.3 的三档装配天然衔接：**降档解决「n 大装不下」，而不是靠 `fadeout` 截断。**

### 7.7 v1.2 追加：两条问答与一处撤回（已答复 art-model-director）

**Q1：`UI` 问「S1 番种行 700 ms 够不够念『三色同顺，二番』」→ 不够，差 2.4 倍。**
实测「三色同顺」1060 + 90 停顿 + 「二番」500 = **≈1650 ms**。若只念名 = **1060 ms**（700 差 1.5×）。「庄家加一番」1204 vs 600（2.0×）、「超过封顶，按六番计」≈2060 vs 600（3.4×）、「三家各付一百二十八分」2600 vs 900（2.9×）、荒庄三句 ≈3040 vs 2100（1.45×）。

**Q2：`UI` 问「TTS 起播是否有 200–300 ms 延迟，S0 要不要从 300 抬到 500」→ 没有，保持 300。**
语音是**离线烘焙 + 启动预载**，运行时零 TTS、零解码。首字延迟 = 首静音 ≤10 ms（实测原始 1–21 ms，稳定 4–5）+ mixer buffer `512/44100` = 11.6 ms + 同帧调度 0 = **≈25–40 ms**。真正会吃掉 S0 的不是延迟，而是 `UI` 的 S0 模板含**昵称**——语音不能念昵称（§6 反模式 4），我只念「自摸」492 ms。

**撤回：启动期预载改为可接受。**
我 v1.0 §5.6 反对启动预载，依据是 57 条 ≈5.2 MB 解码。若最终收敛为 **34 条**（`MOTION` 的扁平形态），解码仅 ≈3.0 MB、耗时 **≈40–60 ms**，按 `F-AU-00d` 启动期一次性 `Sound()` **可以接受**，我同意 `MOTION` §5 的预载口径。§5.6 的「批次 A/B 懒加载」**仅在 57 条方案下生效**。

### 8.6 阅读时间与「跳过播报」的衔接（**阅读时间是动态的，不是常量**）

#### 算法（v1.4 伪代码，实现照抄）

```
def plan_voice(yaku, han_base, dealer_bonus, total, mult, tsumo, per_payer, budget, dur):
    # yaku = win.yaku[]（有序，判定序），dur = {id: 实测ms}
    seq = [mode_id]                                     # A1
    cand = [(han_of(y), i, vo_id_of(y)) for i, y in enumerate(yaku)]   # 全量候选（有序）
    seq += [vid for _, _, vid in cand]
    if tsumo:             seq.append("vo_tsumo_no_add")  # A1（最高保护）
    if dealer_bonus == 1: seq.append("vo_dealer_bonus")  # A1（v1.4 起不可删）
    seq.append(han_id(total))                            # A1，含 vo_han_0「无番」
    if han_base + dealer_bonus > 6: seq.append("vo_cap") # A2
    seq += [mult_id(mult), pay_id(tsumo, per_payer)]     # A1

    # D：按 (han 升序, yaku_idx 降序) 逐条删
    victims = [vid for _, _, vid in sorted(cand, key=lambda t: (t[0], -t[1]))]

    # A2 例外：cap 与 tsumo_no_add 并存且超预算 ⇒ 先让 cap
    a2 = ["vo_cap"] if ("vo_cap" in seq and tsumo) else []

    for v in victims + a2:          # 注意顺序：番种全删完才动 cap
        if total_ms(seq) <= budget: break
        if v in seq: seq.remove(v)

    n_voiced = len([v for v in seq if v in DROPPABLE_16])   # 白名单，不是前缀
    if 2 <= n_voiced <= 6: seq.append(f"vo_yaku_sum_{n_voiced}")   # S-2 已裁 B：仅摘要路径接，逐条路径不接
    return seq
```
