## 0. 与 P0.5 已确认意图的对应关系（先对齐，再展开）

### 0.1 用户已确认的 5 行（**不得改动**）

```
1. 一句话定位：一款对标腾讯麻将的四人麻将游戏，你一个人对着三个 AI 打，一局一局往上算分，比谁最后分高。
2. 怎么操作：轮到你时点一张牌打出去；别人打出的牌会弹「碰 / 吃 / 杠 / 和」按钮，能按就按；自己手里能暗杠、加杠时按钮也会亮。
3. 一局怎么玩：起手十三张，摸一张、打一张，凑出四组顺子或刻子加一对将（或者七对子）就能和牌；和牌按牌型番数算分，番越高赢越多；牌摸完了还没人和牌，这局算荒庄。
4. 赢的条件：一场固定打四局，四家轮流坐庄，四局打完比总分，谁分高谁赢；庄家和牌或荒庄就连庄再打一局，连庄不占局数，分数一路累加。
5. 一句话亮点：有了番型和累计分，你会为了「清一色」「七对子」这种大牌去赌一把，而不是见和就和 —— 每一把都要权衡赢得大还是赢得稳。
```

## 1. 番种表（14 番种 + 2 加成，可算法化）

### 1.1 判番的统一输入与统一口径（先定口径，再逐条判）

判番函数签名为纯函数，输入恒为五元组：

```
ScoreHand(concealed_with_winning_tile, melds, winning_tile, is_tsumo, ctx) -> {tags[], han, ...}
  ctx = { winner_is_dealer, is_rinshan }        // is_rinshan = 和牌张是否本次杠的补牌
```

**口径 1（全集）**：`all = concealed_with_winning_tile ∪ ⋃melds[].tiles`。凡「14 张」表述一律指**逻辑 14 张**（每个杠按 3 张计入面子），物理张数 = `14 + kans`（`GAME_DESIGN.md` §3.2 口径不变）。

**口径 2（拆法枚举）**：番种判定的基础是「4 组面子 + 1 将」的**全部拆法**。现有 `Decompose`（`mahjong_rules.cc:29`）只返回 `bool`，**必须新增枚举版**：

```
EnumerateDecompositions(concealed_with_winning_tile, melds) -> vector<Decomposition>
  Decomposition = { groups[4] (meld 引用或 concealed 面子), pair (牌面), win_group_index (和牌张所在组或其索引) }
```

**口径 3（同一拆法内取最大）**：`han(手牌) = max_{D ∈ 拆法} Σ_{番种成立(D)} 番数`。**禁止跨拆法拼凑**（一手牌不能「在拆法 A 拿平和 + 在拆法 B 拿一杯口」）。**同番数时取枚举序第一个拆法 —— 枚举序的冻结见 §1.3.4**（这是判番唯一的不确定源，必须一起冻结）。

**口径 4（互斥只在结构上无法同时成立时才算，不额外写排除逻辑）**：本表只有一组人造排他（清一色 / 混一色，见 §1.3.2）；其余互斥（平和 vs 对对和、七对子 vs 三暗刻 等）由牌型结构天然保证，**不得**在代码里再加互斥分支。

**口径 5（无起和番）**：**任何完成形都能和牌**，不设「必须 ≥ 1 番才能和」的限制（沿用 `GAME_DESIGN.md` §6.2 的刻意取舍）。0 番和牌合法，得 1 分（§2.1）。

### 1.3 叠加与取舍规则（**四条，逐条冻结**）

**§1.3.1 叠加：全部累加（求和），不做「取最高」**。`han_base = Σ_{命中的番种} han`。理由：`2^番` 的本质是倍率，取最高会让「清一色 + 混一色」之外的正常叠牌（如 门清+平和+断幺九）拿不到应有的倍率增长，等于把番种表退化成「只认最大那个」。

**§1.3.2 唯一的排他组（一色组）**

| 排他组 | 成员 | 规则 | 不写排他逻辑的理由 |
| --- | --- | --- | --- |
| 一色组 | `pure_one_suit`(5) / `honitsu`(2) | 取**高者**，不得相加 | `IsPureOneSuit` 已排除字牌 ⇒ 与「混一色要求至少 1 张字牌」**结构上不可能同时成立**。这条「排他」只用于读文档时的确定性，`han()` 里**不需要任何 `if 互斥` 分支** —— 两边都判，绝不会双命中 |

其余「互斥」（平和 vs 对对和、七对子 vs 三暗刻、平和 vs 七对子…）全部由**牌型结构**保证，**不得**在代码里再加排除分支（多一条分支就多一处可能与结构判断不一致的地方）。

**§1.3.3 箭刻合并为一条**：`yakuhai` 命中 n 组（n ∈ 0..3）时，`win.yaku[]` 中**只出现一条**，`han = n`。理由：① 一个 id 一条记录，客户端渲染与协议断言都只需处理「每 id 至多一条」这一种形状；② 若拆成 3 条同名记录，就必须再冻结「白/发/中 的排列顺序」，多一处可错点；③ 小三元已单独成条，箭刻的逐组明细对玩家理解没有增量。

**§1.3.4 同番数拆法的裁决（确定性真正的风险点，必须冻结）**：当多个拆法的 `han_base` **相同**时，取**拆法枚举序中的第一个**。因此 `EnumerateDecompositions` 的产出顺序也必须冻结：

```
① 将牌牌面按面编号升序（0..33）逐个尝试；
② 每个将牌定下后，面子按「本拆法的最小未用牌面升序」依次展开；
③ 同一最小牌面下，**刻子分支先于顺子分支**（与现有 Decompose 的 A/B 分支次序一致，见 mahjong_rules.cc:45-67）。
```

即：**枚举序 = 现有 `Decompose` 的回溯序**。这样「同番取第一个」与「现有 `IsWinningHand` 的寻找序」完全一致，不会出现「判定说能和、判番却按另一套拆法算番」的分裂。

> 注：**判定顺序（§1.2 的序）不影响 `han` 总和**（加法可交换），它约束的是 `win.yaku[]` 的数组顺序与渲染顺序；真正影响数值确定性的只有 §1.3.4。

### 1.4 与「清一色须无字牌 / 无字一色」旧约束的关系（**明确沿用 + 拆分**）

旧规格（`GAME_DESIGN.md` §0.2、§6.2、`RULESET.md` §3.4）写明「清一色含任何字牌即不成立」「无字一色」。

**新表的处置：沿用旧判据（清一色仍然零字牌），并把被清一色拒绝的那部分牌**（一门数牌 + 字牌）**拆出一个新番种 `honitsu`**。

| 牌面构成 | 旧处理 | 新处理 |
| --- | --- | --- |
| 全为一门数牌，零字牌 | 清一色 ×4 | `pure_one_suit` **5 番** |
| 一门数牌 + 有字牌 | 什么都不是（M=1） | `honitsu` **2 番**（新增） |
| 全字牌（字一色） | 无 | **仍无**：`honitsu` 要求「恰含一门数牌」，全字牌不满足；`pure_one_suit` 要求零字牌，也不满足。全字牌牌只能拿 `toitoi` + `yakuhai`×n + `sanankou` + `tsumo` |

**沿用 + 拆分的理由**（三条，逐条可核）：

1. **不破既有实现与单测**：`IsPureOneSuit` 一行不改，`pure_one_suit` 这个 tag 字符串不变，客户端已渲染的中文标签不用动。
2. **补上一个真实的玩法空洞**：旧表下「一门数牌 + 字牌」的和牌只有 M=1，比「什么都不要的垃圾手」还难做却拿一样的分 —— 这是旧表最反玩法的一处。拆出 `honitsu` 正是填这个洞。
3. **`honitsu` 2 番 vs `pure_one_suit` 5 番 = 2.5 倍差**，恰好表达「去掉字牌」的难度跃升；把两者做成一档会让玩家看不出「清一色到底有多难」。

### 1.5 本表不含的番种（**保留项，不是本期不做**）

| 不含 | 永久保留理由 |
| --- | --- |
| 符数 | 与「番数 → 倍率 = 2^番」的纯整数幂模型互斥：符数会带来 4 舍 6 入/进位等第二种舍入源，使「一张牌值多少分」不可心算。零和由整数运算天然保证（§2.4），不需要符数来「调节」 |
| 立直 / 一发 / 里宝牌 / 宝牌指示牌 | 与「无振听、无王牌」的前提绑定。立直要求「振听」概念（否则立直后放炮可以装作没看见），引入即要把 `win` 选项从「只看 can_win」改成「再看振听标记」，动摇 `ClaimOptions` 的纯函数性 |
| 国士无双 / 九莲宝灯 / 字一色 / 绿一色 / 四暗刻 / 大三元 / 小四喜 / 清老头 | 全部是**役满档**。役满需要独立的「役满优先于番数合计」第二套分值口径 + 封顶豁免，等于在番数制上再套一层。而 A 批的目标是「番越高赢越多」的一条曲线，不是两张分值表。**保留**，等玩家反馈「不够爽」再谈 |
| 二杯口 / 混全带幺九 / 纯全带幺九 / 三色同刻 / 三连刻 / 混老头 | 判定全部需要「两杯口替换一杯口」这类**替换关系**或「每一组都含幺九」的逐组谓词。收益是 +1~3 番，成本是给 §1.1 口径 3（同一拆法取最大）再加一层「替换」语义 —— 单位实现成本换来的玩法增量低于已有 14 番种。**保留** |
| 海底摸月 / 河底捞鱼 | 判据是 `remaining == 0`，与**荒庄判据**共用同一边界（`RULESET.md` §7「需要摸牌而 remaining==0 ⇒ 荒庄」）。给同一个边界挂两种语义（一种是荒庄、一种是 +1 番）是这个项目最容易写错的一类 bug，而玩家在剩余 0 张时还要反应过来「这张是海底牌」几乎没有体验收益。**建议永久不做** |
| 抢杠和 | 见 §4.5（**建议永久不做**，理由是架构级：需要回滚） |
| 四杠散了 | 纯荒庄模型下无玩法价值（荒庄已不计分），且四杠组合概率极低。**建议永久不做** |

## 2. 番数 → 分数公式

### 2.1 主公式（逐项可算，无舍入）

```
逐番种判定（§1.2）        => han_base = Σ 番数                      // 0..11（理论）
庄家加成                  => han_dealer = han_base + (winner_is_dealer ? 1 : 0)
封顶                      => han = min(han_dealer, 6)                // 硬上限，庄家加成也受此封顶
倍率                      => R = 2^han                              // R ∈ {1,2,4,8,16,32,64}
```

| 情形 | 放炮者 | 和牌者 | 其余两家 | 合计 |
| --- | --- | --- | --- | --- |
| 荣和（ron） | `−R` | `+R` | `0` | `0` |
| 自摸（tsumo） | — | `+6R` | 各 `−2R` | `0` |
| 荒庄（draw_exhausted） | `0` | `0` | `0` | `0` |

- `per_payer` = `R`（荣和）/ `2R`（自摸）；`total` = `R`（荣和）/ `6R`（自摸）。字段语义与 `ScoreResult`（`mahjong_rules.h:215`）**完全一致，只改取值**。
- **全部为整数运算，零舍入**（`R` 是 2 的整数次幂，`2R`/`6R` 仍是整数）。

### 2.2 番 → 倍率 → 分数全表（**逐项可算，直接作为单测用例**）

| `han` | `R = 2^han` | 荣和：放炮者 / 和牌者 | 自摸：每家付 | 自摸：和牌者收 |
| --- | --- | --- | --- | --- |
| 0 | 1 | −1 / +1 | 2 | 6 |
| 1 | 2 | −2 / +2 | 4 | 12 |
| 2 | 4 | −4 / +4 | 8 | 24 |
| 3 | 8 | −8 / +8 | 16 | 48 |
| 4 | 16 | −16 / +16 | 32 | 96 |
| 5 | 32 | −32 / +32 | 64 | 192 |
| 6 | 64 | −64 / +64 | 128 | 384 |

- **单局最大得失分 = +384 / −128**（6 番庄家自摸封顶），四家之和恒为 0。
- 与旧规格对照：旧「单局最大 +96 / −32」（附录 A）作废，改为 **+384 / −128**。

### 2.3 新旧换算规则（自洽性证明，逐条可断言）

旧规格的倍率是 `M = 4^[seven_pairs] × 4^[pure_one_suit]`，自摸另 ×2。**定义 `han_legacy = 2×[seven_pairs] + 2×[pure_one_suit] + 1×[tsumo]`**，则恒有：

| 旧情形 | 旧 `han_legacy` | 新 `R = 2^han` | 是否相等 |
| --- | --- | --- | --- |
| 七对子荣和 | `M=4` | `han=2 ⇒ R=4` | ✅ |
| 清一色荣和 | `M=4` | `han=2 ⇒ R=4` | ✅ |
| 七对子 + 清一色荣和 | `M=16` | `han=4 ⇒ R=16` | ✅ |
| 平和自摸（三家各 2、和牌者 6） | `M=1, ×2` | `han=1 ⇒ 每家 2、和牌者 6` | ✅ |
| 七对子自摸（各家 −8、+24） | `M=4, ×2` | `han=3 ⇒ 每家 8、和牌者 24` | ✅ |
| 七对子 + 清一色自摸（各家 −32、+96） | `M=16, ×2` | `han=5 ⇒ 每家 32、和牌者 96` | ✅ |

**结论（可断言）**：**「1 番 = ×2、2 番 = ×4、4 番 = ×16」不是举例，而是上表六行逐项相等的数学结果**。旧系统被完整嵌入新系统，新系统 = 旧系统 + 新增番种。

⚠️ **必须写明的不保证项**（防止下游误当回归标准）：**同一手牌的新旧总分不保证相等**。因为新增番种会与旧 tag 叠加 —— 例如一手「门清 + 七对子 + 清一色」（若再加 `tanyao` 也合法）在旧表是 ×16，在新表是 `seven_pairs(2) + pure_one_suit(5) + menzen(1) [+ tanyao(1)] ≥ 8 番 → 封顶 6 番 = ×64`。这是 A 批**故意**的效果（清一色当年被严重低估），不是缺陷。
可断言的回归锚点只有一条：**「除旧三 tag 外无任何新番种成立」的手牌，新旧 `delta` 逐位相等**（用例需人工构造：七对子带幺九/字牌以避开 `tanyao`，清一色带 1/9 且非对对和以避开 `toitoi`）。

### 2.4 零和证明（逐情形）

- 荣和：`−R + R + 0 + 0 = 0`。
- 自摸：`3×(−2R) + 6R = 0`。
- 荒庄：`0 + 0 + 0 + 0 = 0`。
- 场次累计：每局之和为 0 ⇒ 逐位相加后 `Σ match_total == 0`（归纳成立）。

### 2.5 庄家 与 连庄的加成选择（**各给一条理由，不许「视情况」**）

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 庄家加成 | **+1 番**（不是 ×1.5） | `×1.5` 在「1 番 = ×2」的整数幂表上会产出非整数（如 0 番 `1 × 1.5 = 1.5`），必须引入第二条舍入规则（点以下进位等）；一旦有第二条舍入规则，「番数 → 分数」就不再是一张能心算的 7 行表（§2.2）。**+1 番 = 分数翻倍，与主公式同一条曲线，零新增规则**，且对玩家可直接解释为「庄家多一番」 |
| 庄家加成受封顶 | **是**（同一封顶 6 番） | 若庄家加成不受封顶，则「6 番封顶」这件事就要向玩家解释两次（闲家 6 番、庄家 7 番），两套上限是纯负债 |
| 连庄加成 | **无（0）** | 连庄的收益已经由结构给出：**多打一局 = 多一次得分机会**，且连庄期间累计分**不重置**。再叠加番数加成会让「已经领先的庄家」边际收益越来越高（复利），与「四局比总分、后面还有追分机会」的设计方向相反 |

### 2.6 设计断言：为什么这一版能治「见和就和」（P0.5 第 5 行的兑现判据）

| 手牌类型 | 典型番数（未含庄家/自摸） | 荣和得分 | 与「垃圾和牌」的倍数 |
| --- | --- | --- | --- |
| 副露垃圾手（有碰/吃、含幺九字牌、无任何番种） | 0 番 | **1** | 1× |
| 门清 + 断幺九 | 2 番 | **4** | 4× |
| 门清 + 平和 + 断幺九 | 3 番 | **8** | **8×** |
| 门清 + 混一色（+ 自摸） | 4 番 | **16** | 16× |
| 门清 + 清一色（+ 自摸，易触封顶） | **6 番（封顶）** | **64** | 64× |

> 表中番数为典型值；实际按 §1.2 逐项判番求和后封顶（同一手牌可能再多命中 `yakuhai` 等），但上表的**倍数关系**在封顶前成立、封顶后只会更大。

**判据（供 P3 验收）**：玩家在一局里放弃一次 0~1 番的和牌、多打两手去追 3 番，期望收益必须为正 —— 上表前两行给出的 8 倍差是这条判据的量化依据。若 P3 实测玩家仍然「见和就和」，说明番差被局数稀释（四局太短），此时应调 `HANDS_PER_MATCH`（§3.1 参数）而不是加番种。

## 3. 场次 / 连庄状态机

### 3.1 场次参数（全部为冻结候选值）

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `HANDS_PER_MATCH` | **4** | 一场 4 局（用户 P0.5 第 4 行确认） |
| `SEATS` | 4 | 座位 0..3，出牌顺序 `0→1→2→3→0`（不变） |
| `dealer_` 初值 | **0**（建桌真人） | 首局庄家 = 房主座位 |
| `RENCHAN_MAX` | **4** | **单场累计连庄次数上限**，见 §3.5 的取舍说明 |
| `INTER_HAND_DELAY_MS` | **5000** | 局终 → 下一局 `game_start` 的固定间隔（可点「继续」提前） |
| 庄家加成 | +1 番 | §2.5 |
| 连庄加成 | 0 | §2.5 |

### 3.2 单局内的流程（**不变**，只增两个杠动作）

```
TURN_START → (需摸牌) draw → 打牌窗口
打牌窗口：可 [自摸和牌] / [暗杠] / [加杠] / [打出一张]
    └─ 暗杠/加杠 → 补摸一张（牌山头） → 回到打牌窗口
打出 → 鸣牌窗口（win > kong > pong > chow > pass，头跳不变）
    ├─ 有人和 → 局终（win_ron）
    ├─ 有人鸣 → 打牌窗口（该家）
    └─ 全 pass → 下一家 TURN_START
TURN_START 且需摸牌而 remaining==0 → 局终（draw_exhausted）
打牌窗口内自摸和 → 局终（win_tsumo）
```

`Phase` 枚举需要**新增两个成员**（`room.h:257`）：

| 新 Phase | 含义 |
| --- | --- |
| `kHandSettled` | 本局已结算、`game_end` 已广播，正在 `INTER_HAND_DELAY_MS` 内等下一局（此状态下**拒绝一切对局帧**，回 `BAD_REQUEST`） |
| `kMatchFinished` | 场终结算已广播，房间只等回收（等价于现有 `kFinished` 的语义，但用于场级） |

### 3.3 局终 → 下一局 / 场终 的状态转移（文字箭头 + 每个转移的判据）

```
[ready]                        判据：4 座位就位且有真人发 ready
   ↓
S1 局开始（发牌）              判据：进场 or 上一局的「进入下一局」
   ↓                          副作用：hand_no_ 不变；deal_count_ += 1；按 dealer_ 发牌
S2 摸打循环（§3.2）            判据：无
   ↓
S3 局终（game_end 广播）        判据：win_ron / win_tsumo / draw_exhausted
   ↓                          副作用：match_total_[s] += delta[s]（四家都加）
S4 连庄判定
   ├─ 判据 A：reason ∈ {win_ron, win_tsumo} 且 winner_seat_ == dealer_   → 连庄
   ├─ 判据 B：reason == draw_exhausted（荒庄无和牌者，一律视为庄家荒庄）  → 连庄
   └─ 判据 C：其他（闲家和牌）                                            → 轮庄
S4a 连庄                      副作用：renchan_count_ += 1；dealer_ 不变；hand_no_ 不变
S4b 轮庄                      副作用：dealer_ = (dealer_ + 1) % 4；hand_no_ += 1；renchan_count_ 不变
   ↓
S5 场终判定
   ├─ 判据 D：hand_no_ > HANDS_PER_MATCH(4)        → 场终
   ├─ 判据 E：renchan_count_ > RENCHAN_MAX(4)      → 场终（兜底，§3.5）
   └─ 判据 F：否则                                  → 进入下一局
S5a 进入下一局                副作用：等 INTER_HAND_DELAY_MS → 回到 S1
S5b 场终（match_end 广播）     副作用：按 match_total_ 排名 → 通知 lobby 落库 → 房间回收
```

**关键点（易错，逐条强调）**：

1. **`hand_no_` 只在轮庄时 +1，连庄时不动** —— 这就是「连庄不占局数」的机械含义。`hand_no_` 的取值域是 `1..4`（`> 4` 即场终）。
2. **`deal_count_`（实际打过的局数）与 `hand_no_` 是两个不同的量**，`deal_count_ ≥ hand_no_`；战绩与统计用 `deal_count_`，局号展示用 `hand_no_`。
3. **`match_total_` 在每一局结束时无条件累加（含荒庄的 +0）**，不做任何「只记庄家」的特判。
4. 荒庄的连庄**不需要看是谁**（荒庄没有和牌者），所以判据 B 是一个独立的、无条件的转移 —— 这是把用户的「庄家和牌或荒庄就连庄」翻译成代码时唯一会产生歧义的地方，此处**显式消歧**：荒庄一律连庄。

### 3.4 场终与排名

- 排名：按 `match_total_` **降序**；**同分并列同名次**，后续名次跳号（competition ranking：两处并列第 2 ⇒ `1,2,2,4`；并列第 1 ⇒ `1,1,3,4`）。
- **不设任何 tiebreak**（不按座位、不按和牌数、不按谁先摸到最后一张）。理由：并列是公平结果；任何 tiebreak 都会让玩家看到「我分一样却排第二」而无法解释原因，而本作没有可供解释的公开数据（和牌数等指标不展示）。
- `match_end` 数据（结算页唯一数据源）：

```json
{
  "type":25,
  "hands_played": 5,
  "renchan_count": 2,
  "rankings": [
    {"seat": 0, "final_score":  37, "rank": 1},
    {"seat": 2, "final_score": -10, "rank": 2},
    {"seat": 1, "final_score": -10, "rank": 2},
    {"seat": 3, "final_score": -15, "rank": 4}
  ]
}
```

- **单一数据源**：不另发 `totals[]`（`rankings[].final_score` 已足够），避免两份数据不一致 —— 沿用本项目「一个值只有一个出口」的一贯做法。
- 上例含义：`seat 0` 第一；`seat 1` 与 `seat 2` 同为 `-10` ⇒ **并列第 2**；`seat 3` 第 **4** 名（并列后跳号，`1,2,2,4`）。
- ⚠️ **验收注意两个易错点**：① 排序必须用**有符号**整数比较（`-10 > -12`，若按无符号或绝对值排会全乱）；② 并列后**跳号**（不是 `1,2,2,3`）。`rankings[]` 的顺序固定为 **rank 升序、同 rank 内 seat 升序**（上例 `seat2` 在 `seat1` 之前即由此得来），客户端按数组顺序直接渲染即可。

### 3.5 `RENCHAN_MAX` 的取舍（唯一的非标准规则，**必须显式列出请用户确认**）

| 项 | 内容 |
| --- | --- |
| 规则 | 单场累计连庄次数 > 4 时，**强制场终**（不再连庄） |
| 上界 | 单场最多 `4 + 4 = 8` 局 |
| 为什么不按「每局号最多连庄 N 次」 | 那样上界是 `4 × (N+1) = 20` 局，一场可能 40 分钟，对一人开发的演示项目不可接受 |
| 为什么必须有 | 连庄是无界转移（庄家连续和牌就一直连），而本作没有「流局变体」来打断它。**一场必然终止**是「比总分」这个设计能成立的前提（否则排名可能永远出不来） |
| 玩家可感知的代价 | 只在「庄家已经连庄 4 次」时生效 —— 此时用一句话解释即可：「连庄已达上限，本场结束」。**不改任何单局手感** |
| 待确认 | ⚠️ 这是本文唯一一条标准麻将没有的规则，**请用户点头**；若用户要求严格照搬标准，则改回「无上限」，代价是场次可能很长 |

### 3.6 累计分的保存与战绩落库

| 项 | 设计 | 理由 |
| --- | --- | --- |
| 场次内保存 | `RoomActor` 新增 `std::array<int,4> match_total_{}`，局终时 `match_total_[s] += settlement.delta[s]` | 房间生命周期从「一局」变为「一场」，累计分天然属于房间状态；不落库（无需跨进程恢复，断线走托管） |
| 每局战绩 | `matches` 表**沿用，字段一个不加**（`delta_score` 仍是**本局**得失分） | 现有 `stats` 的 `games/wins/draws/总分` 语义是「每局口径」，改它会破坏已实现的战绩链路（`ACCOUNT_DESIGN.md` §4）。**不改 = 零回归** |
| 场次战绩 | **新增表** `match_results`（每场每账号一行） | 场次维度是新信息，塞进 `matches` 会让「一行 = 一局」的语义被污染（一行到底是局还是场？） |

```sql
CREATE TABLE IF NOT EXISTS match_results (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  account_id    BIGINT UNSIGNED NOT NULL,
  room_id       VARCHAR(16)     NOT NULL,
  final_score   INT             NOT NULL,   -- 本场累计分（零和，四家之和 0）
  final_rank    TINYINT         NOT NULL,   -- 1..4，同分并列同名次
  hands_played  TINYINT         NOT NULL,   -- 本场实际打过的局数（含连庄）
  dealer_hands  TINYINT         NOT NULL,   -- 该座位坐庄的局数
  ended_at      TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_match_results_account (account_id, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- **写入时机**：与现有「局终通知」同一条链路，改为**场终通知**（`match_end` 之后一次），仍为 fire-and-forget，失败只记日志（`ACCOUNT_DESIGN.md` §2.3 降级语义不变）。
- **`stats` 帧**：现有字段不动（每局口径）；`match_results` 的聚合**本期不接入 `stats`**，理由：先让数据落库，等玩家真去看「场次胜率」再加展示字段，避免一次性改三处（DB、协议、界面）。

## 4. 暗杠 / 加杠

### 4.1 术语与台账口径（先定，后面全部引用）

| 记号 | 定义 |
| --- | --- |
| `melds` | 副露组数。**每个杠（不论明/暗/加）= 1 组** |
| `kans` | 杠数 = `kong`(明杠) + `ankan`(暗杠) + `kakan`(加杠) 的组数。**旧规格的 `kans = 明杠数` 作废**（`GAME_DESIGN.md` §3.2） |
| 逻辑张数 | `concealed + 3×melds ∈ {13, 14}` —— **公式逐字不变** |
| 物理张数 | `concealed + 3×melds + kans = (13 或 14) + kans` —— **公式逐字不变** |

**为什么公式不用改**：一个杠在 `melds` 里记 3 张（账面），第 4 张由 `kans` 单独补回。明杠、暗杠、加杠三者的差别只在「第 4 张从哪来 + 什么时候来」，对台账**零影响**。这一点必须写进实现注释，否则下游很容易给暗杠单开一套张数公式。

### 4.2 暗杠（`ankan`）

| 项 | 规则 |
| --- | --- |
| 时机 | **仅本家行动态**（`concealed + 3×melds == 14`）：正常摸牌后、或上一次杠补牌后的打牌窗口内 |
| 不可用的场合 | 鸣牌窗口（不能对他人打出的牌暗杠）；等待态；`kHandSettled`/`kMatchFinished` |
| 条件 | 手中恰好存在某牌面 `F` 且 `count(F, concealed) == 4`；**且 `remaining ≥ 1`**（无牌可补则不提供选项，与现有 `CanKong` 的 `remaining >= 1` 守卫同源，`mahjong_rules.cc:295`） |
| 动作 | 手牌移除 4 张 `F` → 新增副露 `{"type":4,"tiles":[F,F,F,F]}`（**已排序**）；`melds++`、`kans++` |
| 补牌 | **立即**从**牌山头**取 `wall_[next_index_]`（与明杠同源，`room.cc:973`），`next_index_++`，`remaining_ = kTileCount - next_index_` |
| 之后 | **重新打开打牌窗口**（该窗口内可继续暗杠/加杠/杠上开花和牌/打牌） |
| 张数推导 | 暗杠前 `c + 3m = 14` → 扣 4 张、`m+1` ⇒ `(c−4) + 3(m+1) = 13` → 补 1 张 ⇒ **14** ✅ |
| 可见性 | **自家**视图：4 张牌面。**其他三家**视图：`{"type":4,"tiles":[]}` —— 只给「此处有一组暗杠」，不给牌面（`GAME_DESIGN.md` §8.2 私有信息约束） |
| 协议形状（**关键：两种实现都合法，不需返工**） | `melds[]` 元素的 `tiles` 对 `ankan` 允许 **长度 0 或 4**：`0` = 打码（隐藏），`4` = 可见。**客户端两种都要能渲染**（0 张 ⇒ 画 4 张牌背；4 张 ⇒ 画牌面）。因此「隐藏 vs 可见」是**服务端一处渲染策略**，可分批实现：B1 先发 4 张（=可见，成本最低），后续补隐藏时只改 `BuildSeatsArray`，**协议与客户端一行不改** |
| 隐藏的实现路径（成本受控） | 不大改整块 `seats` 数组：`BuildSeatsArray()` 产出**共享打码版**（`ankan.tiles: []`），随后**仅对「持有暗杠的座位」**额外构建一份带牌面的版本并替换自己那一项。额外构建次数 = 场上暗杠持有者数（实战 ≤ 2），**不是 4 份全量重建** |
| 揭示时机 | 局终时由最后一份 `state_sync`（`PROTOCOL.md` §5.12 已有「`game_end` 前必发一次 `state_sync`」）把 `tiles` 由 `[]` 填满。**不新增字段、不新增帧**。若 B1 采用「可见」策略，此步自然成立（本就是 4 张） |
| 门清 | 暗杠**不破门清**（§1.2 序 1） |

### 4.3 加杠（`kakan`）

| 项 | 规则 |
| --- | --- |
| 时机 | **仅本家行动态**（同暗杠） |
| 条件 | `melds` 中存在 `type == "pong"` 且牌面为 `F` 的组；**且** `count(F, concealed) ≥ 1`；**且** `remaining ≥ 1` |
| 动作 | 手牌移除 1 张 `F`；该 `pong` 组**就地**升级为 `{"type":5,"tiles":[F,F,F,F]}`（**组序不变**，第 4 张追加在末尾）；`melds` 不变、`kans++` |
| 补牌 | 同暗杠（牌山头，`remaining_` 用同一派生公式） |
| 之后 | **重新打开打牌窗口** |
| 张数推导 | 加杠前 `c + 3m = 14` → 扣 1 张、`m` 不变 ⇒ `13` → 补 1 张 ⇒ **14** ✅；`kans+1` 使物理张数守恒 ✅ |
| 门清 | **加杠必然破门清**（因为加杠必然起于一个 `pong`，而 `pong` 已破门清）—— 这是结构结论，不需要判据 |
| 抢杠和 | **不做**；**不设任何抢杠窗口**（见 §4.5）。因此加杠与暗杠走**完全相同的路径**：都在自家的打牌窗口内、都是一次自理动作、都无他家应答、都不新增 `seq` 分支 |

### 4.4 杠上开花（`rinshan`）

| 项 | 规则 |
| --- | --- |
| 定义 | 自摸，**且和牌张就是本次杠的补牌** |
| 计数 | **算自摸**：`tsumo` 1 番照计（`win.tsumo = true`、`reason = 2` 均不变），额外加 `rinshan` 1 番 ⇒ 杠上开花自摸本身 = 2 番 |
| 判定实现 | `RoomActor` 在杠后打开打牌窗口时把本次补牌记为 `kong_draw_tile_`；该窗口内自摸和牌且 `winning_tile == *kong_draw_tile_` ⇒ `is_rinshan = true`。**下一个动作（打牌/再杠/进入下一家）即清空该记录** |
| 荣和 | **永不成立**（荣和没有「本次补牌」） |
| 吃和牌张 | **是** —— 本表唯一两个吃和牌张的番种之一（另一个是三暗刻） |

### 4.5 抢杠和：**建议永久不做**（理由，非「本期不做」）

| 维度 | 内容 |
| --- | --- |
| 它要求什么 | 加杠宣言后、补牌前，其他三家有权用该牌和牌；若抢杠成立，则要**撤销这次加杠**（副露退回 `pong`、手牌补回 1 张）、**退回补牌**（`next_index_--`、`remaining_` 复原），并按「荣和」结算 |
| 与本项目架构的冲突 | `GAME_DESIGN.md` §0.3 的前提是「**一次消息处理 = 一次原子状态转移**」且模型**单向不可回滚**。加杠当前是一次原子转移（升级副露 + 补牌 + 重开窗口），抢杠和语义上要求把已完成的转移**回滚**，等于给状态机引入事务与补偿路径 —— 这正是本项目唯一刻意排除的东西（连超时都用「seq 作废」而不是「取消」来避开回滚） |
| 回滚范围 | `next_index_`、`remaining_`、`kans_`、`melds_[seat]`、`hands_[seat]`、`discard`/牌河可见性、`kong_draw_tile_`、窗口 `seq` —— 八处，任一处漏改就是脏状态 |
| 玩家侧代价 | **零**。加杠是玩家自愿动作（不杠就一定不会被抢），不做抢杠不会造成任何局面无法结束、也不会让任何玩家吃亏 |
| 收益 | 一个稀有 +1 番与一点博弈趣味 |
| 结论 | 收益远小于「打破不可回滚前提」的风险 ⇒ **建议永久不做**。若将来要做，前置动作是先把状态机改成「可补偿」（例如快照 + 重放），而不是在加杠里打补丁 |
| **对既有冻结口径的影响** | **不需要解冻任何一条**。`RULESET.md:268-277`（§4.4「不实现的副露」）本来就写着「加杠……涉及抢杠和牌，明确不在范围」；本次裁决与它**方向一致**，只是把理由从「本期收敛范围」升级为「永久不做 + 架构级理由」。落地动作是**改理由文本、不删这一行**，并把它从「本期不做」区移到「永久不做」区 |
| **对窗口模型的确认** | 加杠**不引入新的应答窗口**：不新增 `claim` 窗口、不占用 15 s、不参与优先级裁决、不影响 AI 鸣牌门槛、协议窗口判定表（`PROTOCOL.md` §5.7）**不多一条路径** |

### 4.6 与 `remaining` / 84 次打牌 / 21 张牌河上限的交叉核对（**已核对代码，逐条给结论**）

| 断言 | 结论 | 依据 |
| --- | --- | --- |
| 牌山 83 张不变 | ✅ | 杠补牌取 `wall_[next_index_]`，与普通摸牌**同一副牌山**（`room.cc:973`）；不引入王牌/岭上牌 |
| `kWallSizeAfterDeal == 83` 不变 | ✅ | `remaining_ = kTileCount - next_index_`（`room.cc:975`）是**派生值**，`next_index_` 从 53 起，与 `kWallSizeAfterDeal` 同源 |
| 单局最多 83 次摸牌 | ✅ | 每次摸牌（含杠补牌）恰好消耗 1 张，牌山 83 张耗尽即 `remaining == 0` |
| 单局最多 84 次打牌 | ✅ | **每次摸牌（含杠补牌）之后必定开一次打牌窗口**（`room.cc:986` 的 `OpenDiscardWindow`），故「摸牌 : 打牌 = 1 : 1」不变；再加庄家第一打 1 次 ⇒ 84。杠只把一次普通摸牌换成一次补摸，**不改变这个 1:1** |
| 单座位牌河上限 21 | ✅ | `⌈84/4⌉ = 21` 只依赖 84，而 84 不变 |
| 实现上必须守的一条 | ⚠️ | 杠补牌处**不得**写 `remaining_ -= 1`，必须复用 `remaining_ = kTileCount - next_index_`（现有 `room.cc:975` 的写法）。否则派生值与 `next_index_` 漂移，`remaining` 会在客户端显示错误 |
| `remaining == 0` 时的杠 | ✅ | 不提供 `ankan`/`kakan` 选项（`remaining >= 1` 守卫）；若仍进入杠路径且 `remaining <= 0`，沿用 `room.cc:968` 的「立即荒庄」处理 |
