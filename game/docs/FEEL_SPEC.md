## 0. 本文的强制口径

1. **一切数值写成常量**：ms / px / 0..1 音量 / 帧数 / dBFS。**禁止**「稍快」「适度」这类形容词（参数必须能被直接实现消费）。**音色**允许用描述性语言，但描述只用于「交音效总监匹配样本」，不用于实现判断（§5.2/§5.3）。
2. **输入永不被阻塞**（硬约束）：从「收到使本家可操作的帧」到「手牌可点」≤ **300 ms**（含动画）。玩家连续快速操作时动画必须**可抢占/加速**，不许排队。
3. **表现层可丢帧，不可改状态**：动画/音效的实现若与 `state_sync` 冲突，一律以 `state_sync` 为准，动画直接 snap 到终态。
4. **不设计任何「帮玩家决策」的功能**：不做推荐打牌、不做听牌进度百分比、不做「打这张能听几张」的推演。听牌提示只回答「我现在听什么、还剩几张」，可吃碰提示只回答「这一张你能做什么」。
5. 所有开关**默认开**；**无设置面板**（`UI_UX_SPEC.md` §13 不变），开关只走快捷键 + 会话内记忆，不落盘。

## 2. 听牌提示

### 2.1 数据契约（**已冻结于 `PROTOCOL.md` v1.7 §5.16 + §11**，本节与协议逐字对齐）

```json
{"type":26,"tenpai_seq":7,"is_tenpai":true,
 "waits":[{"tile":"3p","remaining":2},{"tile":"7m","remaining":1},{"tile":"5z","remaining":3}]}
```

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| **`tenpai_seq`** | int | **每座位独立的单调计数器**（从 1 起、**跨局不重置**），与 `room.seq` **完全解耦**。客户端判据：`tenpai_seq <= last_tenpai_seq` ⇒ 丢弃。⚠️ **不得**拿它与 `room.seq` 比大小（协议陷阱 P4，见下） |
| `is_tenpai` | bool | 本家门前手牌**当前**是否已听牌（13 − 3×melds 张、非和牌形）。**`false` 时服务端必须照发该帧且 `waits: []`**（协议 §5.16 冻结规则 2）：**不得用「不发帧」表示未听牌** —— 否则客户端只能靠超时或推测清空听牌条，「消失」变成不可判定；`tenpai{is_tenpai:false}` 是 `F-TP-11` 的第 ⑧ 号清空信号 |
| `waits[]` | array | **已按牌面序（万→筒→条→字，rank 升序）排好**，客户端**不再排序**；`is_tenpai == false` 时为空数组 |
| `waits[].tile` | string | 与 `PROTOCOL.md` §2.1 同编码（`1m`..`9s` / `1z`..`7z`） |
| `waits[].remaining` | int | **「还没露面的最多还有 N 张」**（**不是**「还能摸到 N 张」）。口径见下，由服务端算，`0..4` |

> ⚠️ **两个 `remaining` 同名不同义，不得混用（协议 §5.16 显式消歧，本节同步）**：
>
> | 字段 | 含义 | 何时变 | 可见性 |
> | --- | --- | --- | --- |
> | `state_sync.remaining`（v1.0 起） | **牌山剩余张数**（`136 − 已摸牌数`） | 任何一家每次摸牌（含杠补牌）都 −1 | 四家公开 |
> | `tenpai.waits[].remaining`（v1.7） | **单牌面的可见剩余枚数**（`4 − 已露面的张数`） | **只在该牌面出现/消失时变**；别人摸进暗手牌**不影响**它 | 仅本家 |
>
> 实现侧命名**必须**分开（v1.8：由「建议」升级为「**必须**」，与 `PROTOCOL.md` §11.3「代码侧命名要求（必须照此）」一致）：**`wall_remaining_`**（牌山剩余）与 **`visible_left`**（单面可见剩余），两个名字不得互换、不得共用变量。
> 为什么这条不能写成「建议」：这是「两个同名字段推错方向相反」的最后一层防线 —— 拿 `visible_left` 去推摸牌永远得 0，拿 `wall_remaining_` 去填 `waits[].remaining` 会**泄露牌山真值**。两者都是 `int`，编译期查不出、review 也抓不住（它们看起来都对），所以只能靠命名与范围断言兜。

> ⚠️ **协议陷阱 P4（为什么 `seq` 换成了 `tenpai_seq`，这条不许改回去）**：客户端判 `action_request` 过期是「`seq < last_seq` ⇒ 静默丢弃」。而本家打牌后 `room.seq` 正在变化（`ApplyDiscard` 先关打牌窗口、再决定开 claim 窗口还是推进下一家）；只要 `tenpai` 的发送点早一拍，它就会带一个**比随后 `action_request` 更大的 seq**，把 `last_seq` 抬高 ⇒ 紧随其后的**鸣牌请求被当成过期帧丢掉** ⇒ 玩家收不到鸣牌提示、干等 15 s，且**只在「有人能鸣牌」时复现**。独立计数器彻底消除这类耦合，且对 UI 需求无损（我们只需要「能丢乱序旧帧」）。

**`remaining` 的冻结口径（协议 §11，只减客户端能看到的张数）**

```
remaining = 4
          − 本家手牌
          − 本家副露（全部类型）
          − 三家【公开】副露（pong / chow / kong / kakan）
          − 四家牌河
          − 他家 ankan：计 0（不扣）
```

> ⚠️ **公式恰好 4 项，没有第 5 项（v1.5 修正，协议同步）**：初稿还有「和牌张」与「已结算局的公开手牌」两项，**已全部删除，不留「恒为空」的标注**。理由：跨局时那批牌**不是同一批物理牌**（`StartRound` 每局重建 136 张牌山），上一局揭示的手牌扣进本局 `remaining` 会让它**虚低甚至为负**。标注「恒为空」会让实现者想着「留个 TODO 兜一下」，而兜了就是错的 ⇒ 直接删干净。
> **因此：实现不得触碰 `game_end.results[].hand`，也不得为听牌维护任何跨局可见牌集。** 协议侧原有一条「扁平手牌去重规则」只为那个跨局项存在，已一并作废。

- **他家暗杠必须计 0**：他家 `ankan` 的 `tiles` 对客户端是 `[]`（不可见，`UI_UX_SPEC.md` §4.8）。若按 4 张扣减，本家会看到「某人暗杠后某面 `remaining` 突降 4」⇒ **反推出他暗杠的是哪个牌面**，把暗杠打码从另一条路绕开。公开的只有「某座位杠了」，不是「杠的是什么」。
- **代价（写进 UI 说明）**：别人暗杠 `5z` 后你若听 `5z`，会显示「还剩 N」而真实可摸为 0。所以「`N` 枚」的语义是**「还没露面的最多还有 N 张」**；§2.3 的颜色编码不用改（`0 ⇒ NEG` 仍成立：`0` = 已全部露面）。
- **他家明杠/碰/吃/加杠可扣**（`tiles` 在 `seats[].melds[]` 里完全可见），扣了更准且零泄露。
- ⚠️ **`F-TP-13` 增量计数表必须每局清零**：若为性能实现「34 面可见计数增量表」（协议 PB-2 的降级路径），**必须在本局 `StartRound` 时清零**。否则跨局残留 = 与上面完全相同的「虚低」错误，而且**更难查**（因为它是状态而不是计算）。协议侧已写死同一条。

**下发时机（已冻结为协议 T1–T6）**

| 时机 | 动作 |
| --- | --- |
| 本家 `discard` 生效后 | **发**（13 张口径的真实听牌状态） |
| 本家副露（`pong`/`chow`/`kong`/`ankan`/`kakan`）生效后 | **发**（副露改变牌形，必须重算） |
| 收到本家 **`sync`** 请求后 | **补发一次**（`sync` 是客户端唯一的全量对齐手段；`waits` 从 `state_sync` 搬到独立帧后，`sync` 不再携带听牌状态，不补发会让听牌条永久停在旧值） |
| 本家 `draw` 后、`discard` 前 | **不发** —— **本条已裁决（v1.6，创意总监终裁，协议 T4 的待裁决项闭环）**：① 14 张口径**没有「听牌」定义**；② 若按「打掉刚摸那张」去算，等于替玩家做了唯一的打牌假设，与 §0 第 4 条「不设计帮玩家决策的功能」直接相抵；③ 摸牌后 ≤15 s 内本家必打牌，下一条 T1 立刻补上最新值，**玩家不可感知**。若将来要改判为「发」，唯一冻结口径是「`is_tenpai`/`waits` 仍按**打掉刚摸那张之后的 13 张**计算」，**字段与形状不变**、实现只多一处调用点 |
| 其他三家的任何动作 | **不发**（本家手牌没变） |
| 局终（`game_end`）/ 新一局（`game_start`）/ 场终（`match_end`） | **不发**（客户端按 §2.4 自行清零；结算页没有听牌条，发了是死数据） |

- **为什么独立帧而不是塞进 `state_sync`**：`state_sync` 是「每次摸牌向 4 家各发一份」的热路径，且其 `seats` 块是「一次渲染喂四家」的共享结构（`room.cc` 的既有优化）；塞入本家专属字段会让该结构按座位分版本。
- **为什么不放进 `action_request`**：玩家打牌后仍需要持续看到听牌状态（等别人打出的那段时间才是提示最有用的时候），`action_request` 在手牌变化后就不再有该信息。
- **性能预算（协议门禁，实现不得超线）**：`WaitingTiles` 单次 ≤ **200 µs**；单条 `tenpai` 构建 ≤ **300 µs**、帧 **< 1 KB**；超线先上「34 面可见计数增量表」，再退化为「仅变化时下发」。频率上界：每本家回合 ≤ **2 条** ⇒ 一局 < **170 条** ⇒ 场次 < **1400 条** ⇒ **< 2 条/秒**、**只发 1 份**（对比 `state_sync` 一局 ≥ 136 份 × 4 家广播，量级约 1/8）。
- ⚠️ **`remaining` 是否算「作弊」**：不算。真麻将玩家可以从四家牌河 + 公开副露人工数出剩余枚数；本作把这个「手动可得的公开信息」自动化，属于降低操作负担，不是给未公开信息。**而不可见的部分（他家暗杠）本规格明确不扣**，见上。

### 2.3 剩余枚数的颜色编码（信息密度靠颜色，不靠数字堆叠）

| `waits[].remaining` | 颜色（取 `UI_UX_SPEC.md` §1.4 常量） | 附加表现 |
| --- | --- | --- |
| `≥ 3` | `POS` | 无 |
| `== 2` | `TEXT` | 无 |
| `== 1` | `WARN` | 该项牌名后追加 `·` 标记（1 个点，象征「只剩一张」） |
| `== 0` | `NEG` | 牌名加**删除线**（`remaining == 0` 说明已被打完，理论上不该出现在 `waits` 里，属服务端异常，客户端照画不崩） |
| **`> 4`（越界）** | `NEG` | **视为服务端缺陷**（协议 §5.16 冻结 `waits[].remaining ∈ [0,4]`）：按 `NEG` 照画、**不崩**、记 WARN。**这是"两个 `remaining` 混用"最便宜的探测器** —— 若有人把 `wall_remaining_`（牌山剩余，常 > 4）填进来，**一条范围断言就能抓住**，不必等玩家看出数字不对 |

- **「`N` 枚」的语义是「还没露面的最多还有 N 张」**，不是「还能摸到 N 张」——他家暗杠的 4 张不可见、不计入扣减（§2.1），因此存在「显示 2 枚、实际可摸 0 张」的可能。这是**刻意选择**：宁可枚数偏乐观，也不通过枚数变化泄露他家暗杠的牌面。
- **不显示「和牌概率」「听牌强度」**：本作无役种起和限制、无符数，任何完成形都能和；再算概率就是算牌器。

### 2.4 开关与清零时机

| 常量 | 值 | 说明 |

## 4. 自动理牌

### 4.1 结论先写：本作的「自动理牌」= **服务端新增排序** + 客户端零重排

> ⚠️ **前提修正（v1.2，主理人核代码后纠正）**：**当前服务端并未对手牌排序**（`room.cc` 只有座位排序与名次排序，发牌后手牌按插入顺序保存在 `hands_[seat]`）。
> 因此「自动理牌」**不是沿用既有行为，而是 B 批要新增的服务端行为**。本节 `F-SORT-01` 是对 `RoomActor` 的**规格要求**，不是对现状的描述。

| 常量 | 内容 |
| --- | --- |
| `F-SORT-01` 排序键（**服务端新增实现，冻结**） | `(suit_index, rank, copy)`，其中 `suit_index: m=0, p=1, s=2, z=3`；数牌 `rank = 1..9`，字牌 `rank = 1..7`（`1z`..`7z`）；`copy = 0..3`。**先数牌后字牌**（`GAME_DESIGN.md` §3.1） |
| `F-SORT-01b` 服务端排序触发点（**新增，四个时机，缺一不可**） | ① **发牌后、`game_start` 下发前**；② **每次普通摸牌后**；③ **每次杠补牌后**（暗杠/加杠/明杠同源）；④ **每次鸣牌扣牌后**（`pong`/`chow`/`kong` 生效时从手牌移除 2/3 张之后）。排序对象恒为 `hands_[seat]`，四家都排（他家虽不可见，但 `hand_count` 与后续判定依赖同构数据，不得只排真人座位） |
| `F-SORT-01c` **DRAWN 标记随牌移动（硬约束）** | 排序**不得改变任何一张牌的 `copy` 身份**（`copy` 是排序键的第三分量 ⇒ 同面 4 张副本在排序后仍是同一相对次序）；**客户端禁止**用「手牌最后一个元素 / 数组末尾」判定「刚摸到的牌」——一旦服务端开始排序，末尾元素与摸到的牌**没有任何关系**。正确做法：收到 `draw.tile` 后按**牌面**匹配、取同面中**最左**一张打 `DRAWN` 标记（`UI_UX_SPEC.md` §4.5 已冻结的口径），排序后该面整体位置改变、标记自然跟着走 |
| `F-SORT-02` 客户端行为 | **不排序、不重排、不缓存顺序**：直接按 `state_sync.hand[]` / `game_start.hand[]` 的数组顺序绘制（`UI_UX_SPEC.md` §4.5 冻结：客户端重排会导致点击命中与服务端顺序错位）。**服务端排序后，客户端这段逻辑一行不用改** —— 这正是把排序放在服务端的第二个好处 |
| `F-SORT-03` 新摸的牌位置 | **插入排序后的自然位置**（由服务端给），客户端**就地标记 `drawn`**（`DRAWN` 2 px 描边 + 上移 4 px + 右上角 14×14 实心方块，`UI_UX_SPEC.md` §4.4）。**不设独立右侧摸牌槽位**（同 §4.5 冻结，理由：副本不可区分 + 排序键唯一） |
| `F-SORT-04` 摸牌进场动画 | **120 ms**：该张 `y` 从 `y0+16` 上移至 `y0`（`ease-out quad`）+ `DRAWN` 描边 `alpha 0→255`（120 ms） | 见 §6.3 |
| `F-SORT-05` 副露后的手牌收缩 | 副露生效后手牌少 2/3/4/1 张：**其余牌位在 160 ms 内水平滑到新 `x`**（`ease-out cubic`），不做逐张淡出 | 与 §6.4 鸣牌动画同一时间轴 |
| `F-SORT-06` 拖拽/旋转/手动排序 | **本期不做，且建议永久不做**（理由三条见 4.2） | — |

### 4.2 为什么不做拖拽/旋转（三条理由，逐条可核）

1. **会被 `state_sync` 打回**：手牌顺序的唯一权威是服务端（`F-SORT-01/02`）。玩家拖完，下一次 `state_sync`（每次摸牌/打牌都会来）就会按服务端序重画 —— 玩家看到的是「我理好的牌又被改回去了」，这是比「不能拖」更差的手感。
2. **拖拽会破坏点击命中**：手牌命中测试按服务端顺序下标定位（`UI_UX_SPEC.md` §4.5）；一旦本地顺序偏离，`selected_index` 与服务端牌面必须额外维护一份映射，而**同牌面副本不可区分**（`GAME_DESIGN.md` §5.6.2），映射不可验证 ⇒ 出牌可能打错牌。
3. **收益为零**：服务端序已经满足「同花色同点数相邻、字牌在后」，这正是自动理牌的全部目的。玩家手工微调只在「想按听牌分组」时有用，而该需求已由 §2 的听牌条覆盖。

### 4.3 他家 / 观战

- 他家手牌只有 `hand_count`（牌背张数），无排序概念（`UI_UX_SPEC.md` §4.6）。
- 副露区按 `melds[].tiles[]` 顺序渲染，**客户端不再排序**（同 `F-SORT-02`）。

| `F-AU-16` `match_end` | `match_end`（场终） | **P0** | 可 | 切到场终页后 120 ms | **有仪式感**的铃 + 和弦余韵（比 `F-AU-15` 更长更完整）；情绪：**整场落幕** | **≤ 1600 ms** | **允许长尾** |

> ⚠️ **和牌音的两条触发判定（v1.7 修正，实现按此写）**：`win.tsumo` **只存在于 `game_end` 载荷**，而和牌音必须在 `action_event{action:7}` 时就响（`game_end` 到达偏晚，等它会拖掉整个和牌的即时感——`PROTOCOL.md` E7/E8）。因此判定**改用 `action_event.from_seat` 是否存在**：**有 = 荣和 → `F-AU-09`；无（`null`）= 自摸 → `F-AU-10`**。这是协议已冻结的语义（§11.2.1-B），不需要新增字段。

**三条音色总原则（交音效总监时必须一并理解）**

1. **不抢牌桌信息**：音的职责是「确认动作已发生」，不是表演。同一局内连续 20 次出牌，`F-AU-03` 不得让玩家厌烦 —— 宁可寡淡，不可悦耳过头。
2. **同族必须同材质**：碰/吃/杠（含暗杠、加杠）同属「动作应答」族，必须能听出是一家人；荒庄/局终/场终同属「收束」族；`F-AU-09` 与 `F-AU-10` 必须能盲听分辨（荣和 vs 自摸是本作唯一的「和牌方式」差异，`GAME_DESIGN.md` §6.5 要求界面明示）。
3. **禁用项**：**不得**出现人声/语音、不得含背景音乐式循环、单条样本内音高事件 **≤ 4 个**（避免喧闹）、不得使用现实「洗牌/牌堆倒塌」声（会让玩家误判有人在鸣牌）。

### 5.3 交付契约（本文对音效总监的验收口径）

| # | 要求 |
| --- | --- |
| D1 | 16 个 id 各交付 **1 个**样本文件，命名 `sfx_<id>.ogg`（如 `sfx_win_ron.ogg`），放 `game/client/assets/sfx/`。**本行是命名与路径的唯一权威**（`AUDIO_SPEC.md` 的映射表须落到本路径下，不得另立目录，v1.3） |
| D2 | 每条满足 `F-AU-00c` 的四项准入线（44.1 kHz 单声道 / 峰值 ≤ −3 dBFS / 首尾无静音 / 不循环）。**格式参数的唯一权威在本行**，`AUDIO_SPEC.md` 不得另定第二套（v1.3） |
| D3 | 每条**实测时长 ≤ §5.2 的上界**；上界是硬线（超时即视为不合格，需换样本或裁剪，不允许「先接进来再说」） |
| D4 | 授权与合规（**权威在 `AUDIO_SPEC.md`**）：开源包许可须可商用/可再分发，来源与许可文本由音效总监归档并登记在交付说明里（本项目零收集、纯本地，**不得**引入需联网校验的素材） |

### 5.4 同刻多音与打断规则（**唯一一套，不得各自实现**）

| 常量 | 规则 |
| --- | --- |
| `F-AU-20` 并发上限 | 同一时刻最多 **3 个**音效并存（WIN 组 1 + ACTION 组 1 + UI 组 1），各占独立通道（`F-AU-00`） |
| `F-AU-21` P0 强制静场 | P0（`win_ron` / `win_tsumo` / `match_end`）起播时：ACTION 组与 UI 组通道 `fadeout(30 ms)` 后停，**保证和牌音不被出牌/按钮音糊住** |
| `F-AU-22` P1 组内抢占 | ACTION 组通道上，新音**立即**抢占旧音（`channel.stop()` 后起播，不做交叉淡入）；同一事件的重复帧（同 `seq`）**不重播** |
| `F-AU-23` UI 组不被抢占 | UI 组（点击音）只与自己抢；**不**打断 ACTION/WIN |
| `F-AU-24` 去重键 | 每次播放记录 `(id, seq)`；同一 `seq` 的同一 `id` 在 **200 ms** 内重复到达则丢弃（防 `state_sync` 抖动连播） |
| `F-AU-25` 静音/缺资产 | `M` 关闭或样本缺失时**不出声**，但**照常走 §5.2 的时机判定**（重开或补齐后不会补播积压） |
| `F-AU-26` 切屏静场 | 任何屏切换（`SCREEN_TABLE`↔`SCREEN_RESULT`↔`SCREEN_LOBBY`）时 `channel0..2` 全部 `fadeout(40 ms)` |
| `F-AU-27` **同通道 P0 后到者抢占** | WIN 通道（`ch0`）只容 1 条 P0（`F-AU-20`）。**一场最后一局**的真实情况是：`win_tsumo`（≤1400 ms）尚未播完，`match_end`（≤1600 ms）已在切场终页后 120 ms 起播 ⇒ **`match_end` 立即抢占 `win_tsumo`**（`stop()` 后起播，不做交叉淡入）。这**不算**破坏「和牌音不可被打断」（`F-AU-21`）：两者不共享同一局叙事，场终是整场收束，必须压在最后；反之若让和牌音播完再放场终音，玩家会听到两个「结束」叠着来，更糟 |

### 5.5 为什么本批改用开源包（而不是程序合成）

- 程序合成能给出「零资产、零版权」的确定性，但**音色上限低**（无采样包络、无混响），做不出「碰/杠/和牌」之间的材质区分 —— 而本批要解决的正是「打起来没手感」，音色单薄等于没做。
- 开源包能把「材质与情绪」做到位，代价是引入外部资产，因此**准入线（`F-AU-00c`）与授权归档（D4）**成为硬要求：这是本项目第一次引入二进制资源，必须留下可审查的来源记录。
- 本文的角色因此收敛为：**定约束、定时机、定优先级、定上界**；**不**定波形 —— 后者属于音效总监的专业判断。

## 6. 出牌动画与节奏预算

### 6.1 硬约束（先写约束，再写动画）

| 常量 | 值 | 判据 |
| --- | --- | --- |
| `F-AN-01` 手感预算 | **300 ms**：从「收到使本家可操作的帧」（`action_request{window:1}` / 新 `game_start`）到「手牌可点」 | 期间播放的动画总时长必须 ≤ 300 ms；超出的动画**不允许**安排在该窗口之前 |
| `F-AN-02` 输入永不阻塞 | 手牌命中与按钮点击在任何动画播放期间**都有效** | 动画只是绘制层，不接管输入；点击立即触发对应逻辑 |

| 常量 | 值 |
| --- | --- |

### 6.6 动画与状态帧的冲突处理（幂等）

1. 任何 `state_sync` 到达 ⇒ 立即按权威数据重绘，**正在播放的动画全部 snap**（`F-AN-03`）。
2. 动画只维护「视觉插值进度」，**不持有任何对局数据**；数据永远从 `game_state` 读（`UI_UX_SPEC.md` §11 的分层不变）。
3. 同一张牌不允许同时存在「手牌里的一份」与「飞行中的一份」超过 1 帧（`F-AN-16`）。

### 6.7 加速与抢占的判定顺序（实现照抄）

```
on_event(frame):
  1) 若 --no-feel / 断线 / 结算页 → 直接按终态绘制，return
  2) snap 所有进行中的动画到终态            # F-AN-03
  3) 更新 game_state（唯一的权威状态）
  4) 计算本次要播的动画集合；若「距上次操作 < 400ms」→ speed = 2.0，否则 1.0   # F-AN-04
  5) 若动画总时长 > 300ms 且该帧会使本家可操作 → 截断为 300ms（优先压缩非关键动画：淡入类） # F-AN-01
  6) 启动动画 + 播 §5 的音效（各自独立计时）
```
